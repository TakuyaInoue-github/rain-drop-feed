## このスキルの目的

このリポジトリの `docs/` 配下にある要求定義・要件定義・機能・仕様・ADRの
**初稿生成** および **レビュー・抜け漏れチェック** を行う。

### 層の責務（必ず守ること）

| 層 | 問いに答える | 書かないこと |
|---|---|---|
| 要求定義 (R) | なぜ作るか・誰が困っているか | 解決方法（How） |
| 要件定義 (REQ) | システムが満たすべき性質 | 実装の詳細 |

| ADR | なぜその設計にしたか | 実装手順 |

## 粒度ルール（生成・レビュー時に常に適用する）

> **重要:** 粒度・境界の判断に迷ったら、必ず `05_guides/granularity_guide.md` を参照すること。
> 以下は概要のみ。具体例・アンチパターン・判断フローは granularity_guide.md に詳述されている。

### Fの粒度（概要）
- **1F = ユーザーストーリーが1文に収まるゴールの単位**
- So that（価値）が異なる → 分割する
- アクターが異なる → 分割する
- UIの1ステップにすぎない → 上位Fに統合する

### SPECの粒度（概要）
- **1SPEC = 独立したフロー定義表を必要とする振る舞いの単位**
- フロー定義表が15行を超える → 分割を検討する
- 独立した状態機械が混在している → 分割する
- FとSPECは1:1でなくてよい（1Fが複数SPECを持つ、複数Fが1SPECを共有、どちらも自然）

### FとSPECの境界（概要）
- ユーザーが観察できる振る舞い → F（受け入れ基準）
- 内部動作・実装詳細（型・桁数・暗号化方式・タイムアウト値）→ SPEC
- エラーメッセージの文言 → SPECに一元化（Fには「表示されること」まで書く）

### ADRの粒度（概要）
- **1ADR = 1つの意思決定**
- 決定事項が一文で書けない（複数の動詞・対象物が並記される）→ 分割する
- 評価軸が独立した2テーマに分かれ、一部の選択肢にしか適用できない軸がある → 分割する
- 後続アクションが互いに独立してリリース・撤回できる → 分割を検討する

→ **詳細:** [05_guides/granularity_guide.md](05_guides/granularity_guide.md)

## 執筆品質の原則（生成・レビュー時に常に適用する）

### 独立検証

セルフレビュー（同一セッション・同一執筆者によるレビュー）は執筆時の暗黙の前提を
引き継いでしまうため、抜け漏れの検出力が低い。各テンプレートの完了チェックリストに
ある「独立コンテキストによる初稿レビューを受けている」を満たすには、
[05_guides/prompts/independent_review.md](05_guides/prompts/independent_review.md)
を、執筆に使ったセッションとは別の新しいセッション・サブエージェントで実行すること。

### セクションの必須/任意化（実測してから判断する）

テンプレートの各セクションが実質的な内容を持たず、毎回「対象なし」等の定型文で
埋められているだけの状態は "mandatory but useless" であり、テンプレートの信頼性を
下げる。F-xxx / SPEC-xxx / ADR-xxx の実文書がそれぞれ **5本以上** 蓄積された場合は、
各セクションが定型文で埋まっている割合を `grep` 等で機械的に確認し、大多数
（目安7割以上）が定型文で済んでいるセクションは「該当する場合のみ追加する任意
セクション」として切り出すことを検討する。**実文書が少ない間はこの判断を保留する**
（推測で必須/任意を決め打ちしない）。

### 実装とのcompliance verification（任意・実装完了後）

このスキルの目的（ドキュメントの生成・レビュー）自体は変わらないが、SPEC/Featureが
`approved`になり実装が完了した後、文書の記述と実装コードが一致しているかを検証したい
場合は [05_guides/prompts/compliance_verification.md](05_guides/prompts/compliance_verification.md)
を使う。このリポジトリ自体は実装コードを持たないため、実行時は利用者自身の
リポジトリにある実装コードのパスを対象ドキュメントとあわせて渡す。独立検証
（`independent_review.md`）が文書自体の品質を見るのに対し、こちらは文書と実装の
一致を見る点で対象が異なる。

## ワークフロー

### A. 初稿生成

```
1. ユーザーからコンテキストを収集する（後述の「必要なコンテキスト」を参照）
2. 対応するテンプレートを docs/02_features/_template.md 等から読み込む
3. 粒度ルールを適用しながらテンプレートを埋める
4. **YYYY-MM-DD 形式の日付プレースホルダーは、生成時の実際の日付（今日の日付）に置き換える**
5. 完了チェックリストの各項目を自己評価し、未充足の項目を末尾に列挙する
6. README.md のタスク一覧への登録が必要な OQ があれば明示する
```

**生成時の禁止事項:**
- 受け入れ基準から `[エラー系]` `[境界値]` `[権限]` のカテゴリを省略しない
- フロー定義表から例外系を省略しない（「後で追記」は不可）
- 入力定義の「NULL・空文字の扱い」列を空欄にしない
- 成功基準を定性的な表現（「改善する」「使いやすくする」）で書かない

**用語定義の管理:**
- ドキュメント生成時に専門用語・ドメイン用語が新しく登場した場合は、必ず `00_glossary.md` に追記すること
- 既存の用語と意味が重複する場合は、正式名称を統一すること

### B. レビュー・抜け漏れチェック

```
1. 対象ファイルを読み込む
2. そのドキュメント種別の完了チェックリストを適用する
3. 粒度ルールを適用して粒度の問題を検出する
4. 結果を「問題あり / 要確認 / 問題なし」の3段階で報告する
5. 「問題あり」の項目には具体的な修正案を示す
```

## ドキュメント種別ごとの詳細指示

### business_requirements.md の生成

**必要なコンテキスト（ユーザーから収集する）:**
```
- プロジェクト名・一行サマリー
- 困っているのは誰か（ロール・ペルソナ）
- 何をしようとしたときに困るか（トリガー）
- 現状何が起きているか（観察できる事実）
- 解決後にどう変わるか（To-Be）
- スコープに含めないもの
- リリース期限・予算等の制約（あれば）
```

**生成時の注意:**
- 症状と根本原因を必ず区別して記述する
- 成功基準は必ず定量値・測定方法・計測タイミングをセットで書く
- Out of Scope は「対象外の理由」とセットで書く
- 各 R-xxx に優先度（Must/Should/May）と根拠を必ず付ける

---

### system_requirements.md の生成

**必要なコンテキスト:**
```
- アプリケーション種別（Web / バッチ / CLI / デスクトップ GUI 等）
- 公開範囲（社内限定 / 特定パートナー / 一般公開）
- ユーザーロールの一覧
- 主要な機能の概要（F-xxx が未作成の場合）
- 性能目標の根拠となるデータ（アクセス数・データ量等）
- 連携する外部システムの一覧
```

**生成時の注意:**
- 機能要件は「[ロール]は、[状態・条件]のとき、〜できること」の形式を守る
- 非機能要件の数値には必ず根拠を記載する（「なんとなく2秒」は不可）
- 外部システム連携テーブルの「障害時の挙動」列を省略しない

---

### F-xxx の生成

**必要なコンテキスト:**
```
- 機能名
- 対象ユーザーロール
- ユーザーが達成したいゴール
- 得られる価値（So that）
- 対応する要件 ID（REQ-F-xxx）
- 依存する既存機能（あれば）
```

**生成時の注意:**
- ユーザーストーリーの So that を「〜できる」で終わらせない
- 受け入れ基準は `[正常系]` `[エラー系]` `[境界値]` `[権限]` の4カテゴリを必ず含める
- UXフローは成功パスだけでなくエラー時の分岐を含める
- 粒度ルール（Rule F-1〜4）を適用してゴール単位になっているか確認する

---

### SPEC-xxx の生成

**必要なコンテキスト:**
```
- 対応する機能 ID（F-xxx）
- この仕様が定義する振る舞いの概要
- 入力項目の一覧（名称・型・必須/任意）
- 状態遷移の有無
- 外部システム連携の有無
```

**生成時の注意:**
- フロー定義表は主系・代替系・例外系を同一テーブルに記述する
- 例外系の9チェックリストを必ず確認する:
  未認証 / 権限違反 / 必須項目未入力 / 最大値超過 / 空文字NULL /
  外部システム障害 / タイムアウト / 同時操作競合 / リソース不存在
- 入力定義の「NULL・空文字の扱い」を全項目に記載する
- 状態遷移がある場合「不可の場合の挙動」列を省略しない
- 粒度ルール（Rule S-1〜4）を適用して独立した状態機械が混在していないか確認する
- フロー定義表の条件/トリガーには WHEN/IF/WHILE/WHERE のいずれかを先頭に付けることを
  検討する（常時成立する場合は付けなくてよい）
- テスト観点には「反証可能性（どう壊せばレッドになるか）」を明記する。
  「〜を確認する」としか書けない観点はAC自体かテスト設計を見直す

---

### ADR の生成

**必要なコンテキスト:**
```
- 意思決定が必要になった背景・制約
- 検討している選択肢（2つ以上）
- 重視する評価軸（パフォーマンス・コスト・習熟度 等）
- 現時点での傾き（あれば）
```

**生成時の注意:**
- 評価軸を先に定義してから各選択肢を同じ軸で評価する
- 不採用の選択肢にも「なぜ不採用か」を明記する
- 受け入れたトレードオフを隠さない
- 後続アクションは README.md の TASK-xxx と紐づける
- 再検討条件（どんな状況になったら見直すか）を必ず書く
- 粒度ルール（Rule ADR-1〜4）を適用して1つの決定に集中しているか確認する

## README.md タスク登録ルール

生成・レビューの結果、以下が発生した場合は **必ず README.md のタスク一覧への登録を促す**:

- OQ（未解決の問い）が発生した
- チェックリストに `-`（未検討）の項目がある
- レビューで「要確認」の項目が出た
- ADRの後続アクションが定義された

登録フォーマット:
```
| TASK-xxx | [種別] | [タイトル] | [発生元リンク] | - | YYYY-MM-DD | `open` | - |
```
