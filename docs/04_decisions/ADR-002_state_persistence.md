## コンテキスト

REQ-F-002 は「処理したエントリを、投入の有無にかかわらず処理済みとして永続化する」ことを
**Must** として求めている。この状態が実行をまたいで保持されることが、R-002（重複排除・冪等性）と
R-006（閾値未満エントリの記録による事後検証）の両方の前提である。

本システムは GitHub Actions のランナー上で週1回実行される。**ランナーは実行ごとに破棄される
（ephemeral）ため、状態を明示的にどこかへ退避しなければ、毎回の実行がすべてのエントリを
新規とみなす。** どこへ退避するかが本ADRの主題である。

`.ref/spec.md` は `state.sqlite` というファイル名を挙げているが、それをどう実行間で
保持するかには触れていない。要件定義 OQ-001 でも未解決事項として残されていた。

### 上位要件との関係（許容するリスクの範囲）

REQ-NF-004 は「消失時は重複投入が発生しうることを**許容する**」とし、REQ-NF-003 は
RPO を1週間としている。つまり上位要件は状態消失を「許容するリスク」と位置づけている。
**本ADRはこれを否定しない。**

ただし、許容するのは **例外時に一度起きること** であり、**構造的に毎回起こりうること** ではない。
実行の失敗のたびに状態が全損する方式は後者にあたるため、上位要件の許容範囲外と判断する。
この線引きが、以下の選択肢比較における「永続性の確実性」軸の意味である。

なお本質的な被害はコストではなく、**収集レイヤーへの重複投入**である。Raindrop に同じ記事が
何度も積まれると週次レビューの対象として使い物にならなくなり、R-001 で解決したはずの問題が
形を変えて再発する。

### 判断に用いた実測・調査

**状態のサイズ（2026-07-26 のフィード実測に基づく試算）:**

| 想定 | 1年 | 3年 | 5年 |
|---|---|---|---|
| 実測（40件/週） | 2,080行 / 0.3〜0.7 MB | 6,240行 / 0.8〜2.0 MB | 10,400行 / 1.3〜3.3 MB |
| 上振れ（100件/週） | 5,200行 / 0.6〜1.6 MB | 15,600行 / 1.9〜4.9 MB | 26,000行 / 3.2〜8.2 MB |

GitHub の個別ファイル警告は 50MB、上限は 100MB。**5年運用しても2桁の余裕がある。**
サイズはどの選択肢でも制約にならない。

**GitHub Actions の仕様（2026-07-26 に公式ドキュメントで確認。→ 詳細は補遺B）:**

| 事項 | 確認結果 |
|---|---|
| cache の退避 | 「7日を**超えて**アクセスされていない」エントリを削除。起点は作成日ではなく **last access date**（[出典](https://docs.github.com/en/actions/reference/dependency-caching-reference)） |
| **restore がアクセス扱いになるか** | **公式に明言なし。** 文言上そう読めるが、`last_accessed_at` を更新する保証は文書化されていない |
| cache の容量上限 | 既定 10GB/リポジトリ。超過時は last access 順に退避 |
| cron の信頼性 | 遅延しうる。高負荷時は **"some queued jobs may be dropped"**（発火しないことがある）と公式が明言（[出典](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)） |
| scheduled workflow の60日自動停止 | **public リポジトリ限定**と公式に明記。private での発生はコミュニティ報告のみで一次情報では未確認 |
| `GITHUB_TOKEN` による push | 新規ワークフローを**トリガーしない**（無限ループ防止の仕様）。したがって `[skip ci]` は不要（[出典](https://docs.github.com/en/actions/concepts/security/github_token)） |
| ブランチ保護 | 保護されたブランチへは許可されたアクターのみ push 可能。`GITHUB_TOKEN` に一律の回避特権はない |
| ブランチ保護の適用範囲 | **特定ブランチ／パターンに対する opt-in。** 既定ブランチのみ保護した場合、保護のない他ブランチへは自由に push できる |

> **重要な不確実性:** restore がタイマーをリセットするかは**公式に明言がない**。
> したがって本ADRは、この挙動が「する／しない」いずれであっても結論が変わらない形で
> 判断を組み立てる（選択肢Bの不採用理由は restore の挙動に依存させない）。

## 決定事項

**処理済み状態を、既定ブランチとは別の状態専用ブランチへコミットして永続化する。**

## 選択肢の比較

> **ルール:** 検討した選択肢をすべて記述する。採用・不採用を問わず並べて評価する。

### 評価軸

| 評価軸 | 重み | 定義 |
|---|---|---|
| 永続性の確実性 | 高 | 状態が失われないこと。特に **実行失敗が状態の全損に直結しないこと**（REQ-NF-003 は年数回の失敗を織り込む） |
| 復旧可能性 | 高 | 状態が壊れた・誤って消えた場合に、過去の状態へ戻せるか |
| 運用の単純さ | 中 | 追加のサービス契約・認証情報・インフラ管理を要しないか（要求定義 §7 の制約） |
| 事後検証のしやすさ | 中 | R-006（閾値の妥当性検証）のために、蓄積データを参照・分析しやすいか |
| 既定ブランチへの影響 | 中 | 開発用の履歴・ブランチ保護運用を妨げないか |

---

### 選択肢 E: 状態専用ブランチへコミットする ★採用

状態ファイルを、既定ブランチとは独立したブランチ（例: `state`。履歴を共有しない orphan branch）
に置き、実行の最後にそのブランチへコミット・プッシュする。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 永続性の確実性 | ◎ | Git リポジトリが保持する。有効期限による自動削除がない。実行が失敗しても直前の状態は残る |
| 復旧可能性 | ◎ | コミット履歴が世代管理を兼ねる。任意の時点へ戻せる。監査証跡にもなる（enterprise_checklist C-L02 に合致） |
| 運用の単純さ | ○ | 追加の契約・認証情報が不要（`GITHUB_TOKEN` で完結）。ブランチを1本増やす手間はある |
| 事後検証のしやすさ | ◎ | `git fetch origin state` で全履歴が手元に来る。任意のツールで分析できる |
| 既定ブランチへの影響 | ◎ | **既定ブランチの履歴を汚さない。ブランチ保護も自由にかけられる**（保護は opt-in であり、状態ブランチを対象外にすればよい） |

**採用する理由:**

選択肢A（既定ブランチへコミット）の利点（永続性・復旧可能性・追加インフラ不要）を
すべて保ちながら、その2つの弱点を構造的に解消する。

1. **既定ブランチの履歴が汚れない。** 週1回のボットコミットが人間の変更に混ざらない
2. **ブランチ保護と両立する。** ブランチ保護は特定ブランチ／パターンへの opt-in であるため、
   既定ブランチを保護したまま、状態ブランチへは `GITHUB_TOKEN` で push できる。
   グローバル規約「main には直接コミットしない」とも衝突しない

サイズが制約にならないことは実測で確認済みである（5年で最大8.2MB、上限100MBに対し2桁の余裕）。
本システムの状態は**追記が主で更新が稀**という性質を持ち、Git の得意な形と合致する。

要求定義 §7 の制約「常時稼働のサーバーを用意せず、既存の CI 基盤上で完結させる」に対し、
**追加のインフラも契約も要しない**点が適合する。バックアップを別途用意しないという
enterprise_checklist の判断（R-B01〜B04 を ✗）とも整合する — Git 履歴が事実上の履歴保全になる。

---

### 選択肢 A: 既定ブランチへコミットする

状態ファイルをリポジトリ内に置き、実行の最後に既定ブランチへコミット・プッシュする。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 永続性の確実性 | ◎ | 選択肢Eと同等 |
| 復旧可能性 | ◎ | 選択肢Eと同等 |
| 運用の単純さ | ◎ | ブランチ切り替えが不要な分、Eよりわずかに単純 |
| 事後検証のしやすさ | ◎ | 選択肢Eと同等（`git pull` のみで済む分わずかに容易） |
| 既定ブランチへの影響 | ✗ | **ボットコミットが履歴を占有する。** かつ **既定ブランチにブランチ保護をかけると `GITHUB_TOKEN` の push が拒否され、週次実行が静かに失敗し続ける** |

**不採用の理由:**

永続性・復旧可能性は選択肢Eと同等だが、**既定ブランチへの影響で明確に劣る**。

決定的なのはブランチ保護との非互換である。保護を有効化した瞬間に push が拒否され、
かつ**その失敗は静かに起きる**（状態が更新されないまま実行だけが続き、次回に重複投入が発生する）。
個人リポジトリでは bypass の設定手段も限られる。
グローバル規約が「main への直接コミットを避ける」としていることとも噛み合わない。

選択肢Eがこの欠点だけを取り除いた上位互換であるため、Aを選ぶ理由がない。

### 選択肢 B: GitHub Actions の cache を使う

`actions/cache` で状態ファイルを実行間で受け渡す。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 永続性の確実性 | ✗ | **実行が1回失敗・スキップされれば間隔が14日となり、キャッシュは確実に失われる。** 加えてリポジトリ全体の cache 容量（既定10GB）超過時にも last access 順に退避される |
| 復旧可能性 | ✗ | 世代管理がない。消えたら復旧手段がない |
| 運用の単純さ | ◎ | ワークフローに数行足すだけ。追加の認証情報が不要 |
| 事後検証のしやすさ | △ | キャッシュの中身をローカルに取り出す手段が限られる。R-006 の分析がやりにくい |
| 既定ブランチへの影響 | ◎ | リポジトリの履歴に一切触れない |

**不採用の理由:**

**実行の失敗が状態の全損に直結する。** cron は公式に「高負荷時にジョブがドロップされうる」と
明記されており、REQ-NF-003 も実行成功率の目標を「直近8回のうち7回以上」＝**年に数回の失敗を
織り込んだ設計**としている。その前提のもとで、1回の失敗が全損を招く方式は成立しない。
これは「例外時に一度起きること」ではなく「構造的に毎回起こりうること」であり、
上記「上位要件との関係」で述べた許容範囲を外れる。

加えてキャッシュ消失は静かに起きる（エラーにならず、単に「全件が新規」として扱われる）ため、
運用者が気づく契機がないまま重複投入が発生する。

> **注記:** 定常運用時（毎週成功し続ける場合）にキャッシュが生き残るかは、
> restore が `last_accessed_at` を更新するかに依存し、**これは公式に明言がない**。
> ただし本ADRの不採用理由は「失敗時の全損」であり、restore の挙動がどちらであっても
> 結論は変わらない。定常時に生き残るとしても、失敗時に消える性質は解消されないためである。

### 選択肢 C: 外部ストレージ（S3 / Cloudflare R2 等）に置く

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 永続性の確実性 | ◎ | 有効期限がなく、耐久性も高い |
| 復旧可能性 | ○ | バージョニングを有効にすれば世代管理が可能。ただし明示的な設定が要る |
| 運用の単純さ | ✗ | **アカウント契約・バケット作成・認証情報の発行と管理が新たに発生する。** 秘匿情報の管理対象が増える（要求定義 §8 のリスク） |
| 事後検証のしやすさ | ○ | ダウンロードすれば分析できる |
| 既定ブランチへの影響 | ◎ | リポジトリに触れない |

**不採用の理由:**

永続性という一点では選択肢Eと同等だが、**運用の単純さで明確に劣る**。
個人の学習用ツールのために、追加のクラウドアカウント・バケット・認証情報を管理する
費用対効果が見合わない。要求定義 §7 は「既存の CI 基盤上で完結させる」ことを制約としており、
その意図（個人利用のために専用インフラを保有・保守しない）に反する。

選択肢Eで永続性・復旧可能性がともに満たせる以上、複雑さを増やす理由がない。

### 選択肢 D: Raindrop 上のデータを状態として使う（状態ファイルを持たない）

投入前に Raindrop の該当コレクションを検索し、URL が既に存在すればスキップする。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 永続性の確実性 | △ | Raindrop 側が保持するため消失しにくいが、利用者が手動で削除すると「未処理」に戻る |
| 復旧可能性 | ✗ | 削除された情報は戻らない |
| 事後検証のしやすさ | ✗ | **閾値未満で投入しなかったエントリが記録されない。R-006（生存者バイアスの排除）を原理的に満たせない** |
| 運用の単純さ | ◎ | 状態ファイルの管理そのものが不要 |
| 既定ブランチへの影響 | ◎ | リポジトリに触れない |

**不採用の理由:**

**R-006 を原理的に満たせない。** 本システムは「投入しなかったエントリもスコア付きで記録する」
ことを要求しており（REQ-F-007）、これは閾値の妥当性を事後検証するための母集団である。
Raindrop には投入したものしか存在しないため、この母集団が永久に得られない。

加えて、利用者が Raindrop 上で記事を手動削除する運用は自然に起こりうる（不要と判断した記事の整理）。
その記事が次回実行で「未処理」として再投入されると、削除の意図が無効化される。

### 選択肢 F: Actions Artifacts を使う

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 永続性の確実性 | △ | 保持期間は既定90日・最大400日で設定可能。週次実行に対しては十分な余裕があるが、**明示的な期限が存在する**ことに変わりはない |
| 復旧可能性 | △ | 期間内であれば過去の実行の artifact を取得できるが、Git のような連続した世代管理ではない |
| 運用の単純さ | ○ | 追加の認証情報は不要 |
| 事後検証のしやすさ | △ | ダウンロードに API 操作が必要。手元での分析がやりにくい |
| 既定ブランチへの影響 | ◎ | リポジトリの履歴に触れない |

**不採用の理由:**

選択肢Bより永続性は明確に高い（90日 ≫ 実行間隔7日）ため、Bのように「失敗1回で全損」にはならない。
しかし**期限が存在する以上、長期の運用停止（旅行・多忙による数ヶ月の放置）で失われる**。
本システムは無人運用を前提としており、利用者が数ヶ月放置する事態は現実的に起こりうる。

また R-006 の事後検証は「1年分のスコア分布を見る」性質のものであり、
90日（最大400日）の保持期間では母集団が欠ける。選択肢Eなら期限がなく、
`git fetch` だけで全期間のデータが手元に来る。

## 受け入れたトレードオフ

| あきらめること | その影響 | 緩和策 |
|---|---|---|
| ブランチを1本増やす | リポジトリの構成がやや複雑になる。状態を見るのに `git fetch origin state` が要る | 履歴を共有しない orphan branch とし、開発用の作業と完全に分離する。README に参照手順を書く |
| Actions に `contents: write` 権限を与える | ワークフローがリポジトリを書き換えられる。侵害時の影響範囲が広がる | 権限を当該ジョブの最小限に絞る（`permissions: contents: write` をジョブ単位で指定）。enterprise_checklist S-Z04（サービスアカウントの権限スコープ最小化）に合致 |
| 状態がリポジトリ内で可視になる | 処理した記事URL・スコア・評価理由が Git 履歴として残る | 扱うのは公開記事のメタデータのみであり機密性がない（要件定義 §6 で機密レベル「内部限定」と判定済み）。プライベートリポジトリでの運用を前提とする |
| 手動実行と定期実行が同時に走ると push が競合しうる | 後発の push が non-fast-forward で拒否される | **OQ-004 で解決済み。** `git pull --rebase` して行マージし再 push する（最大3回）。[ADR-005](ADR-005_state_file_format.md) の JSONL 採用により、両方の行を残すマージが成立するため投入済み分を失わない |
| プロセスが強制終了されるとその実行分の記録を失う | ジョブのタイムアウトによる SIGKILL 等でランナーごと破棄された場合、ローカルに追記済みで未 push の記録が失われ、次回に重複投入が発生する | **受け入れる。** OQ-003 の決定（実行末尾に1回 push）に伴う残存リスクであり、行マージでは救えない。REQ-NF-004 が「消失時は重複投入が発生しうることを許容する」としている範囲内。ただし発生時に運用者が気づけるよう、永続化の失敗はサマリに出す（F-004 AC-015） |
| 状態ファイルの形式変更が Git 上で大きな差分になりうる | マイグレーション時に履歴が読みにくくなる | **OQ-001 で解決済み。** 追記専用の JSONL（→ [ADR-005](ADR-005_state_file_format.md)）。行単位の追記のため差分が読め、形式変更の頻度も低い想定 |

## 影響・後続アクション

### この決定によって生じる影響

**ポジティブ:**
- R-002（冪等性）の保証水準が最も高くなる。有効期限による消失がなく、実行失敗でも状態が残る
- コミット履歴が世代管理と監査証跡を兼ね、バックアップを別途用意しない判断（R-B01〜B04 を ✗）が正当化される
- R-006 の事後検証を、`git fetch` した手元のデータに対して任意のツールで実行できる
- **既定ブランチにブランチ保護を自由にかけられる**。グローバル規約「main に直接コミットしない」と両立する
- 追加のサービス契約・認証情報が不要で、要求定義 §7 の制約に適合する
- `GITHUB_TOKEN` の push は新規ワークフローをトリガーしないため、無限ループの懸念がない

**ネガティブ / 受け入れるリスク:**
- ワークフローに `contents: write` 権限が必要になる
- 状態を参照するのに専用ブランチを fetch する一手間が生じる
- プロセスの強制終了時に、その実行分の記録を失う（→ OQ-003 の決定に伴う残存リスク）
- push 競合時に rebase + 行マージの処理が必要になる（→ OQ-004。ADR-005 の JSONL 採用により実装可能）

## 再検討条件

> **問い:** どんな状況になったらこの決定を見直すべきか？

- **状態ファイルが 50MB（GitHub の個別ファイル警告閾値）に近づいた場合** — 実測ベースでは
  5年で最大8.2MB のため当面到達しないが、記事本文の保存（現在スコープ外）を始めた場合や、
  情報源を桁で増やした場合は再評価する。古いエントリのアーカイブ、または外部ストレージへの移行を検討
- **状態ブランチの運用が実際に負担になった場合** — fetch の手間、CI 設定の複雑さが実害として
  現れたら、選択肢A（既定ブランチへコミット）への回帰を検討する。ただしブランチ保護を
  諦めることとのトレードオフになる
- **本システムが複数リポジトリ・複数環境から実行されるようになった場合** — push 競合が現実的な
  問題になるため、外部ストレージ（選択肢C）や排他制御の導入を再検討する
- **リポジトリを public にする場合** — scheduled workflow の60日自動停止が適用対象になる。
  本方式は毎週コミットが入るため自動的に回避されるが、その前提が効いていることを確認する
- **状態を Raindrop 以外の外部サービスと共有する必要が生じた場合** — 例えば別ツールから
  同じ処理済み情報を参照したくなった場合、外部ストレージのほうが自然になる

## 補遺B: 独立レビューと事実検証の記録（2026-07-26）

> 本ADRの初稿は、GitHub Actions の仕様について**事実誤認に基づく不採用理由**を含んでいた。
> 独立コンテキストによるレビュー（`independent_review.md` に基づく）と、
> 別系統での公式ドキュメント検証を経て全面的に改訂した。経緯を記録として残す。

### B-1. 初稿の誤りと訂正

| 初稿の記述 | 訂正後 |
|---|---|
| cache は「実行間隔（7日）と退避期限（7日）が同値」であり「境界上で綱渡り」 | **誤り。** 退避の起点は last access date であり、原文は "not been accessed in **over** 7 days"（7日を**超えて**）。ちょうど7日で消えるわけではない |
| 上記を選択肢Bの主たる不採用理由としていた | **不採用理由を「失敗時に全損する」に差し替えた。** restore がタイマーを更新するか否かに依存しない形にした |
| 選択肢Aを採用（既定ブランチへコミット） | **選択肢E（状態専用ブランチ）に変更。** ブランチ保護との非互換という失敗モードが初稿では検討されていなかった |

### B-2. レビューで判明した論点

独立レビューが指摘し、本改訂で取り込んだもの:

1. **上位要件との無言の格上げ** — REQ-NF-004 が「重複投入を許容する」としているのに、
   初稿は状態消失を「回復困難な被害」として独断で許容不可に格上げしていた。
   → 「コンテキスト §上位要件との関係」に、許容範囲の線引き（例外時 vs 構造的）を明記
2. **ブランチ保護との非互換** — 初稿は OQ で「規約との折り合い」としてのみ扱い、
   **技術的に push が拒否される**失敗モードを見落としていた。→ 選択肢Aの不採用理由に格上げ
3. **循環参照** — 「同時実行は起きない」の根拠に application_checklist C-F03 を挙げたが、
   C-F03 の根拠は REQ-F-002 であり、その実現方式を決めているのが本ADRだった。
   → トレードオフ表を書き直し、OQ-004 として独立に扱う
4. **選択肢の見落とし** — orphan branch と Artifacts が選択肢として評価されていなかった。
   → 選択肢E（採用）・Fとして追加
5. **cron の高負荷帯** — 月曜 06:00 JST は毎時0分にあたり、ドロップのリスクが高い。→ OQ-005

### B-3. 判定が割れた点（重要）

**restore が cache のタイマーをリセットするか**について、検証結果が割れた。

| 検証者 | 判定 |
|---|---|
| 独立レビュー | リセットする（これを根拠に初稿の論理を否定） |
| 事実検証（別系統） | **公式に明言なし**。文言上そう読めるが保証は文書化されていない |

**後者を採用した。** 公式ドキュメントは restore が `last_accessed_at` を更新するかに
踏み込んでおらず、「リセットされる」と断定することもまた根拠を欠く。
本ADRは restore の挙動に依存しない形で選択肢Bを不採用としたため、この不確実性は結論に影響しない。

なお Actions Cache の REST API は `last_accessed_at` フィールドを公開しているため、
実運用で経験的に確認することは可能である（本システムでは不要）。

### B-4. 二次情報と一次情報の区別

初稿の検討過程で「scheduled workflow の60日自動停止は private リポジトリでも発生する」という
情報を用いたが、これは**コミュニティ報告（二次情報）**であった。
公式ドキュメントは "In a **public** repository" と明記しており、private での発生は
一次情報では確認できていない。本ADRでは公式の記述に従い、public 限定として扱う
（本システムは private 前提のため、いずれにせよ該当しない）。

## ADRを supersede（置き換え）する手順

> 既存のADRの決定内容が古くなり、新しいADRで置き換える場合の手順:

1. **新しいADRを作成する**
   - 新しい ADR-xxx を作成し、`status: proposed` で開始

2. **古いADRを更新する**

     ```yaml
     status: superseded
     superseded_by: ADR-xxx  # 新しいADRのIDを記載
     ```
   - 更新履歴に「ADR-xxx により supersede された」と記録

3. **README.md のリンクを更新する**
   - 関連するドキュメント (REQ / F / SPEC) の参照を新しいADRに変更
