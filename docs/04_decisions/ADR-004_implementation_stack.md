## コンテキスト

プロジェクトの `CLAUDE.md` は「**実装を始める段階になったら、まず言語・パッケージマネージャ・
テストランナーの選定を ADR として記録し、確定後にこの節へ実コマンドを追記すること。
推測でコマンドを実行しない**」と定めている。現時点でリポジトリには実装コードも
ツールチェーンも存在せず、この ADR がその選定を担う。

要件定義 §1 は実行言語を「Python（パッケージ管理・実行は `uv` に統一する。→ ADR-001 で記録予定）」と
記載しているが、**ADR-001 は LLM 呼び出し方式の決定であり、スタック選定は含んでいない**。
つまり要件定義の当該記述は宛先のない参照になっており、本 ADR がその受け皿となる。

加えて、TASK-016（静的解析の CI 組み込み方針）が「実装スタック確定後に決める」として
`open` のまま残っており、本 ADR の決定に従属している。

### 判断材料となる既存資産

同一開発者が運用する **`code-review-toolkits` リポジトリ（`diff-review` ツール）** が、
本プロジェクトと以下を共有している。

| 共通点 | 内容 |
|---|---|
| ドキュメント体系 | `docs/` の5層構造（R / REQ / F / SPEC / ADR）、`SKILL.md`、`granularity_guide.md` が同一 |
| アプリケーション種別 | 無人・非対話で動作するローカル CLI ツール |
| LLM 出力の扱い | 構造化された JSON をパースし、スキーマ検証を通す |
| 実行環境 | ローカルと GitHub Actions の両方で同一コマンドを実行 |
| 開発体制 | 単一開発者。レビュアーが実装者と同一である前提 |

2026-07-26 時点の `diff-review` の構成（`pyproject.toml` で確認）:

```
requires-python = ">=3.10"
dependencies     = pyyaml, jsonschema
dev              = pytest, pytest-cov, ruff, mypy, types-*, import-linter
ruff             = target py310, line-length 100,
                   select [E,F,W,I,UP,B,C4,SIM], ignore [E501]
mypy             = strict = true, warn_unused_ignores = true
coverage         = fail_under = 80, branch = true
build-backend    = setuptools.build_meta（uv は実行・依存解決に使用）
import-linter    = 契約2本
                   (1) cli → pipeline → implementation → utilization → contract（5層）
                   (2) implementation 内部の domain → adapters（副作用の隔離）
CI               = Python 3.10 / 3.12 の2バージョン
```

> **注記:** `ignore = ["E501"]` により**行長は lint で強制されない**（`line-length 100` は
> formatter の指針にとどまる）。TASK-054 で設定を写経する際に誤読しないこと。

**設計原則4つ**も明文化されている:

1. **Safe by default** — ソースを変更しない。読み取りとレポート生成のみ
2. **LLM 出力は untrusted input** — パース→スキーマ検証→フィルタ→描画の全段を通す
3. **決定論的部分と確率的部分の分離** — Claude 呼び出しのみ確率的
4. **subprocess は常にリスト引数** — `shell=True` 全面禁止

このうち **(2) と (3) が本プロジェクトの中核構造に直接対応する**。rain-drop-feed は
「フィード取得（決定論的）→ LLM 評価（確率的）→ 閾値判定・投入（決定論的）」という
構造を持ち、F-001 AC-029（範囲外スコアが投入判定に使われないこと）と REQ-F-010
（評価失敗時の処理継続）は、いずれも**確率的部分を隔離し、その出力を決定論的層が検証する**
という原則の帰結である。原則 (3) と import-linter の契約(2)（`domain → adapters`）は
対になる構造であり、**TASK-055（層構造設計）の出発点となる**。

(4) は `enterprise_checklist` S-I04 / `application_checklist` C-S01 が挙げる
コマンドインジェクション対策そのものである。

## 決定事項

**実装スタックを個別に選定せず、`diff-review` リポジトリの構成一式をそのまま継承する。**

継承する構成の内訳:

| 項目 | 内容 |
|---|---|
| 言語 | Python 3.10 以上 |
| パッケージ管理・実行 | `uv`（`uv run` 経由に統一） |
| テスト | `pytest` + `pytest-cov`（`fail_under = 80`、branch coverage） |
| lint | `ruff`（`select [E,F,W,I,UP,B,C4,SIM]`、`ignore [E501]`） |
| 型チェック | `mypy --strict`（`warn_unused_ignores = true`） |
| 依存方向 | `import-linter`（契約の具体は本システム向けに設計する → OQ-001） |
| CI | Python 3.10 / 3.12 のマトリクス |

本システム固有の実行時依存（`diff-review` に継承元がないもの）:

| 用途 | パッケージ | 根拠 |
|---|---|---|
| HTTP 取得 | `httpx` | feedparser の URL モード（未修正の SSRF・メモリ枯渇 issue あり）を使わず、タイムアウトとレスポンスサイズ上限を自前で制御する → 補遺B |
| フィードのパース | `feedparser` | RSS 0.9x〜2.0 / Atom 0.3〜1.0 / CDF と多様な日付形式を吸収する。XXE 対策を自前で持つ（`feature_external_ges=0`） |
| LLM 呼び出し | `anthropic`（公式 SDK） | → [ADR-001](ADR-001_llm_invocation_method.md)。バージョン固定方針は OQ-003 |
| 設定ファイル | `pyyaml` | `feeds.yaml` の読み込み。`diff-review` から継承 |

> **粒度についての注記（Rule ADR-1 / ADR-4）:** 決定事項には6項目が並記されるため、
> Rule ADR-1 の早見表「複数の対象物が並記されている → 分割する」に形式上抵触する。
> また本文は目安の150行を超える（Rule ADR-4）。**それでも分割しない**と判断した根拠は
> Rule ADR-2 にある — 評価軸（学習・判断コスト / 品質ゲートの強度 / 2リポジトリ間の一貫性 /
> 要件との適合 / 撤退可能性）が3つの選択肢すべてに一様に適用でき、「一部の選択肢にしか
> 適用できない軸」が存在しない。実質的な決定は「**構成を個別選定せず既存リポジトリから
> 一括継承する**」という1つであり、上表は分割すべき別の決定ではなくその内訳である。

## 選択肢の比較

### 評価軸

| 評価軸 | 重み | 定義 |
|---|---|---|
| 学習・判断コスト | 高 | 単一開発者が新たに習得・決定すべき事項の少なさ |
| 品質ゲートの強度 | 高 | 型・lint・依存方向の逸脱を機械的に検出できるか（REQ-NF-008「実装品質のゲート」に対応） |
| 2リポジトリ間の一貫性 | 中 | 同一開発者が行き来する際に作法が揃っているか |
| 要件との適合 | 中 | CLI・無人実行・JSON 処理という本システムの性質に合うか |
| 撤退可能性 | 低 | 選定が誤りだった場合に乗り換えられるか |

---

### 選択肢 A: diff-review と同一構成に揃える ★採用

Python 3.10+ / `uv` / `pytest` + `pytest-cov` / `ruff` / `mypy --strict` / `import-linter`。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 学習・判断コスト | ◎ | **実績のある構成をそのまま持ち込むため、新規に決めることがほぼない。** 設定ファイルも流用できる |
| 品質ゲートの強度 | ◎ | mypy strict + ruff + import-linter + カバレッジ80%。単一開発者でレビュアーが同一であるという弱点を、機械的なゲートで補える |
| 2リポジトリ間の一貫性 | ◎ | 同一開発者が両方を行き来する。`uv run pytest` / `uv run ruff check` / `uv run mypy` が同じコマンドで通る |
| 要件との適合 | ○ | 同じアプリケーション種別（無人 CLI）・同じ LLM 出力の扱いで実証済み。**ただし HTTP 取得とフィードのパースは `diff-review` に存在しない依存カテゴリであり、この2つは継承元がない**（→ 補遺B で個別に選定） |
| 撤退可能性 | ○ | いずれも標準的なツールであり、個別に差し替えられる。ロックインがない |

> **「学習・判断コスト ◎」の留保:** `import-linter` だけは例外で、契約の中身は本システム向けに
> 新規設計が必要である（TASK-055）。他の項目が設定の写経で済むのに対し、これは
> 「継承できる資産」ではなく「新たに設計する対象」にあたる。下記の副案 A' を参照。

**副案 A': 同一構成から `import-linter` のみ外す**

上記の留保を踏まえ、`import-linter` を除いた構成も検討した。**採用しない。**

理由は、本システムが ADR-001 と ADR-005 の決定により**確率的な外部入力を扱う層と
決定論的な判定層が明確に分かれる**構造を持つためである。`diff-review` の設計原則 (3)
（決定論的/確率的の分離）と契約(2)（`domain → adapters`）は、まさにこの構造を
機械的に守るための仕組みであり、本システムでこそ効く。F-001 AC-029（範囲外スコアを
投入判定に使わない）は、層の境界が崩れれば容易に破られる種類の要件である。

層構造の設計コスト（TASK-055）は認めるが、それは**後から入れるほうが高くつく**性質のもので
あり、mypy strict と同じ理由で最初に入れる。ただし TASK-055 の設計時に本システムへの
適用が無理だと判明した場合は、契約を作り直すか外すことを再検討条件に含める。

**採用する理由:**

**単一開発者プロジェクトにおける最大のリスクは、実装者とレビュアーが同一であることによる
見落とし**であり、これはグローバル `CLAUDE.md` が Writer/Reviewer パターンや subagent による
独立検証を求めている理由でもある。人間側の独立性を確保しにくい以上、**機械的に強制できる
品質ゲートを最初から入れておく価値が高い**。mypy strict と import-linter はまさにその役割を果たす。

`diff-review` は本プロジェクトと同じドキュメント体系・同じアプリケーション種別・同じ
LLM 出力の扱いを持ち、その制約下で既に運用されている。**ゼロベースで選定し直す合理性がない。**

要件定義 §1 が既に「Python / `uv`」と記載しており、グローバル `CLAUDE.md` も
「Python: `uv` を使う」と定めているため、この2点は既定路線である。本 ADR の実質的な追加は
**テストランナー・lint・型チェック・依存方向チェックの選定**にある。

### 選択肢 B: 最小構成（Python + uv + pytest のみ）

lint・型チェック・依存方向チェックを導入せず、テストのみで品質を担保する。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 学習・判断コスト | ◎ | 導入するものが最も少ない |
| 品質ゲートの強度 | ✗ | **型エラー・未使用インポート・循環依存が CI をすり抜ける。** 単一開発者の見落としを補う機構がない |
| 2リポジトリ間の一貫性 | △ | `diff-review` と作法が食い違い、行き来のたびに切り替えが要る |
| 要件との適合 | △ | LLM 応答の型を扱う場面が多く（スコア・理由・提案タグ）、型チェックの不在が効いてくる |
| 撤退可能性 | ◎ | 後から追加できる |

**不採用の理由:**

導入コストの低さは魅力だが、**本プロジェクトの品質リスクの所在と噛み合わない**。

F-001 AC-029 が示すとおり、本システムは LLM が返す値の型・範囲を検証する必要がある。
また ADR-005 で JSONL を採用した結果、**一意制約・型制約が DB ではなくアプリケーション側の
責任になった**（ADR-005 の受け入れたトレードオフ）。この状況で型チェックを持たない選択は、
リスクを引き受ける先を増やすだけである。

「後から追加できる」ことは事実だが、mypy strict は**既存コードに後付けすると修正量が膨らむ**
性質のものであり、最初から入れるほうが総コストが低い。

---

### 選択肢 C: 別スタックをゼロベースで選定する

言語・ツールを本プロジェクトの要件から独立に選び直す（例: TypeScript + Node、Go 等）。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 学習・判断コスト | ✗ | 言語選定から始めることになり、決定事項が大幅に増える |
| 品質ゲートの強度 | ○ | 言語によっては同等以上（Go の型システム等） |
| 2リポジトリ間の一貫性 | ✗ | 作法が完全に分かれる |
| 要件との適合 | △ | RSS パース・Anthropic SDK とも Python に成熟した選択肢がある。他言語に優位性がない |
| 撤退可能性 | ✗ | 実装後の乗り換えコストが最も高い |

**不採用の理由:**

要件定義 §1 とグローバル `CLAUDE.md` が既に Python / `uv` を前提としており、
**これを覆すだけの理由が本プロジェクトの要件から出てこない**。

RSS/Atom パース（`feedparser`）、Anthropic SDK、YAML 処理のいずれも Python で成熟しており、
他言語を選ぶ動機が性能・エコシステムのどちらからも生じない。REQ-NF-002 は
「スケールしない（単一プロセス・逐次処理）」と明記しており、実行性能が選定要因にならない。

## 受け入れたトレードオフ

| あきらめること | その影響 | 緩和策 |
|---|---|---|
| mypy strict による記述量の増加 | 型注釈を全関数に付ける必要があり、初期の実装速度が落ちる | 本システムの規模は小さい（CLI 1本）。外部入力（フィード・LLM 応答）の型を明示することは、そもそも AC-029 等が要求している |
| import-linter のための層構造の設計 | ディレクトリ構成を最初に決める必要があり、後からの変更コストが上がる。**この1点だけは「継承できる資産」ではなく新規の設計作業**である（→ TASK-055） | `diff-review` の契約2本（5層 + `domain → adapters`）を出発点にできる。特に契約(2) は設計原則 (3)（決定論的/確率的の分離）と対になり、本システムの構造に直接対応する |
| カバレッジ 80% の維持 | テストを書かずに機能を追加できなくなる | グローバル `CLAUDE.md` が Canon TDD をデフォルトとしており、そもそもテストを先に書く前提。閾値は矛盾しない |
| Python 3.10 を下限とすること | それ以前の環境では動かない | GitHub Actions・ローカルとも 3.10 以上が容易に用意でき、実害がない |
| ツール構成が `diff-review` の変更に引きずられうる | 向こうが構成を変えたとき、揃えるか分岐するかの判断が生じる | 揃えることは目的ではなく手段である。乖離しても実害がなければ追随しない（再検討条件に明記） |

## 再検討条件

- **`diff-review` 側が構成を変更した場合** — 追随するか分岐するかを判断する。
  揃えること自体は目的ではないため、乖離しても実害がなければ追随しない
- **mypy strict が実装の足枷として実際に現れた場合** — 外部ライブラリの型スタブ不足等で
  `type: ignore` が多発するようなら、strict の範囲をモジュール単位で緩める
- **層構造が本システムに合わないと判明した場合** — `diff-review` の層構成は
  レビューツール向けの構成であり、本システム（取得→評価→投入のパイプライン）とは
  性質が異なる。TASK-055 の設計時に無理があれば契約を作り直す
- **カバレッジ 80% が実態に合わない場合** — 外部 API 呼び出しの比率が高く到達しにくいなら、
  閾値の引き下げではなくテストダブルの整備で対応する。それでも困難なら閾値を見直す
- **実行環境の制約が変わった場合** — GitHub Actions 以外での実行が要件になったら、
  Python バージョンの下限を再評価する

## 補遺B: フィード取得方式の調査（2026-07-26）

> OQ-002 の決着にあたり、一次情報（PyPI・GitHub issue・ソースコード）で調査した記録。
> **調査の結果、本 ADR の初稿に書いた方針（`defusedxml` 系を経由する）は誤りと判明した。**

### B-1. 調査で判明した事実

| 事項 | 確認結果 | 出典 |
|---|---|---|
| `defusedxml` の保守状況 | **2021-03-08 の 0.7.1 が最終リリース**。0.8.0 は rc 止まりで4年以上更新がない | PyPI |
| feedparser の XXE 対策 | **自前で対策済み**。`saxparser.setFeature(xml.sax.handler.feature_external_ges, 0)` により外部エンティティ参照を無効化している | `feedparser/api.py:312` |
| feedparser の最新版 | 6.0.12（2025-09-10）。依存は `sgmllib3k` のみ | PyPI |
| feedparser の未修正 issue（1） | **SSRF（severity: high）** — `feedparser.http.get()` が `parse()` の URL モードで、ホスト/IP の許可リストも私設ネットワークのブロックもなく取得する。既定でリダイレクトも追従する | GitHub issue（2026-04-02 報告、未クローズ） |
| feedparser の未修正 issue（2） | **メモリ枯渇** — レスポンスボディを無制限に読み込む | GitHub issue（2026-04-02 報告、未クローズ） |
| feedparser の未修正 issue（3） | **ReDoS** — `mixin.py` の email 正規表現（6.0.11 以下） | GitHub issue（2026-04-19 報告） |

### B-2. 本システムにおけるリスク評価

| リスク | 本システムへの該当 | 判断 |
|---|---|---|
| XXE・billion laughs | **低** | feedparser が外部エンティティを無効化済み。`defusedxml` を重ねても、feedparser 内部のパーサを差し替えるのは容易でなく実効性が薄い |
| SSRF | **該当しない** | フィード URL は `feeds.yaml` で運用者が定義する固定値であり、外部入力ではない。issue が想定する「ユーザー提供 URL を `parse()` に渡すサービス」に当たらない |
| メモリ枯渇 | **該当する** | 取得先のフィードは第三者が管理しており、悪意なく巨大なレスポンスを返しうる。REQ-NF-002a の実測でも全文配信フィードが2件（8,800字・9,238字）確認されている |
| ReDoS | **該当する** | 同上。壊れたフィードによる意図しない停止が起こりうる |

**本当のリスクは XML パースではなく、HTTP 取得層（レスポンスサイズ）とパース時間にあった。**
初稿の方針は、確認せずに「XML = XXE」と短絡したものであり、リスクの所在を取り違えていた。

### B-3. 決定

**HTTP 取得は `httpx` で自前に行い、取得したバイト列を `feedparser.parse()` に渡す。**
`feedparser.parse(url)` の URL モードは使わない。

この構成により:
- SSRF issue の経路（`feedparser.http.get()`）を通らない
- レスポンスサイズの上限を自前で設定でき、メモリ枯渇を防げる
- REQ-NF-001 の「フィード取得のタイムアウト 1情報源あたり30秒」を直接実装できる
- XXE 対策は feedparser の自前実装に依拠し、**未保守の依存（`defusedxml`）を増やさない**

ReDoS については feedparser を最新（6.0.12 以上）に保つことで対応し、
あわせてレスポンスサイズの上限が実質的な緩和として働く。

### B-4. 残るリスクと後続アクション

feedparser の未修正 issue は本 ADR の決定後も上流に残る。依存の脆弱性を継続的に検知する
仕組み（S-SC01 / TASK-015）の要否判断は、この事実を踏まえて行う。
レスポンスサイズの具体的な上限値は TASK-062 で決定する。

## 補遺A: 独立レビューの記録（2026-07-26）

> 本 ADR の初稿は、参照元リポジトリ（`code-review-toolkits`）の構成について
> **3件の事実誤認**を含んでいた。独立コンテキストによるレビューが実リポジトリを
> `gh` で読み、突き合わせた結果として検出された。

### A-1. 初稿の誤りと訂正

| 初稿の記述 | 訂正後 |
|---|---|
| 「**設計原則3つ**」として Safe by default / untrusted input / subprocess リスト引数を挙げていた | **誤り。実際は4つ**で、「**決定論的部分と確率的部分の分離（Claude 呼び出しのみ確率的）**」を落としていた。この原則は本プロジェクトの構造（取得=決定論的 → 評価=確率的 → 判定・投入=決定論的）そのものであり、**落とした原則が最も転用価値の高いものだった**。F-001 AC-029・REQ-F-010 の位置づけ、および TASK-055 の設計指針に直結する |
| `import-linter` の構成を「**4層**（cli/pipeline → implementation → utilization → contract）」と記述（本文4箇所） | **誤り。契約は2本**ある。(1) `cli → pipeline → implementation → utilization → contract` の**5層**（`cli` と `pipeline` は別レイヤとして順序が強制される）、(2) `implementation` 内部の `domain → adapters`。特に契約(2) は設計原則 (3) と対になる構造であり、記述の欠落が TASK-055 の出発点を誤らせるところだった |
| ruff の設定を `select [E,F,W,I,UP,B,C4,SIM]` のみ引用し、`line-length 100` と併記 | **不完全。** 実際は `ignore = ["E501"]` があり、**行長は lint で強制されない**。TASK-054 で設定を写経する際に誤読を招く |
| 決定事項に6項目を並記し、完了チェックリストの「決定事項が一文で書ける」に根拠なく `[x]` | Rule ADR-1 に形式上抵触、Rule ADR-4（150行）も超過していた。決定事項を「構成一式をそのまま継承する」の一文に改め、内訳を表に分離。分割しない根拠（Rule ADR-2: 評価軸が全選択肢に一様に適用できる）を明記した |
| 選択肢が3案（同一構成 / 最小構成 / 別スタック）のみ | 中間案が欠けていた。副案 A'（`import-linter` のみ外す）を追加。`import-linter` だけは「継承できる資産」ではなく新規設計を要する点を、選択肢Aの評価表にも留保として明記した |
| 「同一構成に揃える」と述べつつ、XML パースへの言及なし | `diff-review` の依存は `pyyaml` / `jsonschema` のみで、**XML パースという依存カテゴリが存在しない**。継承の射程が主張より狭かった。OQ-002 に方針（`defusedxml` 系を経由）を追記し、S-SC01（TASK-015）との依存関係を後続アクションに追加した |
| 評価軸「品質ゲートの強度」に対応する上位要件が存在しなかった | REQ-NF-008 に「実装品質のゲート」を1項目追加し、本 ADR の受け皿とした |

### A-2. 事実確認が取れた項目

Python バージョン（`>=3.10`）、依存一覧、mypy strict / coverage の設定値、
CI の Python マトリクスと実行順、共通点テーブル（ドキュメント体系・アプリ種別・
LLM 出力の扱い・実行環境・開発体制）は、いずれも実リポジトリと**一致**していた。

### A-3. 検出手段についての記録

これらの誤認は、レビュアーに `gh` で実リポジトリを読ませ、ADR の記述と
突き合わせるよう指示したことで検出された。**外部リポジトリの構成を引用する ADR では、
一次情報との突き合わせをレビュー手順に含める必要がある。** ADR-002 補遺B・
ADR-005 補遺A に続き、外部仕様の未確認に起因する誤りが3件連続している。

## ADRを supersede（置き換え）する手順

> 既存のADRの決定内容が古くなり、新しいADRで置き換える場合の手順:

1. **新しいADRを作成する**
   - 新しい ADR-xxx を作成し、`status: proposed` で開始
   - レビュー・合意を経て `status: accepted` にする

2. **古いADRを更新する**
   - 古いADRのフロントマターを以下のように更新:
     ```yaml
     status: superseded
     superseded_by: ADR-xxx  # 新しいADRのIDを記載
     ```
   - 更新履歴に「ADR-xxx により supersede された」と記録

3. **README.md のリンクを更新する**
   - 関連するドキュメント (REQ / F / SPEC) の参照を新しいADRに変更
