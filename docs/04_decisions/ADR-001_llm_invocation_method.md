## コンテキスト

REQ-F-003 は「各エントリのタイトルと要約をトリアージ基準に照らして評価し、0〜10 のスコアを得る」
ことを求めている。`docs/.ref/spec.md` はその実現手段として `claude -p`（Claude Code CLI）を
指定していたが、これは要件ではなく実装方式の指定であり、本ADRで妥当性を判断する。

**この決定が必要になった直接の契機は、2026-07-26 に実施した疎通確認である。**
`claude -p --output-format json` は非対話で正常終了し、安定した JSON を返した。判定精度も
良好（告知記事に1点、設計解説記事に8点。閾値5を挟んで明確に分離）。
**CLI 方式は機能的に成立する**ことが確認できた。

そのうえで判明したのが、**CLI 経由の呼び出しに付随するトークンオーバーヘッド**である。
既定設定での実測では1回の呼び出しあたり約 18,000 トークンが消費された。これはトリアージの
プロンプト（タイトル＋要約＋基準で数百トークン）ではなく、Claude Code のハーネスが読み込む
システムプロンプト・ツール定義・作業ディレクトリのコンテキストに由来する。
結果として既定モデルで年 $608、軽量モデルに切り替えても年 $127 となり、
要求定義 §7 の予算制約（追加コストを実質ゼロに抑える）に対して余裕がない。

> **オーバーヘッドの性質について（重要な限定）:** 18,000 トークンは**既定設定での自前実測値**
> であり、公式に文書化された数値ではない。またこれは CLI 固有の不可避なコストではなく、
> `--bare`（hooks・skills・plugins・MCP・CLAUDE.md の自動読み込みを skip）と
> `--system-prompt`（既定プロンプトを完全に置換）により削減可能である。
> **削減後の実測値は取得していない。** 本ADRはこの未実測部分を選択肢 B-2 として扱う。

なお本システムは単一利用者の週次バッチであり、対話的な操作・ファイル編集・ツール実行を
必要としない。求めているのは「テキストを渡して JSON を受け取る」という単一の機能である。

### 認証について（初稿の誤りの訂正）

本ADRの初稿は「CLI の認証は対話ログイン由来の OAuth に依存し、無人実行の経路が未確立」と
記述し、これを選択肢 B の**決定的な**不採用理由としていた。**これは事実誤認であった。**

公式ドキュメントは CI での認証手順を明記している。

- GitHub Actions: 「Add `ANTHROPIC_API_KEY` to your repository secrets」が公式手順
  （[出典](https://code.claude.com/docs/en/github-actions)）
- bare モード: 「Bare mode skips OAuth and keychain reads. Anthropic authentication must come
  from `ANTHROPIC_API_KEY` or an `apiKeyHelper`」（[出典](https://code.claude.com/docs/en/headless)）
- 公式の GitHub Action（`anthropics/claude-code-action`）が存在する

つまり **CLI も選択肢 A と同一の `ANTHROPIC_API_KEY` + GitHub Secrets 経路で無人実行できる。**
疎通確認環境に `ANTHROPIC_API_KEY` が設定されていなかったのは環境の状態にすぎず、
CLI の仕様上の制約ではなかった。**環境の観測結果を仕様上の限界と取り違えていた。**

したがって**無人実行の確実性は選択肢間の差にならない**。本ADRの判断は、
コスト・制御性・実装の単純さに基づく。

---

## 決定事項

**トリアージのLLM呼び出しには、Anthropic API（Messages API）を SDK 経由で直接使用する。**

## 選択肢の比較

> **ルール:** 検討した選択肢をすべて記述する。採用・不採用を問わず並べて評価する。

### 評価軸

| 評価軸 | 重み | 定義 |
|---|---|---|
| 運用コスト | 高 | 年間の評価コスト。上限は年 $150（一次根拠: 要求定義 §7 の予算制約「追加コストを実質ゼロに抑える」。REQ-NF-002a はこれを数値化したもの） |
| 制御性 | 高 | モデル・トークン上限・出力形式を明示的に指定できるか。コスト管理と再現性の前提 |
| 実装の単純さ | 中 | 依存関係の少なさ、エラーハンドリングの素直さ |
| 将来の安定性 | 中 | 外部要因（ハーネスの仕様変更等）で壊れにくいか |
| レイテンシ制約への適合 | 中 | REQ-NF-001（1回の実行を30分以内）を満たせるか |

> **「無人実行の確実性」を評価軸から外した理由:** 初稿では最重要軸としていたが、
> 上記「認証について」のとおり、全選択肢が同一の `ANTHROPIC_API_KEY` 経路で
> 無人実行できることが判明したため、選択肢間の差にならない。

### 選択肢 A: Anthropic API を SDK 経由で直接呼び出す ★採用

`anthropic` パッケージを用い、`client.messages.create()` でトリアージを行う。
認証は環境変数 `ANTHROPIC_API_KEY`（Actions では Secrets）。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 運用コスト | ◎ | ハーネスのオーバーヘッドが構造的に存在しない。送るのはプロンプトのみ。Haiku 4.5 で **年 $2.70**（週40件・1件550トークン想定） |
| 制御性 | ◎ | モデル ID・`max_tokens`・`output_config.format` を明示的に指定できる。**モデル ID は必須パラメータ**であり、既定モデルへの暗黙のフォールバックが起こらない（REQ-NF-002a の異常時試算にある「モデル誤指定」の経路を構造的に塞げる） |
| 実装の単純さ | ○ | 依存が1つ増えるが、呼び出しは1関数で完結する。サブプロセス起動・stdout パースが不要 |
| 将来の安定性 | ◎ | 公開APIであり後方互換性が管理されている。ハーネスの内容変更の影響を受けない |
| レイテンシ制約への適合 | ◎ | 同期呼び出しであり、実測で1件2.7〜4.8秒。100件でも5〜8分（REQ-NF-001 の30分以内に収まる） |

**採用する理由:**

**コストと制御性が決定要因である。** 選択肢 B-1（CLI 既定設定）に対しては約47倍、
B-2（`--bare` 適用）に対しても構造的に優位である。トリアージに必要な情報は
タイトル・要約・基準のみ（数百トークン）であり、エージェント実行基盤が読み込む
コンテキストは本システムにとって無用である。

制御性の面では、**モデル ID が必須パラメータである**点が実質的な利点となる。
REQ-NF-002a の異常時試算は「モデル誤指定（Haiku のつもりが Opus 5）で年 $13.52」を
挙げているが、API 直接方式ではモデル指定の省略自体ができないため、この経路は
明示的な設定ミスに限定される。

構造化出力（`output_config.format`）により、**スキーマ違反によるパース失敗そのものが
発生しなくなる**（制約付きデコーディングによる。Claude 4.5 以降で GA、Haiku 4.5 でも使用可能。
[出典](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)）。
ただし後述のとおり REQ-F-010 の必要性は弱まらない。

### 選択肢 B-1: `claude -p` を既定設定でサブプロセスとして呼ぶ

`.ref/spec.md` が当初想定していた方式。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 運用コスト | ✗ | 1回あたり約 18,000 トークンのオーバーヘッド（既定設定での実測）。既定モデルで年 $608、Haiku 指定でも年 $127。上限 $150 に対し余裕がない |
| 制御性 | △ | `--model` 等は指定できるが、ハーネスが読み込むコンテキスト（CLAUDE.md・MCP・hooks 等）を制御できない。消費トークンの内訳が管理下にない |
| 実装の単純さ | △ | サブプロセス起動、stdout の JSON パース、CLI 自体のインストールが必要。`result` フィールド内にさらに JSON 文字列が入る二重構造の展開も要る |
| 将来の安定性 | △ | ハーネスの内容は本システムの管理外で変わりうる。実際、オーバーヘッドの大きさ自体がその一例 |
| レイテンシ制約への適合 | ○ | 実測で1件2.7〜4.8秒。30分以内に収まる |

**不採用の理由:**

**コストが上限に近く、その主因が管理下にない。** 実行環境の `~/.claude` や
プロジェクトの設定ファイルの内容によってトークン消費が変動するため、
コストの予測可能性が低い。公式ドキュメント自身が
「Without it（`--bare`）, `claude -p` loads the same context an interactive session would,
including anything configured in the working directory or `~/.claude`」と述べており、
既定設定での実行は本システムの用途に対して過剰である。

### 選択肢 B-2: `claude -p --bare` でオーバーヘッドを削減して呼ぶ

`--bare` により hooks・skills・plugins・MCP・auto memory・CLAUDE.md の自動読み込みを skip し、
`--system-prompt` で既定プロンプトを置換する方式。公式は「`--bare` is the recommended mode
for scripted and SDK calls」としている（[出典](https://code.claude.com/docs/en/headless)）。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 運用コスト | **未実測** | オーバーヘッドは削減されるが、**削減後の値を測定していない**。API 直接（オーバーヘッドゼロ）を下回ることはない |
| 制御性 | ○ | `--bare` により読み込むコンテキストを制御できる。`--json-schema` でスキーマ準拠の出力も得られる |
| 実装の単純さ | △ | サブプロセス起動と JSON の二重構造展開は残る |
| 将来の安定性 | ○ | `--bare` は「will become the default for `-p` in a future release」と公式が明言しており、方向性は安定 |
| レイテンシ制約への適合 | ◎ | `--bare` は起動時間を短縮する。B-1 以上 |

**不採用の理由:**

**選択肢 A に対する優位性が原理的に存在しない。** `--bare` はハーネスのオーバーヘッドを
削減する手段であり、削減の極限が「オーバーヘッドなし」＝選択肢 A である。
本システムが必要とするのは「テキストを渡して JSON を受け取る」機能のみであり、
`--bare` 後に残る Bash・file read・file edit ツールも使用しない。

加えてサブプロセス起動と出力の二重構造展開という実装上の負担が残る。
**A より複雑で、A より安くはならない。**

> **ただし本選択肢の評価は不完全である。** 削減後のオーバーヘッドを実測していないため、
> 「A に近い水準まで下がる」のか「依然として無視できない差がある」のかは不明である。
> 上記の不採用理由は測定値ではなく論理（削減の上限が A である）に基づく。
> 実測が必要になった場合は再検討条件に従う。

### 選択肢 C: Message Batches API を使う

`client.messages.batches.create()` で全エントリをまとめて非同期処理する。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 運用コスト | ◎ | **通常価格の50%**。Haiku 4.5 で年 $1.35 相当 |
| 制御性 | ◎ | 選択肢 A と同等。モデル ID・スキーマを明示指定できる |
| 実装の単純さ | △ | 投入 → ポーリング → 結果取得の3段階になる。同期呼び出しより状態管理が増える |
| 将来の安定性 | ◎ | 選択肢 A と同等 |
| レイテンシ制約への適合 | ✗ | 「most batches finishing in less than 1 hour」だが、**「Batches expire if processing does not complete within 24 hours」**。REQ-NF-001 の「30分以内」を保証できない |

**不採用の理由:**

**REQ-NF-001（1回の実行を30分以内）を保証できない。** 公式は大半が1時間以内としつつ、
完了保証は24時間である（[出典](https://platform.claude.com/docs/en/build-with-claude/batch-processing)）。
GitHub Actions のジョブでポーリングし続けると実行時間の大半を待機に費やし、
最悪ケースではジョブがタイムアウトする。

コストは魅力的（Aの半額）だが、**年 $2.70 と年 $1.35 の差は月額約11円**であり、
実装の複雑さとレイテンシの不確実性に見合わない。REQ-NF-002a の上限に対して
選択肢 A で既に2桁の余裕がある以上、さらなるコスト削減の価値は小さい。

> **再検討の余地:** 将来エントリ数が桁で増え、コストが問題になった場合は有力な選択肢になる。
> その際は REQ-NF-001 の緩和（「実行完了まで待たず、結果を次回実行で回収する」等）と
> セットで検討する。

### 選択肢 D: ローカルLLM（Ollama 等）を使う

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 運用コスト | ◎ | API 利用料はゼロ |
| 制御性 | ○ | モデル・パラメータを完全に制御できる |
| 実装の単純さ | ✗ | モデルの配布・ロード・実行環境の管理が必要。個人プロジェクトの保守コストとして重い |
| 将来の安定性 | ○ | 外部サービスに依存しない |
| レイテンシ制約への適合 | ✗ | GitHub Actions の標準ランナーでモデルをロードする必要があり、実行時間の制約が厳しい |

**不採用の理由:**

コスト面の利点はあるが、選択肢 A の年 $2.70 という水準に対して、削減額が運用の複雑さに
見合わない。要求定義 §7 は「常時稼働のサーバーを用意せず、既存の CI 基盤上で完結させる」
ことを制約としており、この制約に照らして実行基盤を確保する手段がない。
また判定精度の検証を一からやり直す必要がある。

## 受け入れたトレードオフ

| あきらめること | その影響 | 緩和策 |
|---|---|---|
| `.ref/spec.md` が指定していた `claude -p` を使わない | 当初構想からの逸脱。`.ref/spec.md` は「委任可能」項目に「triage.py 実装」を含めており、実装方式の変更は委任範囲内と解釈する | プロンプトと判定基準は疎通確認の結果をそのまま流用し、検証済みの部分を捨てない |
| API キーという長期有効な認証情報を管理する | **漏洩時の被害が Raindrop トークンと質的に異なる。** Raindrop トークンの漏洩は本人のブックマーク操作に留まるが、API キーの漏洩は**第三者による従量課金の発生＝直接的な金銭被害**であり、要求定義 §7 の予算制約に直結する | リポジトリに含めず GitHub Secrets 経由でのみ供給する（REQ-NF-006）。ログ・サマリへ出力しない。**Console でワークスペースを分離し、当該キーに支出上限を設定する**（enterprise_checklist S-Z04 の具体的手段）→ TASK-036 |
| API キーのローテーション責任が発生する | enterprise_checklist S-S03（シークレットのローテーション方針）は現在 `-`（未検討）であり、その OQ-001 は Raindrop トークンのみを対象としている。**管理対象が1つ増える** | S-S03 / OQ-001 のスコープに API キーを追加する → TASK-037 |
| 従量課金への依存 | エントリ数が急増すると青天井にコストが増えうる | 実行サマリに当該実行の評価コストを出力する（REQ-NF-002a）。週次バッチであり、1回の実行で処理する件数には自然な上限がある |
| モデルの deprecation に追従する保守が発生する | 使用モデルが廃止されると実行が失敗する | モデル ID を設定として外出しし、変更を1箇所で済ませる。廃止は事前告知される |

## 影響・後続アクション

### この決定によって生じる影響

**ポジティブ:**
- 評価コストが年 $2.70 程度に収まり、上限（年 $150）を2桁下回る
- **構造化出力によりスキーマ違反によるパース失敗そのものが発生しなくなる**（ただし REQ-F-010 の必要性は弱まらない。下記参照）
- モデル ID が必須パラメータであるため、既定モデルへの暗黙のフォールバックによる課金増が起こらない
- ハーネスのコンテキストに依存しないため、実行環境（ローカル / Actions）による消費トークンの差が生じない
- ローカル実行と Actions 実行で同一の認証方式を使えるため、環境差が減る

> **REQ-F-010（評価失敗時の処理継続）との関係:** 構造化出力はスキーマ違反を排除するが、
> REQ-F-010 の必要性を**弱めない。両者は独立である。** 構造化出力でも以下は残るためである。
>
> - `max_tokens` 到達による JSON の途中切断
> - `stop_reason: "refusal"` 時にスキーマへ従わない可能性（公式が明示的に注記）
> - ネットワーク障害・API 障害・レート制限（構造化出力と無関係）
> - スキーマは通るが**値が意味的に不正**（score が 0〜10 の範囲外等）→ enterprise_checklist S-I08 が要求する検証は依然必要

**ネガティブ / 受け入れるリスク:**
- `.ref/spec.md` の構成図（`triage.py` が `claude -p` を呼ぶ）と実装が乖離する
- Python の依存パッケージが1つ増える（`anthropic`）
- API キーの管理責任が発生する
- Anthropic API の障害が実行の失敗に直結する（ただし次回実行で自動回復する。REQ-NF-003）

## 再検討条件

> **問い:** どんな状況になったらこの決定を見直すべきか？

- **評価コストが年 $150（REQ-NF-002a の上限）を超えた場合** — 購読フィードの大幅増加や
  モデル価格の改定が要因となりうる。軽量モデルへの変更、プロンプトの短縮、
  または選択肢 C（ローカルLLM）の再評価を行う
- **タイトルと要約のみでの判定精度が実用水準に達しないと判明した場合** — 記事本文の取得
  （現在スコープ外）が必要になり、1件あたりのトークン量が桁で変わる。コスト前提が崩れるため
  本ADRの比較を最初からやり直す
- **選択肢 B-2（`--bare`）のオーバーヘッドを実測する必要が生じた場合** — 本ADRは B-2 を
  「削減の上限が A である」という論理で不採用としており、実測値を持たない。
  CLI 方式を採る動機が別途生じた場合（下記）は、まず実測して比較をやり直す
- **エントリ数が桁で増え、コストが実際に問題になった場合** — 選択肢 C（Batches API、通常価格の50%）が
  有力になる。その際は REQ-NF-001（30分以内）の緩和とセットで検討する
- **モデルの deprecation により使用モデルが廃止される場合** — モデル ID の変更で対応する。
  廃止は事前告知されるため、計画的に対応できる
- **本システムがトリアージ以外の処理（記事の要約生成、対話的な絞り込み等）を担うことに
  なった場合** — エージェント実行基盤の価値が生じるため、CLI 方式の再評価が妥当になる

## 補遺B: 独立レビューと事実検証の記録（2026-07-26）

> 本ADRの初稿は、Claude Code CLI の認証方式について**事実誤認に基づく不採用理由**を
> 含んでいた。独立コンテキストによるレビューと、別系統での公式ドキュメント検証を経て
> 改訂した。経緯を記録として残す。

### B-1. 初稿の誤りと訂正

| 初稿の記述 | 訂正後 |
|---|---|
| 「CLI の認証は対話ログイン由来の OAuth に依存し、無人実行の経路が未確立」→ これを**決定的な**不採用理由としていた | **誤り。** 公式は `ANTHROPIC_API_KEY` + GitHub Secrets を CI の標準手順として文書化しており、`--bare` は OAuth/keychain を skip して同環境変数から認証する。公式 GitHub Action も存在する。**環境の観測結果を仕様上の限界と取り違えていた** |
| 18,000 トークンのオーバーヘッドを CLI 固有の不可避なコストとして扱っていた | **`--bare` / `--system-prompt` で削減可能**。18,000 は既定設定での自前実測値であり、公式に文書化された数値ではない。削減後の値は未実測（選択肢 B-2 として明示） |
| 選択肢が A / B / C（ローカルLLM）の3つ | **Batches API（通常価格の50%）が未評価だった。** 選択肢 C として追加し、REQ-NF-001 との不整合を不採用理由として明記 |
| 「構造化出力によりパース失敗の発生頻度を下げられる」 | **過小記述。** 制約付きデコーディングにより**スキーマ違反によるパース失敗は発生しなくなる**。ただし REQ-F-010 の必要性は弱まらない（両者は独立） |
| 評価軸の「運用コスト」で REQ-NF-002a を外部制約として参照 | **循環参照だった。** REQ-NF-002a 自身が本ADRを根拠にしている。上限 $150 の一次根拠を要求定義 §7（予算制約）に遡らせた |

### B-2. 検証で確認できた事実

| 事項 | 結果 |
|---|---|
| モデル料金（Haiku $1/$5、Sonnet 5 $3/$15・導入 $2/$10、Opus 5 $5/$25 per MTok） | **正しい。** コスト試算12セルを再計算し全一致 |
| Sonnet 5 導入価格の期限 2026-08-31 | **正しい**（公式に明記） |
| 構造化出力のパラメータ名 `output_config.format` | **正しい。** Claude 4.5 以降で GA、**Haiku 4.5 でも使用可能** |
| プロンプトキャッシュによるコスト削減 | **適用不可。** Haiku 4.5 の最小キャッシュ可能プレフィックスは 4,096 トークンであり、本システムの550トークンは対象外。TTL（既定5分・最大1時間）も週次実行では無意味 |
| CLI のトークンオーバーヘッドの存在 | 定性的には**公式に文書化されている**（システムプロンプト・ツール定義・作業ディレクトリのコンテキストを読み込む）。ただし**具体的な数値は公式未文書化** |

### B-3. 結論への影響

**決定事項（API を直接使用する）は維持された。** ただし根拠が入れ替わっている。

- 初稿: 「無人実行できないから CLI は不可」＋「コストが高い」
- 改訂後: 「無人実行は全選択肢で可能」→ **コストと制御性のみで判断**

不採用理由が1つ（しかも「決定的」としていたもの）崩れたにもかかわらず結論が変わらなかったのは、
コスト差（B-1 に対し約47倍）と制御性の優位が独立して成立していたためである。

## ADRを supersede（置き換え）する手順

> 既存のADRの決定内容が古くなり、新しいADRで置き換える場合の手順:

1. **新しいADRを作成する**
   - 新しい ADR-xxx を作成し、`status: proposed` で開始
   - レビュー・合意を経て `status: accepted` にする

2. **古いADRを更新する**
   - 古いADRのフロントマターを以下のように更新:
     ```yaml
     status: superseded
     superseded_by: ADR-xxx  # 新しいADRのIDを記載
     ```
   - 更新履歴に「ADR-xxx により supersede された」と記録

3. **README.md のリンクを更新する**
   - 関連するドキュメント (REQ / F / SPEC) の参照を新しいADRに変更
