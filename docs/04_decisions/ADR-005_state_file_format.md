## コンテキスト

[ADR-002](ADR-002_state_persistence.md) は処理済み状態を**状態専用ブランチへコミットして
永続化する**と決定した。その OQ-001（TASK-030）として、**状態ファイルをどの形式で持つか**が
未決のまま残されている。この形式が決まらないと状態管理の実装に着手できない。

`.ref/spec.md` は `state.sqlite` というファイル名を挙げ、`url` を PRIMARY KEY にすると
記載している。ただし **ADR-002 が指摘するとおり、この指定には根拠の記載がない**。
また `.ref/spec.md` は「state スキーマ詳細」を**委任可能**な項目に分類しており、
「要合意」項目は `profile.md` のトリアージ基準・閾値 5・投入先コレクション構造の3つに限られる。

### 判断の前提となる本システムの性質

| 性質 | 根拠 |
|---|---|
| 書き込みは**物理的には追記のみ**。状態の更新は**追記による論理的上書き**（イベントソーシング）で表現する | REQ-F-007 は記録の保持を求めるのみでスコアの書き換え要件はない。一方 REQ-F-010 / REQ-NF-004 は「失敗回数が上限に達していないエントリを次回実行で再評価する」ことを Must としており、**同一 URL の失敗回数を実行をまたいで増やす**必要がある。これは論理的には既存エントリの更新であり、物理的な追記で表現する |
| 規模が小さい | 実測ベースで年間 2,080行、5年で 10,400行。上振れでも5年 26,000行（ADR-002 の試算） |
| 読み取りは**全件ロードで足りる** | 26,000 行の JSON パースはメモリ・時間とも問題にならない。ただし単純な URL 集合ではなく、**URL をキー・最新レコードを値とする辞書**として再構成する必要がある（→ OQ-001 の結論） |
| **Git 管理下に置かれる** | ADR-002 の決定。マージ可能性が直接効いてくる |
| 単一プロセス・逐次処理 | REQ-NF-002。**同一実行内では**同時書き込みの排他制御を必要としない。プロセスをまたぐ競合は ADR-002 OQ-004 の管轄 |

**Git 管理下に置かれることが本 ADR の判断を支配する。** ただしその効き方は限定的で、
世代管理・復旧可能性（`git checkout <sha> -- <file>`）は形式に依存せず成立する。
形式に依存するのは **push 競合時のマージ**（ADR-002 OQ-004）である。

なお `enterprise_checklist` C-L02 は本記録を「**監査目的ではなく冪等性と基準検証のための記録**」と
位置づけ、C-L04（改ざん防止）を `✗` としている。したがって「履歴が監査証跡になること」は
本システムの要件ではなく、差分の可読性は運用上の利便性として評価する。

## 決定事項

**処理済み状態を、1行1エントリの追記専用 JSONL ファイルとして保持する。**

> **粒度についての注記（Rule ADR-2）:** 本 ADR は [ADR-002](ADR-002_state_persistence.md)（状態を
> どこへ置くか）とは別テーマの決定である。ADR-002 の評価軸（永続性・復旧可能性・運用の単純さ・
> 既定ブランチへの影響）は形式の選択に適用できず、本 ADR の評価軸（マージ可能性・整合性・
> 差分の可読性）は置き場所の選択に適用できない。granularity_guide の早見表
> 「一方の決定がもう一方の決定を前提にしている → 分割し `related` で関連付ける」に該当するため、
> ADR-002 とは分割して `related` で関連付ける。

## 選択肢の比較

### 評価軸

| 評価軸 | 重み | 定義 |
|---|---|---|
| マージ可能性 | 高 | push 競合時（ADR-002 OQ-004）に自動マージまたは手動解決ができるか。**形式選択が唯一構造的に効く軸** |
| データ整合性の担保 | 中 | 一意制約・型制約をどこで担保するか |
| 事後検証のしやすさ | 中 | R-006（閾値の妥当性検証）のための分析が容易か |
| 実装の単純さ | 中 | 追加の依存・スキーマ管理・マイグレーションを要しないか |
| Git 差分の可読性 | 中 | 週ごとの処理内容を人間が履歴から追えるか（運用上の利便性。C-L02 のとおり監査要件ではない） |

> **注記:** 世代管理・復旧可能性（任意の時点へ戻せること）は `git checkout` で形式によらず
> 成立するため、評価軸に含めない。ADR-002 の評価軸表にも「差分の可読性」という軸は存在せず、
> 同 ADR が選択肢E を A より優先した理由はブランチ保護との両立であって形式ではない。

---

### 選択肢 A: JSONL（1行1エントリの JSON） ★採用

| 評価軸 | 評価 | 理由 |
|---|---|---|
| マージ可能性 | ○ | 行単位の追記のみのため、競合しても両方の行を残せば状態として成立する。読み取り規則を `evaluated_at` の最大値とすることで**行順に依存しない**（→ OQ-001 の結論） |
| データ整合性の担保 | △ | 一意制約・型制約を**アプリケーション側で担保する必要がある**。DB が守ってくれない |
| 事後検証のしやすさ | ○ | `jq` で集計できる。ただし同一 URL の複数行を畳み込む前処理が要る |
| 実装の単純さ | ○ | 標準ライブラリのみ。スキーマ定義もマイグレーションも不要。ただし読み取り時の畳み込み処理が必要 |
| Git 差分の可読性 | ◎ | 追記が末尾への行追加として現れる。`git diff` でその週に何が処理されたかが追加設定なしで読める |

**採用する理由:**

**マージ可能性が決め手である。** ADR-002 OQ-004 は push 競合時に `git pull --rebase` して
行マージし再 push すると決定しており、これは行指向のテキスト形式でのみ成立する。
SQLite ではこの決定自体が実行不能になる（→ 選択肢B）。

イベントソーシング的な表現（同一 URL の複数行から最新状態を再構成する）は、
REQ-F-010 の「失敗回数を実行をまたいで増やす」要件を**スキーマ変更なしに**扱える。
規模も小さく（5年で最大 26,000行）、全件ロードによる再構成が現実的に成立する。

データ整合性がアプリ側の責任になる点と、読み取りに畳み込みが要る点は弱点である。
ただし一意性を担保すべき対象は URL 1つだけであり、複雑な参照整合性や結合を必要としない。
差分が追加設定なしで読める点は、C-L02 のとおり要件ではないが運用上の利点として残る。

---

### 選択肢 B: SQLite（`.ref/spec.md` の当初指定）

| 評価軸 | 評価 | 理由 |
|---|---|---|
| マージ可能性 | ✗ | **バイナリのため自動マージも手動解決も不可能。** 競合したらどちらかの実行の記録を捨てるしかない |
| データ整合性の担保 | ◎ | `url TEXT PRIMARY KEY` で一意制約を DB が担保する。型制約も効く。失敗回数の更新も `UPDATE` で自然に書ける |
| 事後検証のしやすさ | ◎ | SQL で任意の集計が書ける。閾値を変えた場合の件数算出が `WHERE` 一つで済む |
| 実装の単純さ | ○ | Python 標準ライブラリに `sqlite3` があり追加依存は不要。ただしスキーマ定義とマイグレーションの管理が発生する |
| Git 差分の可読性 | △ | 素の `git diff` はバイナリとして扱い機能しない。ただし `.gitattributes` に `diff=sqlite3` を設定し `textconv`（`sqlite3 .dump`）を通せば**テキスト差分として表示できる**。設定が前提であり、GitHub の Web UI 上では機能しない |

**不採用の理由:**

**マージ可能性が構造的に欠けている一点による。**

ADR-002 OQ-004（TASK-033）は push 競合時の挙動を「`git pull --rebase` して行マージし
再 push する」と決定している。SQLite ではこのマージが原理的に不可能であり、
**採用すると ADR-002 の確定済みの決定を覆して再決定する必要が生じる**。
その場合に残る選択肢は「実行を失敗させる」か「`concurrency` で直列化する」だが、
前者は投入済み分の記録を失い R-002（重複ゼロ・Must）に反し、後者は運用者の
ローカル実行との競合を防げない。

データ整合性・事後検証の両軸では JSONL に明確に勝り、REQ-F-010 の失敗回数更新も
`UPDATE` で自然に書ける。**これらは SQLite の実質的な優位であり、本 ADR はそれを
承知の上でマージ可能性を優先する。** 整合性の担保がアプリ側の責任になることは、
受け入れたトレードオフとして明記する。

> **初稿からの訂正:** 本 ADR の初稿は「バイナリのため `git diff` が機能せず、
> ADR-002 の採用理由（履歴が監査証跡を兼ねる）が失われる」を不採用の主たる理由としていた。
> これは2点で誤りであった。(1) `textconv` によるテキスト差分表示は SQLite に対する定石であり、
> 「差分が読めない」は無条件には成立しない。(2) ADR-002 の評価軸表に「差分の可読性」という
> 軸は存在せず、同 ADR の「復旧可能性 ◎」の根拠は「任意の時点へ戻せる」であって
> これは SQLite でも `git checkout <sha> -- <file>` で成立する。**ADR-002 が述べていない
> 主張を同 ADR に帰属させていた。** 独立レビュー（TASK-052）の指摘により訂正した。
> 結論（JSONL 採用）は変わらないが、それを支える論拠をマージ可能性1点に整理した。

`.ref/spec.md` が SQLite を指定している点については、同ドキュメントが
「state スキーマ詳細」を委任可能項目としていること、および ADR-002 が
「SQLite 指定には根拠の記載がない」と確認していることから、**本 ADR で変更してよい範囲**と
判断する。ただしこれは `.ref/spec.md` の記述との差異であるため、後続アクションとして
記録する（TASK-049）。

### 選択肢 C: CSV

| 評価軸 | 評価 | 理由 |
|---|---|---|
| マージ可能性 | ○ | 行単位の追記であれば JSONL と同様に扱える |
| データ整合性の担保 | ✗ | 型制約も一意制約もない。すべて文字列として扱われる |
| 事後検証のしやすさ | ○ | 表計算ソフトで直接開ける。ただし型情報が失われるため、数値として集計するには変換が要る |
| 実装の単純さ | △ | **評価理由（`reason`）にカンマ・改行・引用符が含まれるため、エスケープ処理が必須になる。** 提案タグは配列であり、CSV の1セルに平坦化する独自ルールが必要 |
| Git 差分の可読性 | ○ | テキストのため差分は読める。ただし `reason` に改行が含まれると行とレコードが一致しなくなる |

**不採用の理由:**

JSONL と同じ利点（差分・マージ）を持ちながら、**データ構造の表現力で明確に劣る**。

決定的なのは、本システムが記録する値の性質である。`reason` は LLM が生成する自然文であり、
カンマ・改行・引用符を含むことが常態的に起こる。`suggested_tags` は配列である。
CSV でこれらを扱うには、エスケープ規則と配列の平坦化ルールを独自に定める必要があり、
**JSONL なら標準のシリアライズで済むものを、わざわざ壊れやすい形にする**ことになる。

表計算ソフトで開けるという利点は、`jq` や Python で集計できることに対して優位性がない。

### 選択肢 D: SQLite を正とし、コミット時にテキストダンプを併置する

`state.sqlite` を正の状態とし、コミット前に `sqlite3 .dump` の出力を `state.sql` として
併置する。差分の可読性を確保しつつ、整合性は DB に担保させる。

| 評価軸 | 評価 | 理由 |
|---|---|---|
| マージ可能性 | ✗ | **正である `.sqlite` がバイナリである以上、競合時にマージできない。** ダンプは派生物であり、これをマージしても正の側に反映できない |
| データ整合性の担保 | ◎ | 選択肢Bと同じ |
| 事後検証のしやすさ | ◎ | 選択肢Bと同じ |
| 実装の単純さ | △ | **2つの実体を常に同期させる責務が生まれる。** ダンプ生成を忘れた・失敗したコミットが混じると、履歴の一部だけが読めない状態になる |
| Git 差分の可読性 | ○ | ダンプが常に併置されるため、`textconv` の設定なしに差分が読める |

**不採用の理由:**

差分の可読性と整合性を両立するが、**マージ可能性は選択肢Bと同じく ✗ のまま**である。
本 ADR の決め手はマージ可能性であるため、この案は選択肢Bの弱点を解消していない。

加えて、同一の情報を2つの実体で保持する構成は、同期の責務とストレージの二重化を招く。
差分の可読性は `textconv` でも得られる（選択肢B参照）ため、
ファイルを増やしてまで得る利点がない。

## 受け入れたトレードオフ

| あきらめること | その影響 | 緩和策 |
|---|---|---|
| 一意制約を DB が担保しないこと | 実装のバグで同一 URL が意図せず二重に記録されうる | **同一実行内の重複**は、突合時に URL をキー・最新レコードを値とする辞書を構築し、追記前に照合することで防ぐ。この処理を SPEC で明示しテストで担保する（TASK-051）。**プロセスをまたぐ重複（強制終了・push 失敗・同時実行）は本 ADR の緩和対象外**であり、ADR-002 が受け入れた残存リスクに帰属する（SQLite の PRIMARY KEY でも防げない） |
| 型制約がないこと | スコアが文字列として記録される等の不整合が起こりうる | 書き込み時にアプリケーション側で検証する。F-001 AC-029（範囲外スコアの排除）と同じ層で扱う。ADR-004 が採用した mypy strict がこの層の担保を補強する |
| 読み取り時に畳み込みが必要なこと | 単純な行の読み出しでは現在の状態が得られない。同一 URL の複数行から最新を選ぶ処理が常に要る | 読み取り規則を OQ-001 で確定した（`evaluated_at` の最大値が正）。実装は URL をキーとする辞書への畳み込み1回で済む |
| 全件をメモリに読む前提 | データ量が想定を超えると成立しなくなる | 5年で最大 26,000 行という試算に対し十分な余裕がある。再検討条件として観測可能な指標を明記する |
| SQL による集計ができないこと | R-006 の分析を `jq` や Python で書くことになる | 分析の頻度は低く（閾値見直し時のみ）、集計内容も単純（スコア分布・閾値の再適用）。必要なら JSONL から一時的に SQLite へ流し込める |
| `.ref/spec.md` の記述と差異が生じること | 原典を読んだ人が SQLite を前提にする可能性がある。特に AC-5 は「`state.sqlite` に全 score が残っていること」と**受け入れ基準の本文に形式名を含んでいる** | 差異を TASK-049 として登録し、SPEC 層で解消する。`.ref/spec.md` は参照資料であり正典ではない |

## 影響・後続アクション

### この決定によって生じる影響

**ポジティブ:**
- **ADR-002 OQ-004（push 競合時の行マージ）が実行可能になる。** SQLite ではこの決定が成立しない
- 評価失敗の再試行回数（TASK-006 の決定）を**スキーマ変更なしに**追加できる。イベントソーシング的な表現と相性がよい
- 追加の依存・スキーマ管理・マイグレーションが不要になる
- `git log -p` で週ごとの処理内容が追加設定なしに読める（要件ではないが運用上の利点）

**ネガティブ / 受け入れるリスク:**
- 一意制約・型制約の担保がアプリケーション側の責任になる
- **読み取りが単純な行の走査では済まず、URL ごとの畳み込みが常に必要になる**（→ OQ-001 の結論）
- 全件ロードを前提とするため、データ量の増大に対する上限が実質的に存在する
- 同一 URL の行が蓄積するため、行数は処理したエントリ数を上回る（再試行のたびに1行増える）

## 再検討条件

- **状態の畳み込み処理の所要時間が、実行時間全体の 5% を超えた場合** — REQ-NF-001（30分以内）に
  対する余裕が失われ始める。観測可能な指標であり、実行サマリから判断できる
- **状態ファイルが 20,000 行を超えた場合** — 実測ベース（40件/週）で約10年、上振れ（100件/週）で
  約4年に相当する。到達時点で全件ロードの所要時間を実測し、REQ-NF-001 に対する余裕を再確認する。
  インデックス付きの形式（SQLite）への移行、または古いエントリのアーカイブを検討する
- **記事本文の保存を始めた場合** — 現在スコープ外だが、1エントリあたりのサイズが桁で
  増えるため、行指向のテキスト形式が成立しなくなる可能性がある
- **スコア・評価理由の物理的な書き換え、または過去エントリの削除が要件として発生した場合** —
  追記のみで表現できなくなる。JSONL は物理的な更新・削除に向かないため、形式そのものを再評価する
  （失敗回数の増加のような論理的更新は本 ADR の想定内であり、再検討条件に該当しない）
- **複数プロセスからの同時書き込みが発生するようになった場合** — 現在は単一プロセス・逐次処理
  （REQ-NF-002）を前提としている。排他制御が必要になれば DB の採用が合理的になる
- **R-006 の分析要求が複雑化した場合** — 結合や集約を伴う分析が常態化したら、
  JSONL から SQLite へ流し込む中間層を設けるか、形式そのものを見直す

## 補遺A: 独立レビューの記録（2026-07-26）

> 本 ADR の初稿は、**中核前提の誤りと事実誤認に基づく不採用理由**を含んでいた。
> 独立コンテキストによるレビュー（`independent_review.md` に基づく）を経て改訂した。
> ADR-002 の補遺B と同種の記録として残す。

### A-1. 初稿の誤りと訂正

| 初稿の記述 | 訂正後 |
|---|---|
| 「書き込みは追記が主で**更新が稀**」（根拠に REQ-F-007 のみを挙げていた） | **誤り。** REQ-F-010 / REQ-NF-004 が「失敗回数を実行をまたいで増やす」ことを Must としており、これは論理的な更新にあたる。「更新は追記による論理的上書き（イベントソーシング）で表現する」に書き直した。初稿のままでは、再検討条件「更新操作が要件として発生した場合」が**起票時点で既に発火している**状態だった |
| SQLite の「Git 差分の可読性 ✗ — バイナリのため `git diff` が機能しない」 | **誤り。** `.gitattributes` の `diff=sqlite3` + `textconv`（`sqlite3 .dump`）でテキスト差分を表示できる。SQLite に対する定石であり「差分が読めない」は無条件には成立しない。評価を `△` に訂正した |
| 「ADR-002 の採用理由（履歴が監査証跡を兼ねる）が SQLite では失われる」 | **誤り。** ADR-002 の評価軸表に「差分の可読性」という軸は存在せず、「復旧可能性 ◎」の根拠は「任意の時点へ戻せる」であってこれは SQLite でも成立する。**ADR-002 が述べていない主張を同 ADR に帰属させていた。** 不採用理由をマージ可能性1点に整理した |
| 評価軸「Git 差分の可読性」を重み**高**の筆頭に置いていた | `enterprise_checklist` C-L02 が本記録を「監査目的ではなく冪等性と基準検証のための記録」と明記し C-L04（改ざん防止）を `✗` としているため、監査証跡は要件ではない。重みを**中**へ下げ、重み高はマージ可能性のみとした |
| OQ-001（同一 URL の読み取り規則）を `open` のまま残していた | **ADR-002 OQ-004 の「両方の行を残せばよい（順序に意味がない）」と、OQ-001 の候補「最新行が正（順序に意味がある）」が正面から矛盾**していた。`evaluated_at` の最大値を正とする規則で決着させ、両立させた |
| 選択肢が A/B/C の3案のみ | 選択肢D（SQLite + テキストダンプ併置）を追加。マージ可能性が ✗ のままである点を理由に不採用と記録した |
| 再検討条件「10万行を超えた場合」 | 実測ベースで約48年後にあたり**永久に発火しない空文**だった。20,000行（約10年）と、観測可能な指標（畳み込み処理が実行時間の5%超）に置き換えた |
| トレードオフ「全件をメモリ上の集合として保持し照合する」 | 同一プロセス内の重複しか防げず、R-002 の実際の脅威（強制終了・push 失敗・同時実行）をカバーしていなかった。責任範囲を ADR-002 と分離して明記した |

### A-2. 結論に影響しなかった点

不採用理由の中核（マージ可能性の欠如）は訂正後も成立するため、**JSONL 採用という結論は変わらない**。
訂正したのはそれを支える論拠であり、初稿は「差分の可読性」という**要件でない軸**を決め手として
提示していた。

### A-3. 繰り返された失敗パターン

ADR-002 の補遺B は初稿の問題として「事実誤認に基づく不採用理由」「選択肢の見落とし」を
記録している。**本 ADR の初稿は同じ2点を繰り返した**（textconv の未確認、選択肢Dの欠落）。
外部仕様に依拠して選択肢を不採用にする際は、その仕様を一次情報で確認する手順が必要である。

## ADRを supersede（置き換え）する手順

> 既存のADRの決定内容が古くなり、新しいADRで置き換える場合の手順:

1. **新しいADRを作成する**
   - 新しい ADR-xxx を作成し、`status: proposed` で開始
   - レビュー・合意を経て `status: accepted` にする

2. **古いADRを更新する**
   - 古いADRのフロントマターを以下のように更新:
     ```yaml
     status: superseded
     superseded_by: ADR-xxx  # 新しいADRのIDを記載
     ```
   - 更新履歴に「ADR-xxx により supersede された」と記録

3. **README.md のリンクを更新する**
   - 関連するドキュメント (REQ / F / SPEC) の参照を新しいADRに変更
