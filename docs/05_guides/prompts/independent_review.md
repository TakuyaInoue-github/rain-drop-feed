# プロンプト: 独立検証（SPEC / Feature / ADR 共通）

> 対象: `docs/02_features/F-xxx_*.md` / `docs/03_specs/SPEC-xxx_*.md` /
> `docs/04_decisions/ADR-xxx_*.md`
>
> **このプロンプトの前提:** 執筆に使ったセッションと同一のセッション・同一の
> 会話履歴では実行しないこと。新しいセッション・サブエージェント・別レビュアーに、
> 対象ファイルと上位文書（`traces.upstream` が指すファイル）だけを渡して実行する。
> 執筆時の暗黙の前提（「このケースは考慮不要だろう」等）は、同一セッションのまま
> 読み返しても引き継がれてしまうため検出できない。

---

## このプロンプトと通常の「レビュー・抜け漏れチェック」の違い

各ドキュメント種別のプロンプトファイル（`spec.md` / `feature.md` / `adr.md`）にある
「レビュー・抜け漏れチェック」は、完了チェックリストの項目が埋まっているかという
**体裁確認**が中心。一方、このプロンプトが求めるのは **執筆者の暗黙の前提そのものを
疑う検証**であり、チェックリストには機械的に引っかからない種類の問題を狙う。

両者は代替ではなく併用する。通常のレビューを先に行い、体裁上の欠落を解消してから、
このプロンプトで独立検証を行う。

---

## 独立検証

```
docs/SKILL.md を読んでから、
[対象ファイルパス] をレビューしてください。
このセッションはこのドキュメントの執筆には関与していません。

## 渡す情報

対象ドキュメント: [F-xxx / SPEC-xxx / ADR-xxx のファイルパス]
上位文書（traces.upstream が指すファイル）: [ファイルパスを列挙]

## チェック観点

1. 上位文書が意図しているゴールと、対象ドキュメントの記述に齟齬はないか
2. 対象ドキュメント内の複数セクション間で矛盾はないか
   （例: SPECの入出力定義とAPI仕様のフィールド不一致、
   FeatureのACとUXフローの不整合、ADRの評価表と採用理由の不整合）
3. （SPEC-xxx の場合）テスト観点表の「反証可能性」列が実質的な内容を持っているか。
   「〜を確認する」を言い換えただけの記述になっていないか
4. 完了チェックリストには機械的に引っかからないが、このドメイン固有のリスクとして
   存在するケースはないか

## 出力形式

「問題あり / 要確認 / 問題なし」で分類してから、問題がある箇所には
具体的な修正案を示してください。文体・粒度の好みには言及しないでください。
```

---

## 運用への組み込み方

各テンプレートの完了チェックリストには「独立コンテキストによる初稿レビューを
受けている」という項目がある。ドキュメントを `reviewing` から次のステータス
（`approved`）へ上げる前に、このプロンプトを新しいセッション・サブエージェントで
一度は実行し、その結果をもとにチェックリストの当該項目を満たすこと。
