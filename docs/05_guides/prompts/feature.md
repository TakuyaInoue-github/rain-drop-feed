# プロンプト: 機能 (F-xxx)

> 対象ファイル: `docs/02_features/F-xxx_[name].md`

---

## 初稿生成

```
docs/SKILL.md を読んでから、
docs/02_features/ に F-[番号]_[name].md を新規作成してください。

## コンテキスト

機能名: [機能名]
機能ID: F-[番号]
対応する要件ID: REQ-F-[番号]
対象ユーザーロール: [ロール名]

ユーザーのゴール:
[例: 自分が登録したタスクを一覧・検索・編集・削除する]

得られる価値（So that）:
[例: 進捗を常に把握でき、抜け漏れなく業務を遂行できる]

依存する既存機能（あれば）:
- F-xxx: [依存の内容]

補足情報:
[画面イメージ・業務フロー・制約・エラーケースの手がかり等を自由記述]

## 出力指示

- 粒度ルールを適用してゴール単位になっているか確認すること
  問題があれば分割・統合の提案を先に示してから生成すること
- ユーザーストーリーの So that を「〜できる」で終わらせないこと
- 受け入れ基準は [正常系] [エラー系] [境界値] [権限] の4カテゴリを必ず含めること
- UXフローはエラー時の分岐を含めること
- Out of Scope は「対象外にする理由」とセットで書くこと
- 不明点は OQ として記載し、README.md への登録を促すこと
```

---

## 複数機能の一括生成

> 要件定義をもとに F-xxx を一括で洗い出したいとき。

```
docs/SKILL.md を読んでから、
docs/01_requirements/system_requirements.md の機能要件をもとに、
F-xxx の一覧と各機能の初稿を生成してください。

## 出力指示

まず粒度ルールを適用して機能の洗い出しと分割・統合の提案を行い、
合意を得てから各 F-xxx ファイルを生成すること。

生成する機能の優先順位は system_requirements.md の
REQ-F-xxx の優先度（Must → Should → May）の順とすること。
```

---

## レビュー・抜け漏れチェック

```
docs/SKILL.md を読んでから、
docs/02_features/F-[番号]_[name].md をレビューしてください。

以下の観点で確認し、「問題あり / 要確認 / 問題なし」で報告してください:

1. ユーザーストーリーの So that に価値が明確に書かれているか
   （「〜できる」で終わっていないか）
2. 受け入れ基準に [正常系] [エラー系] [境界値] [権限] の
   4カテゴリがすべて含まれているか
3. UXフローにエラー時の分岐が含まれているか
4. Out of Scope が「理由」とセットで記載されているか
5. 粒度が適切か（広すぎ・細かすぎ・UIステップになっていないか）
6. 依存関係が網羅されているか
7. OQ が README.md のタスク一覧に登録されているか

問題がある箇所は具体的な修正案を示すこと。
```

## 粒度チェック（単体）

> 「これは1つのFでいいか？」を判断したいとき。

```
docs/SKILL.md と docs/05_guides/granularity_guide.md を読んでから、
以下の機能の粒度を評価してください。

機能名: [機能名]
概要: [どんな機能か]
対象ユーザー: [ロール]
含まれる操作: [操作1, 操作2, ...]

Rule F-1〜4 を適用して:
1. この機能をそのまま1つの F-xxx にすべきか
2. 分割すべき場合、どう分割するか（分割後の構造案を示すこと）
3. 統合すべき場合、どのFに統合するか
```
