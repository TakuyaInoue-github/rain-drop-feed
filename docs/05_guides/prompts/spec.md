# プロンプト: 仕様 (SPEC-xxx)

> 対象ファイル: `docs/03_specs/SPEC-xxx_[name].md`

---

## 初稿生成

```
docs/SKILL.md を読んでから、
docs/03_specs/ に SPEC-[番号]_[name].md を新規作成してください。

## コンテキスト

仕様名: [仕様名]
仕様ID: SPEC-[番号]
対応する機能ID: F-[番号]
この仕様が定義する振る舞いの概要: [1〜2文で]

入力項目:
| 項目名 | 型 | 必須 | 備考 |
|---|---|---|---|
| [項目名] | [string / number / boolean 等] | Yes/No | [備考] |

状態遷移の有無: あり / なし
（ありの場合）エンティティ名と状態の一覧: [エンティティ: 状態1, 状態2, ...]

外部システム連携の有無: あり / なし
（ありの場合）連携先と概要: [システム名: 何をするか]

補足情報:
[業務ルール・特殊なエラーケース・パフォーマンス要件等を自由記述]

## 出力指示

- 粒度ルールを適用して独立した振る舞い単位になっているか確認すること
  状態機械が混在している場合は分割提案を先に示してから生成すること
- フロー定義表は主系・代替系・例外系を同一テーブルに記述すること
- 条件/トリガー列は可能な範囲で WHEN/IF/WHILE/WHERE のいずれかを先頭に付けること
  （常時成立する前提の場合は付けなくてよい）
- 以下の例外ケースをすべて検討し、該当するものをフロー定義表に含めること:
  □ 未認証アクセス
  □ 権限違反アクセス
  □ 必須項目未入力
  □ 最大値・最小値超過
  □ 空文字・NULL入力
  □ 外部システムの障害・タイムアウト
  □ 同時操作・競合
  □ 対象リソースが存在しない (404)
  □ 対象リソースが削除済み
- 入力定義の「NULL・空文字の扱い」を全項目に記載すること
- 状態遷移がある場合「不可の場合の挙動」列を省略しないこと
- 不明点は OQ として記載し、README.md への登録を促すこと
```

## 機能から仕様への展開

> F-xxx を読んで SPEC-xxx を一括で洗い出したいとき。

```
docs/SKILL.md と docs/05_guides/granularity_guide.md を読んでから、
docs/02_features/F-[番号]_[name].md をもとに、
必要な SPEC-xxx の構成を提案し、各初稿を生成してください。

## 出力指示

まず粒度ルール（Rule S-1〜4）を適用して SPEC の分割構成を提案し、
合意を得てから各 SPEC-xxx ファイルを生成すること。

提案時には以下を示すこと:
- 何個の SPEC-xxx に分割するか
- 各 SPEC が対応する振る舞いの概要
- 複数の F-xxx から共有参照される SPEC があればその旨
```

## レビュー・抜け漏れチェック

```
docs/SKILL.md を読んでから、
docs/03_specs/SPEC-[番号]_[name].md をレビューしてください。

以下の観点で確認し、「問題あり / 要確認 / 問題なし」で報告してください:

1. フロー定義表に主系・代替系・例外系がすべて含まれているか
2. 以下の例外ケースが検討されているか（該当するものが含まれているか）:
   未認証 / 権限違反 / 必須未入力 / 最大値超過 / 空文字NULL /
   外部障害 / タイムアウト / 競合 / リソース不存在
3. 入力定義の「NULL・空文字の扱い」が全項目に記載されているか
4. 例外系のユーザー表示メッセージが具体的か（「エラーを表示する」で終わっていないか）
5. 状態遷移がある場合「不可の場合の挙動」が定義されているか
6. テスト観点に正常系・異常系・境界値・セキュリティが含まれているか
7. テスト観点に反証可能性（どう壊せばレッドになるか）が明記されているか
8. 粒度が適切か（独立した状態機械が混在していないか）
9. OQ が README.md のタスク一覧に登録されているか

問題がある箇所は具体的な修正案を示すこと。
```
