# プロンプト: 実装とのコンプライアンス検証（任意・実装完了後）

> 対象: `docs/03_specs/SPEC-xxx_*.md` / `docs/02_features/F-xxx_*.md` と、
> 対応する実装コード
>
> **このプロンプトの前提:** このリポジトリ自体は実装コードを持たない
> ドキュメントテンプレート集である。実行する際は、利用者自身のリポジトリにある
> 実装コードのパスを対象ドキュメントとあわせて渡すこと。

---

## このプロンプトと独立検証（independent_review.md）の違い

[independent_review.md](independent_review.md) はドキュメントそのものの品質
（上位文書とのゴール齟齬・セクション間矛盾など）を検証するもので、対象は
**文書だけ**。このプロンプトが検証するのは **文書の記述と実装コードが一致しているか**
であり、対象には実装コードを含む。文書の品質と実装の準拠は独立した観点であり、
どちらか一方では代替できない。

---

## コンプライアンス検証

```
docs/SKILL.md を読んでから、
[SPEC-xxx / F-xxx のファイルパス] と、対応する実装コード
[実装コードのパス・ディレクトリ] を照らし合わせてレビューしてください。

## チェック観点

1. SPECのAPI仕様（8節）に記述されたエンドポイント・リクエスト/レスポンス形式が
   実装と一致しているか
2. SPECの入出力定義（4節）に記述された型・必須/任意・NULL/空文字の扱いが
   実装のバリデーションと一致しているか
3. SPECのフロー定義表（3節）に記述された例外系（未認証・権限違反・タイムアウト等）が
   実装で実際にハンドリングされているか
4. SPECの画面仕様（9節）に記述された表示ルールが実装（UIコンポーネント）と
   一致しているか
5. SPECの非機能仕様（7節）に記述された数値要件が実装で満たされているか
   （測定可能なものは実測値を確認する）
6. SPECのテスト観点（10節）に対応する自動テストが実装側に存在するか。
   存在しない場合、どの観点がテストされずに残っているか
7. Feature の受け入れ基準（3節）のうち、正常系・エラー系・境界値・権限の
   各カテゴリが実装で観察可能な振る舞いとして実現されているか

## 出力形式

「問題あり / 要確認 / 問題なし」で分類してください。
「問題あり」の項目には、文書と実装のどちらを直すべきかを明記した上で
具体的な修正案を示してください（文書側の記述が古い場合と、実装が仕様から
逸脱している場合を区別すること）。
```

---

## 運用への組み込み方

このプロンプトは、SPEC/Feature が `approved` になり、かつ対応する実装が完了した
**後** に実行する。ドキュメントのステータス（`draft`/`reviewing`/`approved`/
`deprecated`）はドキュメントの合意状態を表す軸であり、実装の進捗とは独立している
ため、このプロンプトの実行有無によってドキュメントのステータスは変えない。

検証の結果、文書と実装の不一致が見つかった場合は、README.md のタスク一覧に
`IMPL`（実装タスク）として登録し、どちらを直すか（文書の追従漏れか、実装の
仕様逸脱か）を備考欄に明記すること。
