> 具体例とともに定義する。迷ったときはまずこのドキュメントを参照すること。

## 1. F-xxx の粒度ルール

### 定義

> **1つのFとは、「1人のユーザーが1つのゴールを達成するための機能」である。**

テスト: 以下の文が自然に1文で書けるなら、それは1つのF。

```
As a [ロール],
I want [ゴール],
So that [価値].
```

---

### Rule F-1: ユーザーストーリーが1文に収まらないなら分割する

**Bad: 広すぎる（複数のゴールが混在している）**

```
F-001「ユーザー管理」
  As a 管理者,
  I want ユーザーの招待・権限変更・削除・一覧表示をしたい
         ↑ ゴールが4つある
```

**Good: ゴール単位に分割する**

```
F-001「ユーザーを招待する」
F-002「ユーザーの権限を変更する」
F-003「ユーザーを削除する」
F-004「ユーザー一覧を確認する」
```

---

### Rule F-2: ユーザーストーリーの「So that」が異なるなら分割する

**Bad: So that が違う2つのゴールを1Fにまとめている**

```
F-001「ログイン」
  As a ユーザー,
  I want パスワードまたはGoogleアカウントでログインしたい
  So that サービスを利用できる
```

一見1文に収まるが、「パスワード認証」と「ソーシャル認証」は
実現手段が異なり、それぞれ独立してリリース・テスト・廃止できる。

**Good: 認証手段ごとに分割する**

```
F-001「パスワードでログインする」
  So that サービスを利用できる

F-002「Googleアカウントでログインする」
  So that アカウント作成なしにサービスを利用できる
```

---

### Rule F-3: アクターが異なるなら分割する

**Bad: 異なるアクターの操作を1Fにまとめている**

```
F-001「申請と承認」
  ユーザーが申請し、管理者が承認する
  ↑ アクターが2人いる
```

**Good: アクター単位に分割する**

```
F-001「申請する」（アクター: 一般ユーザー）
F-002「申請を承認・却下する」（アクター: 管理者）
```

---

### Rule F-4: 独立してリリースできないなら統合を検討する

**Bad: 分割しすぎ（UIの1ステップを1Fにしている）**

```
F-001「メールアドレスを入力する」
F-002「パスワードを入力する」
F-003「ログインボタンを押す」
↑ ユーザーのゴールではなく、UI操作の分解になっている
```

これらは「ログインする」という1つのゴールの内部ステップであり、
個別にリリースしてもユーザーに価値を届けられない。

**Good: ユーザーゴールの単位にまとめる**

```
F-001「パスワードでログインする」
  ← メールアドレス入力・パスワード入力・送信はこのFの内部フロー
  ← 詳細はSPEC-001で定義する
```

---

### F-xxx 分割・統合トリガー早見表

| 状況 | 判断 |
|---|---|
| ユーザーストーリーの So that が異なる | **分割する** |
| アクターが異なる | **分割する** |
| 片方だけリリースしてもユーザーに価値がある | **分割を検討する** |
| UIの1ステップ・1フォームにすぎない | **統合する** |
| 1文のユーザーストーリーに自然に収まる | **統合を維持する** |
| 2つのFの受け入れ基準が完全に重複している | **統合する** |

## 2. SPEC-xxx の粒度ルール

### 定義

> **1つのSPECとは、「独立したフロー定義表を必要とする振る舞いの単位」である。**

テスト: 「このSPECだけを見れば、この振る舞いを完全に実装・テストできる」なら1つのSPEC。

---

### Rule S-1: フロー定義表が15行を超えたら分割を検討する

フロー定義表が肥大化するのは、**独立した状態機械が混在しているサイン**。

**Bad: 1つのSPECに複数の振る舞いが混在している**

```
SPEC-001「ログイン」
  フロー定義表（主系2行 + 認証エラー3行 + アカウントロック4行
              + ロック解除3行 + セッション管理4行 = 16行）
  ↑ 「ロック」と「セッション管理」はそれぞれ独立した状態を持つ
```

**Good: 独立した状態機械ごとに分割する**

```
SPEC-001「パスワード認証フロー」    ← 認証の成否を扱う
SPEC-002「アカウントロック管理」    ← ロック状態の遷移を扱う
SPEC-003「セッション発行・管理」    ← セッションのライフサイクルを扱う
```

---

### Rule S-2: 状態遷移が独立しているなら分割する

**独立した状態機械の見分け方:**
- 別のエンティティ（テーブル）に状態を持つ
- 別のアクターがトリガーする
- 別のタイミング・スケジュールで動作する

**例: ログインとアカウントロックは独立した状態機械**

```
ログインフロー:
  [入力待ち] → [認証中] → 成功 or 失敗

アカウントロック（別の状態機械）:
  [通常] → [警告 (3回失敗)] → [ロック (5回失敗)] → [解除]
           ↑ 失敗カウントという独自の状態を持つ
```

→ SPEC-001「認証フロー」と SPEC-002「アカウントロック」に分割する

---

### Rule S-3: 独立してテストできないなら統合する

**Bad: 分割しすぎ（2〜3行のフローを1SPECにしている）**

```
SPEC-001「ログインボタンの活性・非活性制御」
  フロー: 入力あり→活性、入力なし→非活性  ← 2行
  ↑ これ単体でテスト・実装するのに1ファイルは重すぎる
```

これは「パスワード認証フロー」のバリデーション仕様の一部として
SPEC-001 に含めるべき内容。

---

### Rule S-4: 1つのFに対してSPECを機械的に1:1にしない

**Bad: F-SPECを1:1で対応させている**

```
F-001「ログイン」→ SPEC-001「ログイン仕様」（全部入り・肥大化）
```

**Good: 1つのFが複数のSPECを持つことが自然**

```
F-001「ログイン」→ SPEC-001「パスワード認証フロー」
                → SPEC-002「アカウントロック管理」
                → SPEC-003「セッション発行・管理」
```

逆に、**複数のFが1つのSPECを参照することもある**

```
F-001「ログイン」      ─┐
F-002「パスワードリセット」─┤→ SPEC-003「セッション発行・管理」
F-003「ソーシャルログイン」─┘   （認証後のセッション処理は共通）
```

---

### SPEC-xxx 分割・統合トリガー早見表

| 状況 | 判断 |
|---|---|
| フロー定義表が15行を超えている | **分割を検討する** |
| エンティティの状態機械が独立している | **分割する** |
| アクターが異なる操作を含む | **分割を検討する** |
| このSPECだけで完全に実装・テストできる | **分割を維持する** |
| 分割後のSPECが3行以下になる | **統合する** |
| 複数のFで同じ振る舞いを使う | **1SPECにまとめ、複数Fから参照する** |

## 3. ADR-xxx の粒度ルール

### 定義

> **1つのADRとは、「1つの意思決定」である。**

テスト: 「決定事項」セクションが一文で明確に述べられているなら、それは1つのADR。
ADRテンプレートの「決定事項は一文で明確に述べる」という制約自体が、この粒度テストを兼ねる。

---

### Rule ADR-1: 決定事項が一文で書けないなら分割する

**Bad: 複数の決定が1つのADRに混在している**

```
ADR-001「認証方式とセッションストアの選定」
  決定事項: JWTベースの認証方式を採用し、かつセッションはRedisで管理する
            ↑ 「認証方式の選定」と「セッションストア構成の選定」という
              独立した2つの決定が混在している
```

**Good: 決定ごとに分割する**

```
ADR-001「認証方式にJWTを採用する」
ADR-002「セッションストアにRedisを採用する」
  ↑ ADR-002はADR-001の決定を前提にできる（related: ADR-001）
```

---

### Rule ADR-2: 評価軸が独立した2テーマに分かれるなら分割する

**独立したテーマの見分け方:** 評価軸の一部が、選択肢の一部にしか適用できない
（例: 「認証方式」の評価軸である「トークン失効管理コスト」は、インフラ選定の
選択肢には無関係）。SPECのRule S-2（独立した状態機械）に相当する判定。

```
評価軸: 開発速度 / セキュリティ / スケーラビリティ / 運用コスト
  ↑ 選択肢A・B（認証方式）にはすべて適用できるが、
    選択肢C・D（キャッシュ戦略）には「セキュリティ」が意味を持たない
    → 評価軸が噛み合っていない = テーマが2つ混在しているサイン
```

→ ADR-001「認証方式の選定」と ADR-002「キャッシュ戦略の選定」に分割する

---

### Rule ADR-3: 後続アクションが独立してリリース・撤回できるなら分割を検討する

「後続アクション」に、互いに依存せず個別にリリース・撤回できる複数の作業が
含まれている場合、それぞれが別の決定に対応している可能性が高い。

```
後続アクション:
  - リフレッシュトークン仕様の策定（ADR-001の決定に依存）
  - セッションストアの冗長化構成の設計（ADR-001の決定と無関係に進められる）
    ↑ 後者は別の意思決定（インフラ構成）に属する可能性がある
```

---

### Rule ADR-4: 本文が1ページ相当を超えたら分割を検討する

本文（コンテキスト〜再検討条件まで、見出しを除く）が概ね150行を超える、
または選択肢が4つ以上ある場合、複数の決定が1つのADRに詰め込まれているサイン。

---

### ADR-xxx 分割・統合トリガー早見表

| 状況 | 判断 |
|---|---|
| 決定事項が一文で明確に書ける | **分割を維持する** |
| 決定事項に複数の動詞・対象物が並記されている | **分割する** |
| 評価軸が独立した2テーマに分かれ、一部の選択肢にしか適用できない軸がある | **分割する** |
| 後続アクションに互いに独立してリリース・撤回できる作業が複数含まれる | **分割を検討する** |
| 本文が1ページ相当（目安150行）または選択肢が4つ以上 | **分割を検討する** |
| 一方の決定がもう一方の決定を前提にしている | **分割し、`related` で関連付ける** |

## 4. F と SPEC の境界ルール

### 定義

> **F: ユーザー視点で「何ができるか」を定義する。実現方法に踏み込まない。**
> **SPEC: システム視点で「どう動くか」を定義する。フロー・制約・データを詳細に記述する。**

---

### Rule B-1: ユーザーが観察できる結果はF、内部の動作はSPEC

| 記述内容 | 置き場 | 理由 |
|---|---|---|
| 「5回失敗するとロックされること」 | F（受け入れ基準） | ユーザーが観察できる振る舞い |
| 「ロック解除までの時間は15分であること」 | SPEC（フロー定義） | 内部ルールの詳細 |
| 「パスワードはハッシュ化して保存されること」 | SPEC（非機能仕様） | 実装の詳細、ユーザーには見えない |
| 「エラー時に『認証情報が正しくありません』と表示されること」 | F（受け入れ基準）またはSPEC（画面仕様）どちらでも可 | ※後述 |

---

### Rule B-2: 受け入れ基準（AC）の書き方でFとSPECを分ける

Fの受け入れ基準は **「何が起きるか」** を書く。
「どうやって起きるか」はSPECに委ねる。

**Bad: AcがSPECの記述になっている**

```
F-001 受け入れ基準:
  AC-003 パスワードは bcrypt (cost=12) でハッシュ化されること
         ↑ 実装詳細。FではなくSPEC-001の非機能仕様に書く
  AC-004 セッショントークンは JWT (HS256) で発行されること
         ↑ 同上
```

**Good: ACはユーザーが観察できる振る舞いに限定する**

```
F-001 受け入れ基準:
  AC-001 [正常系] 正しい認証情報でログインすると、
                  ダッシュボードへ遷移すること
  AC-002 [エラー系] 誤った認証情報でログインすると、
                    エラーメッセージが表示され、入力フォームに留まること
  AC-003 [権限] 未認証でダッシュボードURLにアクセスすると、
                ログイン画面にリダイレクトされること

→ パスワードのハッシュ化方式は SPEC-001 の非機能仕様に書く
→ JWTの仕様は SPEC-003「セッション発行・管理」に書く
```

---

### Rule B-3: エラーメッセージの文言はどちらに書くか

エラーメッセージの文言はFとSPECで**二重管理しない**。

| 書く場所 | タイミング |
|---|---|
| F（受け入れ基準）| 「エラーが表示されること」という**振る舞いの確認**として書く |
| SPEC（フロー定義表・画面仕様）| **具体的な文言**を定義する |

```
F-001 受け入れ基準:
  AC-010 [エラー系] 必須項目未入力で送信すると、エラーメッセージが表示されること
                    ↑ 「表示されること」まで。文言はSPECに委ねる

SPEC-001 フロー定義表:
  例外系 | 必須項目未入力 | バリデーション | 「○○を入力してください」を表示
          ↑ ここで文言を定義する
```

---

### Rule B-4: 実装に依存する情報はすべてSPECに書く

以下はすべてSPECに書く。Fには書かない。

- 入力の型・桁数・文字種制約
- NULL/空文字の扱い
- API のエンドポイント・リクエスト/レスポンス形式
- エラーコード
- タイムアウト時間の具体的な数値
- 状態遷移の条件・遷移先
- 暗号化方式・アルゴリズム

## 5. 判断フロー早見表

### 「これはFかSPECか？」

```
書こうとしている内容は...

ユーザーが観察できる振る舞いか？
  Yes → F（受け入れ基準）に書く
  No  ↓
    実装・内部動作の詳細か？
      Yes → SPEC に書く
      No  ↓
        ユーザーが達成するゴールの定義か？
          Yes → F（ユーザーストーリー）に書く
```

---

### 「1つのFか、複数のFか？」

```
ユーザーストーリーが1文に収まるか？
  No  → 分割する（Rule F-1）

So that（価値）が同じか？
  No  → 分割する（Rule F-2）

アクターが同じか？
  No  → 分割する（Rule F-3）

UIの1ステップにすぎないか？
  Yes → 上位のFに統合する（Rule F-4）
```

---

### 「1つのSPECか、複数のSPECか？」

```
フロー定義表が15行を超えるか？
  Yes → 分割を検討する（Rule S-1）

独立した状態機械が混在しているか？
  Yes → 分割する（Rule S-2）

分割後のSPECが3行以下になるか？
  Yes → 統合する（Rule S-3）

複数のFで同じ振る舞いを使うか？
  Yes → 1SPECにまとめ複数Fから参照する（Rule S-4）
```

---

### 「1つのADRか、複数のADRか？」

```
決定事項が一文で明確に書けるか？
  No  → 分割する（Rule ADR-1）

評価軸が独立した2テーマに分かれていないか？
  分かれている → 分割する（Rule ADR-2）

後続アクションが互いに独立してリリース・撤回できないか？
  できる → 分割を検討する（Rule ADR-3）

本文が1ページ相当（目安150行）・選択肢4つ以上か？
  Yes → 分割を検討する（Rule ADR-4）
```

## アンチパターン集

| アンチパターン | 症状 | 対処 |
|---|---|---|
| **ゴール混在F** | 1つのFにユーザーストーリーが複数ある | So that単位で分割（Rule F-2） |
| **UIステップF** | F名が「〇〇を入力する」「〇〇ボタンを押す」になっている | 上位ゴールのFに統合（Rule F-4） |
| **全部入りSPEC** | 1つのSPECのフロー定義表が20行を超えている | 状態機械の単位で分割（Rule S-2） |
| **形骸化SPEC** | 1つのSPECがフロー3行・例外なしで終わっている | 上位SPECに統合（Rule S-3） |
| **1:1強制** | 「F-001があるからSPEC-001」と機械的に対応させている | SPECはFと1:1でなくてよい（Rule S-4） |
| **実装詳細F** | 受け入れ基準に暗号化方式・タイムアウト値・APIレスポンス形式が書かれている | SPECに移動（Rule B-4） |
| **文言二重管理** | FとSPECの両方にエラーメッセージの文言が書かれている | SPECに一元化（Rule B-3） |
| **決定混在ADR** | 1つのADRの決定事項に複数の独立した決定が並記されている | 決定ごとに分割し `related` で関連付け（Rule ADR-1） |

## 具体例: ログイン機能の全体構造

> 以下はルールを適用した場合の正しい構造例。

```
F-001「パスワードでログインする」
  traces: SPEC-001, SPEC-002, SPEC-003

F-002「Googleアカウントでログインする」
  traces: SPEC-004, SPEC-003   ← セッション管理はSPEC-003を共有

F-003「ログアウトする」
  traces: SPEC-005, SPEC-003   ← 同上

F-004「パスワードをリセットする」
  traces: SPEC-006, SPEC-007

  ↓

SPEC-001「パスワード認証フロー」        ← F-001のみが参照
SPEC-002「アカウントロック管理」        ← F-001のみが参照
SPEC-003「セッション発行・管理」        ← F-001, F-002, F-003が共有参照
SPEC-004「OAuthフロー (Google)」       ← F-002のみが参照
SPEC-005「ログアウト処理」             ← F-003のみが参照
SPEC-006「パスワードリセットメール送信」 ← F-004のみが参照
SPEC-007「パスワード再設定フロー」      ← F-004のみが参照
```
