# 用語定義 (Glossary)

> このドキュメント全体で使う用語を定義する。
> 同じ概念に複数の呼称が存在する場合は **正式名称** を決め、別名を記載する。
>
> **運用ルール:**
> - 要求定義・要件定義・機能・仕様ドキュメントで専門用語・ドメイン用語を使用する場合は、必ずこのファイルに定義を追加する
> - 複数の呼び方がある概念は、プロジェクト内で使う **正式名称** を決定し、ここに記録する
> - 用語の追加・変更は README.md の更新履歴にも記録すること
> - チーム内で用語の認識齟齬が発生した場合は、このファイルを参照して解決する

## ドメイン用語

| 用語 | 定義 | 別名・略称 | 備考 |
|---|---|---|---|
| 運用者 | 本システムの単一の利用者。フィード定義・トリアージ基準・閾値を編集し、必要に応じて手動実行する人間のロール | 利用者、本人 | 定期実行ジョブと合わせて2ロールのみ（要件定義 §2） |
| 定期実行ジョブ | GitHub Actions の cron により週1回起動される実行主体。無人で全処理を行う | バッチ、cron ジョブ | 設定変更と状態のリセットは行わない（権限マトリクス参照） |
| 学習パイプライン | 収集 → 週次レビュー → deep-inquiry → tech-learning-note という、運用者が既に確立している一連の学習プロセス | パイプライン | 本システムはこのうち最上流の「収集」のみを担う |
| 収集レイヤー | 学習パイプラインの最上流。読む候補となる記事を溜める場所。本プロジェクトでは Raindrop.io を指す | - | 収集レイヤーの実体を Raindrop から変更することは制約上不可（要求定義 §7） |
| 週次レビュー | 収集レイヤーに溜まった候補を運用者が確認し、深く読むものを選別する下流の運用 | - | 本システムのスコープ外。本システムはその素材を供給する |
| トリアージ | 取得した記事を、学習価値の観点から機械的に評価し、収集レイヤーへ投入するか否かを選別する処理 | 選別、スコアリング | 本システムの中核機能（REQ-F-003） |
| トリアージ基準 | トリアージにおいて記事を評価する際の判断基準。`profile.md` として管理される想定 | 評価基準、profile | 変更には運用者の合意を要する（`.ref/spec.md` の「要合意」項目） |
| スコア | トリアージの結果として記事に付与される 0〜10 の整数。値が大きいほど学習価値が高いと評価されたことを示す | - | 情報源の重みによる補正前の値を指す |
| 重み (weight) | 情報源ごとに事前定義される補正値（+1 / 0 / -1）。設計解説の比率が高い情報源を優遇し、告知の比率が高い情報源を減点する | ソース重み | 記事単体からは読み取れない情報源の傾向を反映する（REQ-F-004） |
| 補正後スコア | スコアに情報源の重みを加算した値。投入可否の判定にはこの値を用いる | - | `補正後スコア = スコア + 重み` |
| 投入対象 | 補正後スコアが閾値以上と判定され、収集レイヤーへの投入が予定されるエントリ。**実際に投入されたか（＝投入数）とは区別する** | - | dry-run では投入対象と判定されても投入は行われない（F-005 AC-003）。通常実行でも投入失敗により投入対象数 ≠ 投入数となりうる |
| 閾値 | 投入可否を分ける境界値。補正後スコアがこの値以上のエントリを収集レイヤーへ投入する | しきい値 | 初期値は 5。変更には運用者の合意を要する（`.ref/spec.md` の「要合意」項目） |
| 二層方式 | 週20本以上を広く投入した上で、レビュー時の視線を高スコア帯（`#hot`）に絞る運用方針 | - | 「広く拾うこと」と「レビュー時間を抑えること」を両立させるための方針（R-004） |
| エントリ | フィードから取得される個々の記事を指す単位。URL・タイトル・要約・公開日時・情報源名を持つ | 記事、アイテム | 一意性は URL で判定する（REQ-F-002） |
| 新規エントリ | 取得したエントリのうち、過去に処理済みとして記録されていないもの | - | 重複排除を経た後のエントリ |
| 情報源 | 購読対象の RSS/Atom フィード1件。名称・URL・重み・タグ・疎通確認状態を持つ | ソース、フィード | 現在13件（`.ref/feeds.yaml` が唯一の出典。件数変更時はそちらを参照する） |
| 処理済みエントリ | 一度トリアージを経たエントリ。投入の有無にかかわらず記録される | 状態、state | 記録が重複排除（R-002）と基準検証（R-006）の両方を支える |
| 畳み込み | 追記専用の状態ファイルに複数存在しうる同一 URL の行から、`evaluated_at` が最大の行を選んで現在の状態を再構成する処理 | fold | [ADR-005](04_decisions/ADR-005_state_file_format.md) OQ-001 の読み取り規則。SPEC-002 §1 |
| 状態ブランチ | 処理済み状態（`state.jsonl`）のみを保持する orphan branch `state` | state ブランチ | [ADR-002](04_decisions/ADR-002_state_persistence.md) の決定。既定ブランチとは履歴を共有しない |
| `evaluated_at` | 状態の各行が持つ評価時刻（UTC の ISO 8601）。畳み込みで最新行を決めるキー | - | 行順ではなくこの値で最新を判定する（rebase 後の行順が保証されないため） |
| 失敗回数 | 評価に失敗した記事について記録される**総試行回数**。上限に達すると以降再評価しない | `failure_count` | 週数ではない。実行内の試行回数分だけ増加する（F-001 AC-015）。API 呼び出し自体の失敗は計上しない（AC-015a） |
| 持ち越し | 1回の実行の評価件数上限を超えたため評価せず、**記録もせずに**次回実行へ回すこと | - | F-001 AC-025。記録しない点が「再評価対象」と異なる |
| dry-run | 収集レイヤーへの投入を一切行わず、評価結果とサマリのみを出力する実行方法 | ドライラン | 基準変更時の影響確認に用いる（REQ-F-009） |
| 実行サマリ | 1回の実行について出力される、取得数・新規数・投入数・スコア分布・情報源別取得数の要約 | サマリ | 無人実行における唯一の異常検知手段（R-007） |
| 告知系記事 | 新機能の発表・GA・リリースノート等、事実の告知を主とする記事。学習素材としての価値が低い | - | 設計解説系との混在がトリアージを必要とする理由（要求定義 §1） |
| 設計解説系記事 | アーキテクチャ・設計判断・内部実装の解説を主とする記事。学習素材としての価値が高い | - | 同上 |

## システム用語

| 用語 | 定義 | 備考 |
|---|---|---|
| Raindrop.io | 本プロジェクトが収集レイヤーとして使用するブックマークサービス | 正式名称は「Raindrop.io」。文中で「Raindrop」と略記してよい |
| コレクション | Raindrop.io におけるブックマークの分類単位 | 投入先コレクションは事前に手動作成し、ID を環境変数で渡す |
| `#auto` | 本システムが自動投入したことを示すタグ | 運用者が手動登録したものとの区別に使う。撤退時の一括削除の手がかりにもなる（要件定義 §7） |
| `#hot` | 補正後スコアが高評価帯（7以上）であることを示すタグ | 二層方式におけるレビューの視線を絞る手段（R-004） |
| `#score-{n}` | 付与されたスコアを示すタグ | 事後の分布確認に用いる |
| `#digest-candidate` | 週次レビューを経て、さらに深く扱う候補に昇格したことを示すタグ | 本システムが付与するものではなく、下流の運用で付与される。トリアージ精度の検証指標として参照する（要求定義 §4） |
| 冪等性 | 同じ操作を複数回実行しても結果が変わらない性質 | 本システムでは「同一フィード定義で連続実行したとき、2回目の投入数が0になること」を指す（R-002 / C-R01） |
| 生存者バイアス | ここでは「投入したエントリのみを記録すると、閾値を下げていれば拾えていた記事が観測できなくなる」という偏りを指す | 閾値未満のエントリも記録する理由（R-006） |
| フィード | RSS または Atom 形式で配信される、更新情報の一覧 | 本システムは取得のみを行い、フィードの自動発見は行わない |
| JSONL | 1行1レコードの JSON を並べたテキスト形式。処理済み状態の保持形式 | 追記のみを行い、既存行の書き換え・削除は行わない（→ [ADR-005](04_decisions/ADR-005_state_file_format.md)） |

## 用語間の関係

```
学習パイプライン
  └─ 収集レイヤー (= Raindrop.io)   ← 本システムが供給する
        └─ コレクション
              └─ エントリ (投入されたもの)
                    └─ タグ (#auto, #hot, #score-{n}, ソース由来タグ, 提案タグ)
  └─ 週次レビュー   ← 収集レイヤーを消費する (本システムのスコープ外)
        └─ #digest-candidate への昇格
  └─ deep-inquiry
  └─ tech-learning-note

情報源 ─[配信する]─ フィード ─[含む]─ エントリ
情報源 ─[持つ]─ 重み

エントリ ─[トリアージにより]─ スコア
スコア + 重み = 補正後スコア ─[閾値と比較]─ 投入可否
処理済みエントリ ─[記録する]─ 全エントリ (投入したもの・しなかったもの両方)
```
