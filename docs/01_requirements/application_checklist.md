# アプリケーション種別チェックリスト (Application Type Checklist)

> **重要:** このドキュメントは `enterprise_checklist.md`（全種別共通）の **追加チェックリスト** です。
> `enterprise_checklist.md` を先に完了してから、このドキュメントに取り組んでください。
>
> このドキュメントでは、アプリケーション種別に固有の観点をチェックします:
> - 自分のアプリケーション種別に該当するセクションを記入する
> - 複数の種別に該当する場合（例: CLIとバックグラウンドサービスを兼ねる）は複数セクションを記入する
>
> **記入ルール:**
> - `○` 適用する → `対応方針 / 参照先` に具体的な内容を記入
> - `✗` 対象外 → `対象外の理由` を必ず記入（空欄は「未検討」とみなす）
> - `-` 未検討 → **README.md のタスク一覧に `CL` 種別で登録し**、リリース前に ○ / ✗ に解決すること

---

## 適用セクションの選択

> 該当する種別にチェックを入れ、そのセクションを記入する。

- [ ] **Section 1:** Web アプリケーション（ブラウザ経由でアクセスするもの）
- [ ] **Section 2:** ローカル GUI アプリケーション（デスクトップで動作するもの）
- [x] **Section 3:** ローカル CUI / CLI アプリケーション（ターミナルで動作するもの）

> **判断:** 本システムは CLI ツールであり、GitHub Actions 上でバッチとして無人実行される

> 各項目に `✗` と理由を記入して「見て除外した」証跡を残している。

## Section 3: ローカル CUI / CLI アプリケーション

### 3.1 セキュリティ（CLI固有）

> **背景:** CLIはスクリプトやCI/CDから呼ばれることが多く、
> 引数・環境変数・標準入力が攻撃面になる。

| # | 観点 | 適用 | 対応方針 / 参照先 | 対象外の理由 |
|---|---|---|---|---|
| C-S01 | 引数インジェクション対策（外部コマンド呼び出し時のエスケープ） | ○ | 外部コマンド (`claude -p`) 呼び出し時、記事タイトル・要約を引数に連結せず、標準入力またはリスト形式の引数で渡す。SPEC 化時に方式を確定する |  |
| C-S02 | シェルインジェクション対策（サブプロセス起動時のシェル経由禁止） | ○ | サブプロセス起動時に `shell=True` を使用しない。フィード由来の文字列がシェルに解釈される経路を作らない |  |
| C-S03 | 環境変数経由のシークレット受け取り（引数での渡し禁止: `ps` で見える） | ○ | Raindrop の認証情報・コレクション ID は環境変数で受け取る。コマンドライン引数では渡さない (REQ-NF-006) |  |

| C-S05 | 設定ファイルのパーミッション確認（機密情報を含む場合は 600） | ✗ |  | 機密情報を含む設定ファイルを持たない。フィード定義・トリアージ基準は公開可能な内容のみを含み、秘匿値は環境変数に分離する (REQ-NF-006) |
| C-S06 | sudo / 特権昇格の要否と最小化（必要なければ一般ユーザーで動作） | ○ | 特権昇格を必要としない。一般ユーザー権限で全処理が完結する |  |
| C-S07 | 破壊的操作（削除・上書き等）の実行前確認プロンプト | ✗ |  | 削除・上書きを伴う破壊的操作を提供しない。処理済み状態への書き込みは追記のみで、状態のリセットは運用者が手動でファイルを削除する運用とする |

### 3.2 インターフェース設計

> **背景:** CLIはヒューマンオペレーターとスクリプト双方から使われる。
> 両者に対して予測可能な動作をすることが信頼性の基本。

| # | 観点 | 適用 | 対応方針 / 参照先 | 対象外の理由 |
|---|---|---|---|---|
| C-I01 | 終了コードの標準化（0: 正常終了 / 非0: 異常終了 / コードの意味を文書化） | ○ | 正常終了 0 / 異常終了 非0 とする。**個別**エントリの評価・投入失敗、個別情報源の取得失敗は異常終了とせず 0 で終える (REQ-F-010)。ただし**投入対象が1件以上あったにもかかわらず全件失敗した場合は非0で終了する**（無人実行では実行履歴が唯一の検知契機であり、投入0件が緑に見えると R-007 が満たせないため）。**コード体系（0〜4）の正典は [SPEC-005 §5](../03_specs/SPEC-005_cli.md) が定義する** |  |
| C-I02 | stdout / stderr の使い分け（データ出力は stdout / エラー・ログは stderr） | ○ | 実行サマリ (REQ-F-008) は stdout、ログ・警告・エラーは stderr に出力する (REQ-NF-007) |  |
| C-I03 | パイプ・リダイレクトでの動作確認（stdin からの入力受け取り） | ✗ |  | stdin からの入力を受け取らない。入力源はフィード定義ファイルと各フィードの HTTP 応答に限られる |

### 3.5 信頼性・冪等性

> **背景:** CLIはスクリプトから繰り返し実行されることが多い。
> 「同じコマンドを2回実行しても安全か」を設計段階で意識する。

| # | 観点 | 適用 | 対応方針 / 参照先 | 対象外の理由 |
|---|---|---|---|---|
| C-R01 | 冪等性の確保（同じコマンドを複数回実行しても結果が変わらない） | ○ | 同一のフィード定義で連続実行したとき、2回目の投入数が 0 になること。処理済み URL の永続化により保証する (REQ-F-002) |  |
| C-R02 | 中断・再実行時のリカバリ（途中で止まっても再実行で完了できる） | ○ | 実行が途中で中断しても、それまでに処理済みとして記録された分は次回スキップされ、未記録の分は次回に新規として再処理される。記録は投入直後に行い、投入済みなのに未記録という状態を最小化する。詳細は SPEC 化時に定義する |  |
| C-R03 | タイムアウト設定（外部通信・長時間処理に対して明示的に設定） | ○ | フィード取得は1情報源あたり30秒、評価・投入にも明示的なタイムアウトを設定する (REQ-NF-001 / REQ-NF-004) |  |
| C-R04 | 大量データ処理時のメモリ使用量（ストリーミング処理 vs 全件ロード） | ○ | 週あたり新規100件・年間5,000件規模であり全件ロードで問題ない (REQ-NF-002)。ストリーミング処理は行わない |  |
