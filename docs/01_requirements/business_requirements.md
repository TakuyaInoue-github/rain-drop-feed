## 1. 背景・文脈

技術ブログからのインプットを、**収集 → 週次レビュー → deep-inquiry → tech-learning-note** という
個人の学習パイプラインで処理している。このうち下流（レビュー以降）の運用は確立している一方、
最上流の **収集レイヤー（Raindrop.io への流入）が完全に手動** であり、パイプライン全体の
ボトルネックになっている。

収集対象は AWS・GCP・Databricks・Snowflake 等の公式ベンダーブログ、企業テックブログ、
データエンジニアリング領域の個人ブログ、Hacker News の該当トピックであり、
情報源は 10 数件に分散している。

公式ベンダーブログは **新機能の告知（GA・リリースノート等）と、設計・アーキテクチャの解説記事が
同一フィードに混在する**。前者は学習素材としての価値が低く、後者は高い。この選別は
タイトルと要約を読んで判断する必要があり、購読フィードを増やすほど選別コストが線形に増える。

## 3. 問題の構造 (Problem Statement)

> **注意:** ここにはソリューション（どう解決するか）を書かない。「何が起きているか」の事実を記述する。
> 症状（表面に見えること）と根本原因（なぜそれが起きるか）を必ず区別すること。

### 3.1 誰が困っているか

| 困っている人 | 業務文脈 |
|---|---|
| 本人（学習者として） | 週次レビューの前に、読むべき記事の候補を集めようとするとき |
| 本人（学習者として） | 複数の情報源を巡回して、学習価値のある記事を選別しようとするとき |

### 3.2 トリガー（何をしようとしたときに困るか）

- 週次レビューの直前に、13 件の情報源を個別に開いて新着を確認しようとするとき
- ベンダーブログの新着一覧から、告知記事と設計解説記事を見分けようとするとき
- 巡回を数週間サボった後、どこまで確認済みかを思い出そうとするとき
- 良さそうな記事を見つけて Raindrop に手動で登録し、タグを付けようとするとき

### 3.3 症状（現状何が起きているか）

> **注意:** 本プロジェクトは個人利用であり、業務ログ・インシデント管理システムのような
> 客観的な計測基盤を持たない。現状値は体感ベースであり、**実測値の確定は OQ-001 で扱う**。

| 症状 | 確認方法・根拠 |
|---|---|
| 巡回が習慣として続かず、数週間単位で途切れる | 本人の実感（Raindrop の登録日の分布で検証可能） |
| 巡回が途切れた週は、週次レビューに乗る候補がゼロになる | 同上 |
| Raindrop への登録が「見つけたときに手で入れる」運用のため、登録数が週によって大きく振れる | Raindrop のコレクション内の登録日分布 |
| どの情報源をどこまで確認したかの記録がなく、再開時に既読分を読み直している | 本人の実感 |

### 3.4 根本原因

| 症状 | 根本原因 |
|---|---|
| 巡回が習慣として続かない | 収集が「人間が定期的に能動的に動く」ことを前提にした設計になっている。継続の動機づけが本人の意志力に依存している |
| 巡回が途切れると候補がゼロになる | 収集レイヤーに自動化された供給経路が存在せず、人間の巡回が唯一の入力経路になっている |
| 登録数が週によって大きく振れる | 投入のタイミングと量が人間の可処分時間に従属しており、供給が定常化する仕組みがない |
| 選別コストが情報源の数に比例して増える | ベンダーブログが告知と設計解説を同一フィードで配信しており、フィード購読だけでは選別できない。選別が人間の読解に依存している |
| 再開時に既読を読み直す | 「どこまで処理したか」の状態がどこにも永続化されていない |

### 3.5 To-Be（解決されたとき何が変わるか）

| 現状 (As-Is) | 解決後 (To-Be) |
|---|---|
| 収集が本人の巡回に依存し、途切れる週がある | 週1回自動実行され、本人が何もしなくても候補が供給される |
| 13 件の情報源を個別に開いて確認する | Raindrop の 1 コレクションを見れば済む |
| 告知と設計解説を人間が読んで選別する | 機械が事前にスコアリングし、閾値以下は Raindrop に入らない |
| 全候補を平等に見るため、レビューの視線が分散する | `#hot` タグで高スコア帯に視線を絞れる（二層方式） |
| どこまで処理したか分からず既読を読み直す | 処理済み URL が永続化され、再実行しても重複しない |

## 4. ゴールと成功基準

> **注意:** 「改善する」「使いやすくする」は成功基準として不十分。**測定可能な数値・状態**で書くこと。

| ゴール | 成功基準 | 計測方法 | 計測タイミング |
|---|---|---|---|
| 収集の自動化（人手の排除） | 週次実行が人間の操作なしで完了した週の割合を 100% にする | GitHub Actions の実行履歴（成功/失敗） | 稼働開始から4週間後 |
| 供給量の確保 | Raindrop に投入される候補を **週20本以上** にする（判定単位は OQ-005 で確定する） | 実行サマリの投入数、および state 内の投入フラグ件数 | 毎週の実行時 |
| 選別コストの削減 | レビュー時に精読する候補を `#hot`（score 7以上）に限定し、週あたり精読対象を投入数の3割以下に抑える | state 内の **投入フラグが立ったエントリ** の score 分布（閾値未満を含む全件の分布ではない点に注意） | 稼働開始から4週間後 |
| トリアージ精度の事後検証を可能にする | score 7以上のうち、レビューを経て `#digest-candidate` に昇格した割合を測定できる状態にする（＝全 score が永続化されている） | state に閾値未満の分も含めた全件の score が記録されていること。**実際の昇格率の算出は Raindrop 上での手動突合による**（自動突合は §5 Out of Scope） | 稼働開始から2週間後 |
| 重複ゼロ | 同一エントリが Raindrop に二重投入された件数を 0 件にする | Raindrop コレクション内の URL 重複チェック | 毎週の実行時 |

> **注記:** 「週20本以上」は `docs/.ref/spec.md` の方針「週20本以上を広く拾い、レビューの視線は
> `#hot` タグで絞る二層方式」に由来する。この数値は閾値（初期値 5）と購読フィード構成に依存するため、
> 稼働後の実測で閾値を再調整する余地がある（→ R-006）。

## 5. スコープ

### In Scope

- 定義済みフィードからの新着エントリの定期取得
- 取得済みエントリの永続化による重複排除（冪等な再実行）
- 記事タイトルと RSS 要約に基づく機械的なスコアリング
- スコアに基づく取捨選択と、Raindrop.io の指定コレクションへの自動投入
- 投入時のタグ付与（自動投入の識別、スコア帯、情報源、内容に基づく提案タグ）
- 無人での定期実行
- 1回の実行結果の可視化（取得数・新規数・投入数・スコア分布）

### Out of Scope

> **注意:** 「あれもやるんですよね？」と言われそうなことを先回りして明示する。
> 書かれていない = やる、と解釈されるリスクがある。

| 対象外の内容 | 対象外にする理由 |
|---|---|
| 記事本文の取得・要約 | タイトルと RSS 要約のみで選別が成立するかを先に検証する。本文取得はスクレイピング耐性・実行時間・コストの負担が大きく、効果が確認されるまで持ち込まない |
| フィードの自動発見・OPML インポート | 購読フィードは手動管理で足りる規模（13件）。情報源の追加は年に数回程度であり、自動化の投資対効果が見合わない |
| 重み・閾値の自動チューニング | チューニングの前に、判断根拠となる実測データ（score 分布と昇格率）を蓄積する必要がある。データがない段階での自動化は根拠のない最適化になる |
| Slack 等への通知 | 単一利用者であり、実行結果は GitHub Actions のログで確認できる。通知経路を増やすと秘匿情報の管理対象も増える |
| Raindrop 側での既読・評価の反映（双方向同期） | 本システムは Raindrop への一方向の投入のみを担う。レビュー結果の反映は下流の運用（週次レビュー）が担当する |
| 投入済みエントリの事後的な再スコアリング・削除 | 誤投入は Raindrop 上で手動削除すれば足りる。取り消し機能は状態管理を複雑にする |
| 複数ユーザーでの共有・権限管理 | 単一利用者の個人ツールであり、認証・認可の対象となる境界が存在しない |

## 6. ビジネス要求 (R-xxx)

> **書き方:** 「〜できること」「〜であること」の形で記述する。
> 機能の実現方法（How）はここに書かない。何が必要か（What）を書く。
>
> 優先度の定義:
> - **Must:** これがなければシステムの目的を達成できない
> - **Should:** あると大きく価値が上がるが、なくても目的は達成できる
> - **May:** あれば望ましいが、優先度は低い

---

### R-001: 収集レイヤーへの供給が人手を介さず継続すること

**説明:**
定義された情報源から新着記事を定期的に取得し、選別を経て収集レイヤー（Raindrop.io）へ
供給する一連の流れが、利用者の操作なしに継続すること。利用者が巡回を忘れた週があっても
供給が途切れないこと。

**根拠:**
問題の根本原因は「収集が人間の能動的な巡回を前提にした設計になっている」ことにある（§3.4）。
人間の意志力に依存する限り、途切れは再発する。パイプライン全体（週次レビュー →
deep-inquiry → tech-learning-note）は上流の供給が前提であり、供給の途切れは下流全体を停止させる。

**優先度:** Must
**ステータス:** draft

---

### R-002: 同じ記事を繰り返し処理・投入しないこと

**説明:**
処理済みの記事が記録され、システムを何度実行しても同じ記事が収集レイヤーに重複して
投入されないこと。また、前回どこまで処理したかを利用者が意識しなくてよいこと。

**根拠:**
「どこまで確認したかの記録がない」ことが、再開時に既読を読み直す症状の根本原因である（§3.4）。
また定期実行を前提とする以上、実行のたびに重複が増えるようでは収集レイヤーが汚染され、
レビューの対象として使い物にならなくなる。障害時の再実行も安全に行えなくなる。

**優先度:** Must
**ステータス:** draft

---

### R-003: 学習価値の低い記事が収集レイヤーに混入しないこと

**説明:**
取得した記事が、利用者の定めた基準に照らして機械的に評価され、価値が低いと判断された
ものは収集レイヤーに投入されないこと。評価基準は利用者が定義・変更できること。

**根拠:**
公式ベンダーブログでは告知系と設計解説系が同一フィードに混在しており（§1）、
フィードを購読するだけでは選別できない。選別を人間が行う限り、購読フィードを増やすほど
コストが線形に増え、「情報源を増やす」という改善策そのものが取れなくなる。

**優先度:** Must
**ステータス:** draft

---

### R-004: レビュー時に注力すべき記事が識別できること

**説明:**
収集レイヤーに投入された記事のうち、特に価値が高いと評価されたものを、利用者が
レビュー時に区別できること。

**根拠:**
「週20本以上を広く拾い、レビューの視線は `#hot` タグで絞る」という二層方式を採る（§4）。
広く拾うことと、レビュー時間を抑えることは本来トレードオフであり、この両立には
投入した中での優先度表示が必要になる。これがないと、広く拾った結果としてレビュー
コストが増大し、R-001 で解決したはずの問題が形を変えて再発する。

**優先度:** Must
**ステータス:** draft

---

### R-005: 情報源ごとの傾向を評価に反映できること

**説明:**
情報源ごとに、機械的な評価を事前に補正できること。設計解説の比率が高い情報源を
優遇し、告知の比率が高い情報源を減点できること。

**根拠:**
記事単体の評価だけでは、情報源が持つ既知の傾向（例: 特定のベンダーブログは告知の比率が
構造的に高い）を反映できない。この傾向は記事のタイトル・要約からは読み取れず、
利用者が事前に知っている情報である。反映手段がないと、告知比率の高い情報源を
購読対象から外すしかなくなり、そこに含まれる少数の良質な記事を取り逃がす。

**優先度:** Should
**ステータス:** draft

---

### R-006: 選別基準の妥当性を後から検証できること

**説明:**
収集レイヤーに投入しなかった記事についても、評価結果が記録として残ること。
それにより、選別基準（閾値・重み）が厳しすぎたか緩すぎたかを事後に検証できること。

**根拠:**
初期の閾値・重みは実測データのない状態で決めた暫定値である。投入したものだけを
記録すると、「閾値を下げていれば拾えていた記事」が観測できず、基準を見直すための
根拠が永久に得られない（生存者バイアス）。スコープ外とした「重み・閾値の自動
チューニング」を将来検討する場合も、この記録が前提になる。

**優先度:** Should
**ステータス:** draft

---

### R-007: 1回の実行で何が起きたかを利用者が把握できること

**説明:**
実行のたびに、取得した件数・新規の件数・投入した件数・評価の分布が利用者に
提示されること。

**根拠:**
無人実行では、異常（フィードの停止、評価の偏り、投入のゼロ件化）が起きても
利用者が気づく契機がない。R-001 で人手を排除する以上、代わりに「結果を見れば
異常が分かる」状態が必要になる。またこの記録は R-006 の検証の入り口としても機能する。

**優先度:** Should
**ステータス:** draft

---

### R-008: 収集レイヤーへ投入せずに評価結果だけを確認できること

**説明:**
実際の投入を伴わずに、評価結果のみを確認できる実行方法があること。

**根拠:**
評価基準や購読フィードを変更した際、その影響を確認する手段が「実際に投入してみる」
しかないと、確認のたびに収集レイヤーが汚染され、手動削除が必要になる。基準の変更は
継続的に発生する運用作業であり（R-003 の「利用者が定義・変更できること」）、
その試行が安全でないと基準の改善そのものが行われなくなる。

**優先度:** Should
**ステータス:** draft

## 7. 制約条件

### ビジネス制約

| 制約 | 内容 | 理由 | 交渉可否 |
|---|---|---|---|
| 予算 | 追加の金銭的コストを実質ゼロに抑える（LLM 利用料は週100エントリ規模の短いプロンプトに収まる範囲） | 個人の学習用ツールであり、継続的な支出を正当化する収益がない | 要相談 |
| スケジュール | 明示的なリリース期限は設けない | 個人プロジェクトであり、外部への納期コミットが存在しない | - |
| 実行基盤 | 常時稼働のサーバーを用意せず、既存の CI 基盤上で完結させる | 個人利用のために専用インフラを保有・保守するコストが見合わない | 要相談 |
| 外部サービス | 収集レイヤーは Raindrop.io を使用する（変更しない） | 下流の週次レビュー運用がすでに Raindrop 上で確立しており、変更は下流全体の作り直しになる | 不可 |
| 法規制 | 対象外 | 公開された RSS/Atom フィードの取得と、個人のブックマークサービスへの登録のみを行う。個人データの取り扱いが発生しない | - |

### 前提条件

> **問い:** このプロジェクトが成立するために「すでに真である」必要があることは何か？
> 前提が崩れた場合のリスクも合わせて記述する。

| 前提 | 崩れた場合のリスク |
|---|---|
| 購読対象の情報源が RSS/Atom フィードを提供し続けている | 該当情報源からの供給が停止する。フィード廃止が相次いだ場合、収集の網羅性が落ち R-001 の価値が減じる |
| Raindrop.io が外部からの登録手段（API）を提供し続けている | 収集レイヤーへの投入経路が失われ、システムが成立しない。収集レイヤー自体の移行が必要になる（制約上は不可） |
| LLM API（Anthropic）が利用可能であり、価格が予算制約を破らない水準にとどまる | トリアージが実行できず、R-003 が達成されない。評価手段の再選定が必要になる（→ [ADR-001](../04_decisions/ADR-001_llm_invocation_method.md) の再検討条件）。従量課金への依存とモデルの deprecation 追従が保守コストとして残る |
| タイトルと RSS 要約だけで、告知と設計解説をある程度選別できる | 選別精度が実用水準に達しない。本文取得（スコープ外）の再検討が必要になる |
| 機械的な評価が、利用者の判断と大きく乖離しない | 価値ある記事の取りこぼし、または低価値な記事の混入が続き、R-003 が達成されない |
| 実行基盤（CI）の無料枠が週1回の実行に対して十分である | 実行のたびに費用が発生し、予算制約に抵触する |
| 下流の週次レビュー運用が継続している | 供給しても消費されず、システムを稼働させる意味が失われる |

## 8. リスク

| リスク | 影響度 (高/中/低) | 発生確率 (高/中/低) | 対応方針 | オーナー |
|---|---|---|---|---|
| 機械的な評価の質が低く、選別が信用できない | 高 | 中 | 閾値未満のエントリも評価結果を記録し（R-006）、実測に基づいて基準を調整する。初期は閾値を低めに設定し、取りこぼしより混入を許容する | 本人 |
| フィードの URL 変更・廃止に気づかず、供給が静かに減る | 中 | 高 | 実行サマリで情報源ごとの取得件数を可視化する（R-007）。稼働前に全フィードの疎通を確認する | 本人 |
| 供給される候補が多すぎて、レビューが追いつかない | 中 | 中 | `#hot` による二層方式で精読対象を絞る（R-004）。それでも過剰な場合は閾値を上げる |  本人 |
| 収集レイヤー側の仕様変更（API・レート制限）で投入が失敗する | 高 | 低 | 実行結果で投入数のゼロ件化を検知する（R-007）。投入前に評価だけを確認できる手段を用意する（R-008） | 本人 |
| 秘匿情報（収集レイヤーの認証情報）の漏洩 | 高 | 低 | 認証情報をリポジトリに含めず、CI のシークレット管理機構経由で受け渡す | 本人 |
| **LLM API キーの漏洩** | 高 | 低 | 収集レイヤーの認証情報と異なり、漏洩は第三者による従量課金の発生＝**直接的な金銭被害**を生む。API キーに支出上限を設定しワークスペースを分離する（→ TASK-036）。ローテーション方針を定める（→ TASK-037） | 本人 |
| 個人プロジェクトゆえに保守が止まり、壊れたまま放置される | 中 | 中 | 実行失敗が CI 上で可視化される状態を維持する。運用の複雑化を避け、スコープ外を守る | 本人 |
