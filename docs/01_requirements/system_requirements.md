## 1. システム概要

| 項目 | 内容 |
|---|---|
| アプリケーション種別 | CLI ツール（バッチ処理として無人実行される） |
| 主要ユーザー | 単一の個人利用者（本人）。および CI 上の自動実行主体 |
| 稼働環境 | GitHub Actions のランナー上（ephemeral）。ローカル PC 上でも同一コマンドで実行可能 |
| 公開範囲 | 非公開。単一利用者のプライベートリポジトリ内で完結する |
| 実行言語・実行系 | Python 3.10 以上（パッケージ管理・実行は `uv` に統一する。→ [ADR-004](../04_decisions/ADR-004_implementation_stack.md)） |

このシステムは、定義済みの RSS/Atom フィードから新着記事を取得し、記事タイトルと要約を
LLM で評価（トリアージ）した上で、閾値を超えたものを Raindrop.io の指定コレクションへ
自動投入する CLI である。GitHub Actions の cron により週1回無人実行される。

## 2. ユーザーロールと権限マトリクス

> **注意:** ロールが不明確だと機能要件に「誰が」が書けなくなる。最初に確定させる。
> 人間ユーザーだけでなく、サービスアカウント・バッチ実行ユーザーも含めて洗い出す。

本システムは単一利用者の個人ツールであり、**システム内部に認証・認可の機構を持たない**。
ロールの区別は「システムが提供する権限境界」ではなく、**実行主体と、その主体が
どの秘匿情報にアクセスできるか**という運用上の区別として定義する。

| ロール | 種別 | 説明 | 登録方法 |
|---|---|---|---|
| 運用者 | 人間 | 本人。フィード定義・トリアージ基準・閾値を編集し、ローカルで手動実行する | リポジトリへの書き込み権限（GitHub アカウント） |
| 定期実行ジョブ | サービスアカウント | GitHub Actions の cron により起動される実行主体。無人で全処理を行う | ワークフロー定義とリポジトリ Secrets の設定 |

### 権限マトリクス

| 操作 | 運用者 | 定期実行ジョブ |
|---|---|---|
| フィード定義・トリアージ基準・閾値の変更 | ○ | ✗（読み取りのみ） |
| CLI の実行（投入あり） | ○ | ○ |
| CLI の実行（dry-run） | ○ | ✗（通常実行のみ） |
| Raindrop への投入 | ○ | ○ |
| 処理済み状態の参照 | ○ | ○ |
| 処理済み状態の書き込み（状態専用ブランチへの push） | ○ | ○（`contents: write`。既定ブランチへは書き込まない → [ADR-002](../04_decisions/ADR-002_state_persistence.md)） |
| 処理済み状態の削除・リセット | ○ | ✗ |
| Raindrop 認証情報の参照 | ○（自身の環境変数として） | ○（Secrets 経由で注入される） |
| LLM API キー（`ANTHROPIC_API_KEY`）の参照 | ○（自身の環境変数として） | ○（Secrets 経由で注入される） |

> **注記:** 両ロールとも実質的に同一人物・同一権限セットに帰着する。この表は
> 「定期実行ジョブに何をさせないか」（＝設定変更と状態リセットは人間の操作に限る）を
> 明示することを目的とする。
>
> **強制手段について:** 本システムは認証・認可の機構を持たないため、この表の `✗` の大半は
> **システムが強制する制約ではなく、運用上の取り決め**である。技術的に強制されるのは
> 「既定ブランチへの書き込み」（ワークフローの `permissions` 設定による）のみで、
> dry-run の使用可否や状態リセットの禁止はワークフロー定義とコマンド引数の運用に依存する。

### 4.1 パフォーマンス

| 処理 | 目標値 | 測定条件 | 根拠 |

#### REQ-NF-002a: 評価コストの上限

> **背景:** `.ref/spec.md` は評価コストを「週100エントリ×短プロンプト。無視できる規模」と
> 見積もっていたが、実測により **既定モデルでは年 $600 規模**になることが判明した。
> 要求定義 §7 の「追加の金銭的コストを実質ゼロに抑える」制約に抵触するため、
> 非機能要件として明示的に管理する。

| 項目 | 目標値 | 根拠 |
|---|---|---|
| 評価コスト | 年 $150 以下（週あたり $3 以下） | 年 $150 = 月額約 $12.5（約1,900円）。個人の学習用サブスクリプション1本分に相当し、これを超えると要求定義 §7 の「実質ゼロ」とは言えなくなる境界として設定した。**上限値自体は暫定であり、初年度の実測後に見直す**。下記の実測により、正常運用では大幅に下回る |
| コスト超過の検知 | 実行サマリに当該実行の評価コストと処理件数を出力する | 無人実行のため、モデル変更・エントリ数の急増・リトライ暴走に気づく契機が他にない |
| **コスト超過の強制的な停止** | 専用ワークスペースに**月 $10 の支出上限**を設定する（2026-07-26 設定済み → TASK-036） | 上記の「検知」は運用者がサマリを見るまで働かない。無人実行では気づくまでに最大1週間かかるため、**気づく前に止まる**手段が別に要る。月 $10 は最悪の複合ケース（年 $31.20 = 月 $2.60）に対しても正常運用を妨げず、モデル誤指定（年 $13.52）や暴走時には停止する水準 |
| 1回の実行で評価する件数の上限 | **200件（暫定）**。超過分は次回に持ち越す | 実測の週31〜49件の約4倍であり、上振れケース（週100件）も吸収できる。状態ファイル消失時の全件再処理など、異常時に無制限の課金が発生する経路を塞ぐ安全弁。**暫定値であり OQ-007 / TASK-028 で確定する** |

**採用方針:** Anthropic API を直接呼び出し（→ [ADR-001](../04_decisions/ADR-001_llm_invocation_method.md)）、
評価には軽量モデル（Haiku 4.5 を暫定採用。→ [ADR-003](../04_decisions/ADR-003_triage_model_selection.md)）を用いる。
なお Sonnet 5 でも上限内（年 $8〜20）に収まるため、**コストはモデル選定の決定要因にならない**。

> **上限 $150 の位置づけ:** 一次的な根拠は要求定義 §7 の予算制約「追加の金銭的コストを
> 実質ゼロに抑える」であり、本項はそれを数値化したものである。下記のコスト試算は
> ADR-001 / ADR-003 の検証結果に基づくが、**上限値そのものは ADR に依存しない**。
既定モデルや CLI 経由では1回あたり約 18,000 トークンのオーバーヘッドが付随するため、
これを避けることがコスト削減の主因となる。

> **実測に基づく物量（2026-07-26、全14フィードへの疎通確認）:**
>
> | 項目 | 実測値 |
> |---|---|
> | 疎通できたフィード | 13 / 14（`blef-fr` が HTTP 404。**同日フィード未提供と確認し情報源から削除** → TASK-027） |
> | 直近7日の新着 | 55 件 |

### 4.2 可用性・信頼性

#### REQ-NF-003: 可用性目標

> **注記:** 本システムは常時稼働のサービスではなく、週1回起動されるバッチである。
> 「稼働率」ではなく「実行機会あたりの成功率」で目標を定義する。

| 指標 | 目標値 | 計算根拠 |
|---|---|---|
| 実行成功率 | 直近8回の実行のうち7回以上が正常終了（87.5%以上） | 週次実行のため、1回の失敗は最大1週間の供給遅延を意味する。連続失敗でなければ次週の実行で取り戻せる（未処理エントリは状態に記録されないため次回に持ち越される。**ただし状態の書き込みに失敗した場合は「投入済みだが未記録」が生じ、次回に重複投入されうる** → [ADR-002](../04_decisions/ADR-002_state_persistence.md) OQ-004 / TASK-033） |
| 投入0件で終了した実行の連続回数 | 2回連続を異常とみなす | 投入対象が0件の実行（新着がない週）は正常だが、それが連続する場合はフィードの失効・評価の異常・閾値の設定ミスのいずれかが起きている可能性が高い。全件投入失敗は非0終了で検知できる（§5 Raindrop 行）が、**投入対象そのものが0件になる異常は終了コードに現れない**ため、副指標として定義する |
| RPO（目標復旧時点） | 重複排除の情報: 1週間（＝直前の実行時点）／**評価記録: 復旧不能** | 重複排除の情報については、失われても記事そのものは情報源に残っており再取得できるため、次回実行で自動回復する。**一方、評価記録（score・理由）は再取得できず、R-006 の検証母集団は復旧しない**（そのとき評価した score の記録が唯一の情報源であり、生存者バイアスの解消手段が失われる）。この非対称性を許容するかは TASK-040 で判断する |
| RTO（目標復旧時間） | 1週間（＝次回の定期実行まで） | 個人の学習用途であり、即時復旧の必要がない。障害時は次回実行で自動的に回復する（未投入分が新規として再処理される）。**評価に失敗したエントリは、失敗回数が上限（暫定3回 → TASK-053）に達するまでは次回実行で再評価されるため、一時的な障害からは自動回復する。上限に到達したエントリのみ処理済みとして扱われ、この経路では回復しない**（→ OQ-002 の結論） |
| MTTR | 定義しない | オンコール体制を持たない個人プロジェクトであり、復旧は運用者が気づいた時点で着手する |

**優先度:** Should
**ステータス:** draft

#### REQ-NF-004: 耐障害性

> 詳細な実装方針は `enterprise_checklist.md` の「耐障害性」セクション参照。

| 要件 | 内容 | 対象コンポーネント |
|---|---|---|
| 部分障害の分離 | 個別の情報源の取得失敗が、他の情報源の処理を停止させないこと | フィード取得処理 |
| 部分障害の分離 | 個別エントリの評価失敗が、他のエントリの処理を停止させないこと（REQ-F-010） | スコアリング処理 |
| 部分障害の分離 | 個別エントリの投入失敗が、他のエントリの投入を停止させないこと | 投入処理 |
| リトライ（実行内） | 評価に失敗した場合、規定回数再試行する（**暫定1回。回数は TASK-024 で確定する**）。再失敗時はスキップし、失敗の事実と失敗回数を記録する | スコアリング処理 |
| リトライ（実行をまたぐ） | 失敗回数が上限（暫定3回。→ TASK-053）に達していないエントリは、次回の実行で再評価する。上限到達後は処理済みとして扱う。**失敗回数は実行内の試行回数分だけ増加する**（上限は週数ではなく総試行回数を意味する） | 状態管理 |
| リトライの対象外 | **API 呼び出し自体の失敗**（ネットワーク障害・5xx・429・タイムアウト）は失敗回数に計上せず、次回の実行に持ち越す。外部の一時的な障害でエントリを恒久的に失わないため（→ OQ-002 の結論） | スコアリング処理・状態管理 |
| タイムアウト | 外部への全通信に明示的なタイムアウトを設定する | フィード取得・評価・投入 |
| データ保護 | 処理済み状態のファイルを実行間で永続化する（方式は [ADR-002](../04_decisions/ADR-002_state_persistence.md) で決定）。**状態が失われた結果として**重複投入が発生しうることを許容する。ただし許容するのは例外時に一度起きることであり、実行の失敗のたびに全損する方式は許容しない | 状態管理 |
| 状態を読めない場合の扱い | **状態の読み込みに失敗したときは、空の状態とみなして処理を継続してはならない。** 記事を1件も投入せずに実行を失敗させる（→ F-002 AC-018）。読めない状態を「記録なし」と解釈すると全件が新規とみなされ、**リモート障害のたびに全件が重複投入される**。これは上記の「例外時に一度」ではなく「構造的に毎回起こりうる」側にあたり、許容範囲外である | 状態管理 |
| 冗長化 | 行わない | 全体 |

**優先度:** Must
**ステータス:** draft
