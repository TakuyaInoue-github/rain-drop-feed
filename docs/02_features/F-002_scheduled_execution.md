## 1. ユーザーストーリー

```
As a   運用者,
I want 週に1回、自分が何も操作しなくても収集の一連の処理が実行されること,
So that 巡回を忘れた週や、多忙で手が回らなかった週があっても
        収集レイヤーへの供給が途切れず、下流の週次レビューが
        素材不足で停止することがなくなる.
```

---

## 2. 背景・動機

問題の根本原因は「収集が人間の能動的な巡回を前提にした設計になっている」ことにある
（要求定義 §3.4）。人間の意志力に依存する限り、途切れは再発する。

[F-001](F-001_triage_and_ingest.md) は手動実行でも成立する機能だが、それだけでは
「運用者が実行を思い出す」という人間依存が残り、R-001 の根本原因が解消されない。
本機能は実行の起動そのものを自動化することで、この最後の人間依存を取り除く。

**F-001 との分割根拠（Rule F-4）:** 本機能は F-001 に依存するが、逆は成立しない。
F-001 は F-002 なしに手動運用としてリリースでき、F-002 はその後に追加される増分として
独立に有効化・撤回できる（ワークフローを無効化すれば F-001 は手動運用として生き残る）。
この片方向の独立性により、Rule F-4 の統合トリガー（独立してリリースできない）には
該当しない。So that も F-001（選別の手作業がなくなる）とは明確に異なるため、
Rule F-2 が分割を支持する。

学習パイプライン全体（収集 → 週次レビュー → deep-inquiry → tech-learning-note）は
上流の供給が前提であり、供給の途切れは下流全体を停止させる。

**対応する要求:** R-001（収集レイヤーへの供給が人手を介さず継続すること）

## 3. 受け入れ基準 (Acceptance Criteria)

> cron 式の記法、ワークフロー定義の具体的な構造、リトライの実装は SPEC 層に委ねる。

### 正常系

- [ ] AC-001 `[正常系]` 定期実行が有効化されているとき、週1回（月曜 06:17 JST）に、運用者の操作なしで一連の処理が開始されること
- [ ] AC-002 `[正常系]` 定期実行が完了したとき、実行の成否が運用者から事後に確認できる形で残ること
- [ ] AC-003 `[正常系]` 運用者が手動で起動したとき、定期実行と同一の処理が実行されること
- [ ] AC-004 `[正常系]` 定期実行によって処理された結果が、次回の実行時に処理済みとして引き継がれること

### エラー系

- [ ] AC-010 `[エラー系]` 定期実行が異常終了したとき、失敗した事実が運用者から確認できる形で残ること
- [ ] AC-011 `[エラー系]` 定期実行が起動しなかった週があるとき、次回の定期実行で、その時点でフィードから取得できる未処理分が新規として処理されること（フィードの保持件数を超えて古くなったエントリは取得できない。取得可能な範囲を超える欠落の扱いは OQ-004 で判断する）
- [ ] AC-012 `[エラー系]` 実行に必要な秘匿情報が未設定のとき、処理を開始する前に失敗し、部分的な処理が行われないこと
- [ ] AC-013 `[エラー系]` 実行が投入の途中で例外により中断したとき、それまでに投入した記事が処理済みとして記録・永続化され、次回実行で再投入されないこと（プロセスが強制終了された場合は対象外。→ [ADR-002](../04_decisions/ADR-002_state_persistence.md) の受け入れたトレードオフ）
- [ ] AC-014 `[エラー系]` 処理済み記録の永続化に失敗したとき、その事実が運用者から確認できる形で残ること（静かに成功扱いにならないこと）
- [ ] AC-016 `[エラー系]` 状態の push が競合により拒否されたとき、既存の記録と自動的に統合された上で再試行され、いずれの実行の記録も失われないこと
- [ ] AC-017 `[エラー系]` push の再試行が規定回数すべて失敗したとき、実行が失敗として終了すること（静かに成功扱いにならないこと）
- [ ] AC-015 `[エラー系]` 定期実行が起動しなかった週があったことを、運用者が事後に判別できること（直前の実行からの経過期間が確認できること）

### 境界値

- [ ] AC-020 `[境界値]` 前回の実行から間隔が空いた（数週間実行されなかった）とき、その間に蓄積した新着記事が処理対象になること
- [ ] AC-021 `[境界値]` 定期実行と手動実行が同時に発生したとき、処理済み記録が破損せず、いずれの実行についても投入した記事が記録に残ること
- [ ] AC-022 `[境界値]` 想定上振れの入力量（13情報源・新規100件）で実行したとき、実行基盤のジョブ時間上限に達する前に完了すること

### 権限

- [ ] AC-030 `[権限]` 定期実行ジョブは、フィード定義・トリアージ基準・閾値を変更しないこと
- [ ] AC-031 `[権限]` 定期実行ジョブは、処理済み記録の削除・リセットを行わないこと
- [ ] AC-032 `[権限]` 秘匿情報は実行環境に注入された形でのみ参照され、実行ログ・履歴に出力されないこと
- [ ] AC-033 `[権限]` 定期実行ジョブは、状態専用ブランチにのみ書き込み、既定ブランチへは書き込まないこと

## 4. UXフロー概要

```
[ワークフローが有効・秘匿情報が設定済み]
  ↓
週1回のスケジュール到来（または運用者による手動起動）
  ├─ 起動しなかった → 供給が1週間停止。**起動しなかったジョブは実行履歴に
  │                   現れない**ため、次回実行時のサマリに出る「前回実行からの
  │                   経過期間」で事後に判別する（→ AC-015）。
  │                   手動起動するか次週の実行を待つ
  │                   （未処理分は持ち越されるが、フィードの保持件数を
  │                     超えた分は取得できない → AC-011 / OQ-004）
  └─ 起動した ↓
[実行環境の準備・秘匿情報の注入]
  ├─ 秘匿情報が未設定 → 処理開始前に失敗（何も投入しない）
  │                     → 運用者が設定を修正して手動起動
  └─ OK ↓
[F-001 の処理を実行]
  ├─ 異常終了 → 失敗として実行履歴に残る
  │             → 未処理エントリは記録されず次回に持ち越される
  └─ 正常終了 ↓
[処理済み記録を状態ブランチへ commit + push（実行末尾に1回）]
  ├─ push が競合で拒否
  │    → pull --rebase して行マージ → 再 push（最大3回）
  │    ├─ 成功 → 両実行の記録が保たれる（→ AC-016）
  │    └─ 3回とも失敗 → 非0終了（→ AC-017）
  │                      「投入済みだが未記録」が残り次回に重複投入
  │                      → 失敗の事実をサマリに残す（→ AC-014 / F-004 AC-015）
  └─ 成功 ↓
[完了。実行履歴に成否とサマリが残る]
```

## 5. スコープ

### In Scope

- 週1回（月曜 06:17 JST）の自動起動
- 運用者による手動起動の手段
- 実行の成否が事後に確認できること
- 実行間での処理済み記録の引き継ぎ
- 秘匿情報の実行環境への受け渡し

### Out of Scope

| 対象外の内容 | 理由・代替 |
|---|---|
| 取得・評価・投入の処理内容 | [F-001](F-001_triage_and_ingest.md) が担う。本機能は起動のみを担当する |
| 実行結果のサマリの内容 | [F-004](F-004_execution_summary.md) で対応する |
| 定期実行での dry-run 利用 | REQ-F-009 除外条件。[F-005](F-005_dry_run.md) AC-031 で担保する（本機能側では AC を持たず、二重管理を避ける） |
| 実行頻度の動的な変更 | REQ-F-011 除外条件。頻度の変更はワークフロー定義の手動編集で行う |
| 失敗時の外部通知（Slack 等） | 要求定義 §5 Out of Scope。実行履歴で確認する |
| 失敗した実行の自動リトライ | 週次バッチであり、次回実行で自動的に回復する（REQ-NF-003 の RTO 1週間） |
