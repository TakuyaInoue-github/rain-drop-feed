## 1. ユーザーストーリー

```
As a   運用者,
I want トリアージ基準・閾値・情報源の定義を変更したとき、収集レイヤーへ
       何も投入せずに選別結果だけを確認できること,
So that 変更が意図した効果を持つかを、収集レイヤーを汚染するリスクなしに
        試せるようになり、基準の調整を「本番に流して結果を見る」以外の
        方法で行える.
```

---

## 2. 背景・動機

トリアージ基準・閾値・情報源の重みは、いずれも運用者が手で調整する値である。
しかし調整の効果は実際に評価を走らせてみないと分からない。

dry-run がない場合、基準を変更した運用者は通常実行するしかない。その結果が
意図と異なっていた場合、**収集レイヤーには既に誤った選別結果が投入されており、
かつ処理済みとして記録されているため取り消せない**。誤投入は手動削除できるが
（要求定義 §5）、記録の側は残るため、同じ記事を修正後の基準で再評価することが
できなくなる。

この機能は、基準変更という運用行為を安全に行うための前提であり、
要件定義 REQ-NF-008 の「変更の安全な検証」もこの機能に依存している。

**対応する要求:** R-008（投入なしでの確認）

## 3. 受け入れ基準 (Acceptance Criteria)

> dry-run を指定するオプションの名称・記法は SPEC 層に委ねる（Rule B-4）。

### 正常系

- [ ] AC-001 `[正常系]` 運用者が dry-run を指定して実行したとき、収集レイヤーへの投入が一切行われないこと
- [ ] AC-002 `[正常系]` dry-run で実行したとき、各記事のスコアと投入可否の判定結果が、記事を識別できる形（URL またはタイトル）で、サマリと同じ出力先に出力されること
- [ ] AC-003 `[正常系]` dry-run で実行したとき、通常実行と同じ項目のサマリが出力され、投入に関する項目は実際の投入数ではなく**投入対象と判定された件数**として出力されること
- [ ] AC-004 `[正常系]` dry-run で実行したとき、処理済み記録が更新されないこと（同じ記事を繰り返し dry-run できること）
- [ ] AC-005 `[正常系]` dry-run の出力から、その実行が dry-run であったことが判別できること
- [ ] AC-006 `[正常系]` トリアージ基準または閾値を変更して dry-run を実行したとき、変更後の基準に基づく判定結果が得られること

### エラー系

- [ ] AC-010 `[エラー系]` dry-run 中に情報源の取得が失敗したとき、通常実行と同様にその情報源をスキップして処理が継続すること
- [ ] AC-011 `[エラー系]` dry-run 中に記事の評価が失敗したとき、通常実行と同様に再試行・スキップが行われ、実行全体が異常終了しないこと。**ただし失敗回数は記録されず、通常実行における再評価の打ち切り（[F-001](F-001_triage_and_ingest.md) AC-018 / AC-019）に影響しないこと**
- [ ] AC-012 `[エラー系]` dry-run 中に投入以外の処理でエラーが発生したとき、収集レイヤーへの投入は行われないままであること

### 境界値

- [ ] AC-020 `[境界値]` 新規エントリが 0 件のとき、dry-run が正常終了し、0 件であることが出力されること
- [ ] AC-021 `[境界値]` すべての記事が閾値未満のとき、投入対象 0 件として出力されること
- [ ] AC-022 `[境界値]` すべての記事が閾値以上のとき、全件が投入対象として出力され、かつ実際には投入されないこと
- [ ] AC-023 `[境界値]` 処理済み記録が空の状態で dry-run を実行したとき、取得した全記事が新規として評価されること
- [ ] AC-024 `[境界値]` 過去の実行で評価に失敗し、失敗回数が上限未満の記事があるとき、dry-run でも通常実行と同じ範囲が評価対象に含まれること（→ [F-001](F-001_triage_and_ingest.md) AC-018）

### 権限

- [ ] AC-030 `[権限]` 収集レイヤーの認証情報または投入先コレクション ID が未設定でも、dry-run は評価まで実行できること（LLM API キーは評価に必要なため対象外）
- [ ] AC-030a `[権限]` 収集レイヤーの認証情報が未設定の状態で dry-run を実行したとき、評価は実行された上で、通常実行では起動時に失敗する状態であることが出力から判別できること
- [ ] AC-031 `[権限]` 定期実行ジョブは dry-run では実行されないこと（通常実行として動作すること）
- [ ] AC-032 `[権限]` dry-run の出力に秘匿情報が含まれないこと

## 4. UXフロー概要

```
[運用者がトリアージ基準・閾値・情報源定義を変更した]
  ↓
運用者が dry-run を指定して実行する
  ↓
[秘匿情報の検証]
  ├─ 収集レイヤーの認証情報・コレクション ID が未設定
  │    → dry-run では投入しないため続行する。ただし
  │      「通常実行では起動時に失敗する状態」であることを出力に含める
  │      （→ AC-030a。dry-run で OK を確認した後に定期実行が
  │        失敗する落とし穴を防ぐ）
  ├─ LLM API キーが未設定 → 評価できないため中止する
  └─ ↓
[全情報源からフィードを取得]
  ├─ 一部失敗 → スキップして継続（通常実行と同じ）
  └─ ↓
[処理済み記録と突合して新規記事のみ抽出]
  ↓
[各記事を評価してスコアを得る]
  ├─ 評価失敗 → 再試行 → 再失敗ならスキップ（通常実行と同じ）
  └─ ↓
[補正後スコアと閾値を比較し、投入可否を判定]
  ↓
[投入は行わない。判定結果とサマリのみ出力]
  ↓
[処理済み記録も更新しない]
  ├─ 副作用: この実行で得た評価結果は F-003 の検証母集団に入らない
  │          （→ OQ-002。コストを払って得たスコアが蓄積されない）
  └─ ↓
運用者が結果を確認する
  ├─ 意図どおり → 変更を確定し、通常実行または次回の定期実行に委ねる
  │               （秘匿情報が未設定なら先に設定する → AC-030a）
  └─ 意図と異なる → 基準・閾値をさらに調整して dry-run をやり直す
                    （収集レイヤーは汚染されていない）
```

## 5. スコープ

### In Scope

- 収集レイヤーへの投入を行わない実行方法の提供
- 投入を行わないまま、評価結果と投入可否の判定を出力すること
- dry-run 実行時に処理済み記録を更新しないこと
- dry-run であることが出力から判別できること

### Out of Scope

| 対象外の内容 | 理由・代替 |
|---|---|
| 定期実行での dry-run 利用 | REQ-F-009 除外条件。定期実行は通常実行のみ。**本機能 AC-031 で担保する**（[F-002](F-002_scheduled_execution.md) 側は AC を持たない） |
| 処理済みと確定した記事を対象とした再評価 | dry-run の評価対象は通常実行と同じ（未評価の記事 + 失敗回数が上限未満の記事 → AC-024）。評価に成功した記事や失敗回数が上限に達した記事は対象外であり、過去分の再評価は蓄積された記録（[F-003](F-003_verify_triage_criteria.md)）で代替する |
| 投入内容のプレビュー（実際に付与されるタグの完全な再現） | 判定結果とスコアが確認できれば基準調整の目的は達せられる。要否は OQ-001 で判断する |
| dry-run 結果のファイル出力・差分比較 | 標準出力を運用者がリダイレクトすれば足りる |
| 評価をスキップした高速な確認モード | 評価結果こそが確認対象であり、スキップすると目的を果たさない |
