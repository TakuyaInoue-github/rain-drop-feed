## 1. ユーザーストーリー

```
As a   運用者,
I want 1回の実行について、取得数・新規数・投入数・スコア分布・情報源別の
       取得件数がまとまった形で出力されること,
So that 無人で動き続けるシステムが静かに壊れている状態
        （フィードURLの失効・投入0件の継続・評価の異常）に気づくことができ、
        供給が途切れていることを数週間後に発見する事態を避けられる.
```

---

## 2. 背景・動機

本システムは週1回無人で実行され、正常に動いている限り運用者は何も操作しない。
この性質は R-001 の目的そのものだが、同時に **「壊れても気づかない」というリスク**
を生む。

特に問題になるのは、プロセスとしては正常終了しているが供給が止まっている状態である。
たとえば情報源の URL が失効した場合、その情報源はスキップされて他の処理は継続し、
実行は成功として記録される。実際 2026-07-26 の疎通確認では 14 件中 1 件
（`blef-fr`）が HTTP 404 になっていた（TASK-027）。情報源別の取得件数が
可視化されていなければ、この種の静かな停止は検知できない。

外部への通知基盤は導入しない（要求定義 §5 Out of Scope）ため、**サマリが無人実行に
おける唯一の異常検知手段**となる。

**対応する要求:** R-007（実行結果の把握）

## 3. 受け入れ基準 (Acceptance Criteria)

> 出力の具体的なフォーマット・文言・桁揃えは SPEC 層に委ねる（Rule B-3 / B-4）。

### 正常系

- [ ] AC-001 `[正常系]` 実行が完了したとき、取得したエントリ数・新規エントリ数・投入数が出力されること
- [ ] AC-002 `[正常系]` 実行が完了したとき、スコアの分布が出力されること
- [ ] AC-003 `[正常系]` 実行が完了したとき、情報源ごとの取得件数が出力されること
- [ ] AC-003a `[正常系]` 情報源ごとの取得件数が、その情報源の直近の実行における取得件数と対比できる形で出力されること（取得が継続的に 0 件である情報源を、元から低頻度の情報源と区別できること）
- [ ] AC-004 `[正常系]` 実行が完了したとき、当該実行で発生した評価コストと評価件数が出力されること
- [ ] AC-004a `[正常系]` 1回の実行で評価する件数の上限に達したとき、持ち越された件数がサマリに出力されること
- [ ] AC-005 `[正常系]` サマリが、処理経過のログと混ざらずに単独で取り出せる形で出力されること（出力先の具体名は SPEC で定義する）
- [ ] AC-006 `[正常系]` 定期実行で出力されたサマリを、運用者が事後に参照できること
- [ ] AC-007 `[正常系]` 運用者が詳細ログを有効にして実行したとき、通常実行より詳細な処理経過が出力され、サマリの内容は変化しないこと
- [ ] AC-008 `[正常系]` 実行が完了したとき、直前の実行からの経過期間がサマリに出力されること（定期実行が起動しなかった週を事後に判別できること → [F-002](F-002_scheduled_execution.md) AC-015）

### エラー系

- [ ] AC-010 `[エラー系]` 取得に失敗した情報源があるとき、その情報源が失敗したものとしてサマリ上で識別できること
- [ ] AC-011 `[エラー系]` 評価に失敗した記事があるとき、その件数がサマリに含まれること
- [ ] AC-011a `[エラー系]` 評価の失敗回数が上限に達し、以降再評価されなくなった記事があるとき、その件数が他の評価失敗と区別できる形でサマリに含まれること（一時的な障害と恒久的な取りこぼしを区別する → [F-001](F-001_triage_and_ingest.md) AC-019）
- [ ] AC-012 `[エラー系]` 投入に失敗した記事があるとき、その件数がサマリに含まれること
- [ ] AC-013 `[エラー系]` 実行が処理途中の例外により終了したとき、または永続化の失敗により失敗として終了したとき、それまでに集計できた範囲がサマリとして出力されること（プロセスが強制終了される場合は対象外 → TASK-012）
- [ ] AC-014 `[エラー系]` すべての情報源の取得に失敗したとき、全情報源が失敗した事実がサマリで識別できること
- [ ] AC-015 `[エラー系]` 処理済み記録の永続化に失敗したとき、その事実と、次回実行で重複投入が発生しうる旨がサマリで識別できること
- [ ] AC-016 `[エラー系]` 投入対象が1件以上あったにもかかわらず全件失敗したとき、その事実がサマリで識別でき、かつ実行が失敗として終了すること（→ [F-001](F-001_triage_and_ingest.md) AC-014）

### 境界値

- [ ] AC-020 `[境界値]` 新規エントリが 0 件のとき、0 件であることが明示的に出力されること（出力が空にならないこと）
- [ ] AC-021 `[境界値]` 投入数が 0 件のとき、0 件であることが明示的に出力されること
- [ ] AC-022 `[境界値]` ある情報源の取得件数が 0 件のとき、その情報源が 0 件として出力されること（行が省略されないこと）
- [ ] AC-023 `[境界値]` 情報源の定義が 0 件のとき、その旨が出力されること
- [ ] AC-024 `[境界値]` 評価に成功した記事が 0 件のとき、スコア分布が空であることが判別できる形で出力されること
- [ ] AC-024a `[境界値]` 評価に成功した全記事のスコアが同一値であるとき、その事実がサマリ上で識別できること（分布が縮退している状態を、正常な分布と区別できること）

### 権限

- [ ] AC-030 `[権限]` サマリに秘匿情報（認証トークン・投入先コレクション ID）が含まれないこと
- [ ] AC-031 `[権限]` エラーメッセージに秘匿情報が含まれないこと
- [ ] AC-032 `[権限]` サマリの出力先が、運用者以外から参照可能な場所に置かれないこと

## 4. UXフロー概要

```
[F-001 の処理が進行]
  ↓
[各段階の結果を集計]
  ├─ 情報源ごとの取得件数（失敗した情報源を含む）
  ├─ 新規エントリ数
  ├─ 評価の成功・失敗件数、スコア分布、評価コスト
  └─ 投入の成功・失敗件数
  ↓
[実行の終了]
  ├─ 異常終了 → それまでに集計できた範囲を出力
  │              → 実行履歴に失敗として残る
  └─ 正常終了 ↓
[サマリを出力。処理ログとは混ざらない形にする]
  ↓
運用者がサマリを確認する
  ├─ 投入数が想定を下回る / 特定の情報源が 0 件（前回比で判別）
  │    → 情報源の URL 失効・閾値の見直しを検討
  ├─ 評価失敗が多い
  │    → 評価方式・プロンプトの見直しを検討
  ├─ 評価コストが想定を超える / 持ち越しが発生している
  │    → モデル指定・件数上限の見直しを検討
  ├─ スコア分布が縮退している（全件同一）
  │    → トリアージ基準の破損・モデル誤指定を疑う
  ├─ 記録の永続化に失敗している
  │    → 次回の重複投入に備える（→ TASK-033）
  ├─ 前回実行からの経過が2週間以上
  │    → 定期実行の不発火を疑う（→ F-002 AC-015）
  └─ 想定どおり → 何もしない
```

## 5. スコープ

### In Scope

- 1回の実行における取得数・新規数・投入数の出力
- スコア分布の出力
- 情報源ごとの取得件数の出力（失敗した情報源の識別を含む）
- 評価コストと評価件数の出力、および件数上限に達した場合の持ち越し件数の出力
- 直前の実行からの経過期間の出力（定期実行の不発火を事後に判別する手段）
- スコア分布の縮退（全件同一スコア）の識別
- 処理済み記録の永続化失敗の識別
- サマリと処理ログの分離（出力先の具体名は SPEC で定義する）
- 詳細ログの任意有効化

### Out of Scope

| 対象外の内容 | 理由・代替 |
|---|---|
| 外部サービスへの通知（Slack 等） | 要求定義 §5 Out of Scope。単一利用者であり実行履歴で確認できる。通知経路を増やすと秘匿情報の管理対象も増える |
| メトリクス収集基盤への送信 | 要件定義 REQ-NF-007。1回の実行で得られる指標をサマリとして出力すれば足りる |
| 複数実行にまたがる傾向分析・時系列グラフ | 長期の検証は蓄積された記録側（[F-003](F-003_verify_triage_criteria.md)）で行う。ただし**直近実行との対比（AC-003a）と経過期間（AC-008）は本機能が担う**。REQ-F-008 の「供給の停止に気づける形」は単発スナップショットでは満たせないため |
| 異常の自動判定・アラート閾値の設定 | 何を異常とみなすかの基準の大半は実測前に定まらないため、運用者が目視で判断する。ただし**分布の縮退（全件同一スコア）は実測前でも定義できる異常**であり、AC-024a で識別対象とする |
| 機械可読形式（`--json` 等）での出力 | 要否を TASK-010 で判断する。現時点では人間が読む前提 |
