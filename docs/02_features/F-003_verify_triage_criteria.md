## 1. ユーザーストーリー

```
As a   運用者,
I want 閾値未満で投入されなかった記事についても、スコアと評価理由が
       残っていること,
So that 「閾値を1つ下げていれば何が拾えていたか」を実データで確認でき、
        閾値やトリアージ基準の調整を勘ではなく観測に基づいて行える.
```

---

## 2. 背景・動機

投入したエントリのみを記録すると、**閾値を下げていれば拾えていた記事が観測できなくなる**
（生存者バイアス）。この状態では「閾値 5 が妥当か」を検証する手段がなく、調整が
運用者の体感に依存し続ける。

`.ref/spec.md` は閾値 `5` を初期値としているが、この値には実測の裏付けがない。
`docs/CLAUDE.md` でも「閾値以下のエントリも score 付きで state に記録する。これは
後から閾値を検証するための実測データであり、省略すると AC-5 が満たせなくなる」と
明示されている。

本機能は新しい出力や画面を提供せず、**記録が満たすべき網羅性の制約そのものが提供価値**
である点が他の F と異なる。

**F-001 との責務境界（Rule F-2 による分割根拠）:**
[F-001](F-001_triage_and_ingest.md) は「投入すべきものを投入する」ことに責任を持ち、
記録は重複排除の手段として行う。本機能は「投入しなかったものを含む全件が、閾値検証に
耐える粒度で残っている」ことに責任を持つ。**前者を満たしても後者は自動的には満たされない**
（投入分のみを記録する実装でも F-001 のゴールは成立し、AC-006 を除くすべての AC が通る）。
この非従属性により、両者は別の F とする。

**対応する要求:** R-006（選別基準の事後検証）

## 3. 受け入れ基準 (Acceptance Criteria)

> 記録の格納形式・カラム構成・ファイルレイアウトは SPEC 層に委ねる（Rule B-4）。

### 正常系

- [ ] AC-001 `[正常系]` 補正後スコアが閾値未満で投入されなかった記事について、評価スコアが記録されていること
- [ ] AC-002 `[正常系]` 投入されなかった記事について、評価理由が記録されていること
- [ ] AC-002a `[正常系]` 投入されなかった記事について、評価時に得られた提案タグが記録されていること
- [ ] AC-003 `[正常系]` 記録された各記事から、投入されたものと投入されなかったものが区別できること（記録の有無自体は [F-001](F-001_triage_and_ingest.md) AC-006 が担保する。本 AC は区別可能性に責任を持つ）
- [ ] AC-004 `[正常系]` 記録された各記事から、どの情報源に由来するかが判別できること
- [ ] AC-005 `[正常系]` 実行を重ねたとき、過去の実行で記録された評価結果が失われずに蓄積されること（**記録そのものが全損した場合の復旧は保証しない。** 要件定義 REQ-NF-003 の RPO「評価記録: 復旧不能」を許容する → OQ-003 の結論）
- [ ] AC-006 `[正常系]` 蓄積された記録から、スコアの分布と、任意の閾値を適用した場合の投入対象件数を運用者が算出できること
- [ ] AC-006a `[正常系]` 蓄積された記録から、任意の閾値を適用したときに新たに投入対象となる**個々の記事**（URL・タイトル・スコア・評価理由）を運用者が特定できること

### エラー系

- [ ] AC-010 `[エラー系]` 評価に失敗した記事が、スコアを持つ記事と混同されない形で記録され、スコア分布の算出から除外できること
- [ ] AC-013 `[エラー系]` 同一の記事について複数の評価結果が記録されている場合（失敗による再試行を経て成功した場合等）、スコア分布の算出において**その記事の最新の評価結果のみが 1 件として数えられ、過去の評価結果は数えられないこと**（「最新」の判定規則は [ADR-005](../04_decisions/ADR-005_state_file_format.md) OQ-001 による）
- [ ] AC-011 `[エラー系]` 投入に失敗した記事について、投入されなかったことが判別できる形で記録されること
- [ ] AC-012 `[エラー系]` 記録の書き込みに失敗したとき、その事実が運用者から確認できる形で残ること

### 境界値

- [ ] AC-020 `[境界値]` スコアが値域の下端または上端の記事も、他と同様に記録されること
- [ ] AC-021 `[境界値]` 新着記事が 0 件の実行では、記録が追加されないこと（既存の記録が破損しないこと）
- [ ] AC-022 `[境界値]` 記録が 1 件も存在しない状態（初回実行）でも、処理が正常に開始できること
- [ ] AC-023 `[境界値]` dry-run による実行で評価された記事は、記録に追加されないこと（記録の対象は投入判定を伴う通常実行に限られること → [F-005](F-005_dry_run.md) AC-004）

### 権限

- [ ] AC-030 `[権限]` 記録には公開記事のメタデータとスコアのみが含まれ、秘匿情報が含まれないこと
- [ ] AC-031 `[権限]` 定期実行ジョブは記録の追記のみを行い、削除・リセットを行わないこと
- [ ] AC-032 `[権限]` 記録の削除・リセットは運用者の明示的な操作によってのみ行えること

## 4. UXフロー概要

> 本機能は運用者が随時操作するものではなく、記録の蓄積と事後参照の2つの局面を持つ。

```
【蓄積の局面（実行のたびに自動で行われる）】

[F-001 が各記事の評価を完了]
  ↓
[投入可否を判定]
  ├─ 閾値以上 → 投入 → 「投入した」として記録
  ├─ 閾値未満 → 投入しない → 「投入しなかった」としてスコア・理由付きで記録
  └─ 評価失敗 → 「評価に失敗した」として記録（スコアなし）
  ↓
[記録の書き込み]
  ├─ 失敗 → その事実が実行結果に残る
  │         → 次回実行時に重複投入が発生しうる（許容する異常）
  └─ 成功 ↓
[蓄積完了]

【参照の局面（運用者が閾値を見直したいとき）】

運用者が蓄積された記録を参照する
  ↓
[スコア分布を確認し、任意の閾値での投入対象件数を算出]
  ├─ 記録が不足（期間が短い） → 判断を保留し、蓄積を待つ
  └─ 十分 ↓
[閾値・トリアージ基準の調整を判断]
  ↓
[F-005 の dry-run で変更の影響を確認してから反映]
```

## 5. スコープ

### In Scope

- 投入しなかった記事のスコア・評価理由・提案タグの記録
- 投入した記事との区別が可能な形での記録
- 実行をまたいだ評価結果の蓄積（過去分が失われないこと）
- 評価に失敗した記事の、失敗の事実の記録
- 蓄積された記録からスコア分布を算出できる状態の維持

### Out of Scope

| 対象外の内容 | 理由・代替 |
|---|---|
| 記録の可視化 UI・グラフ描画 | 単一利用者であり、記録を直接参照すれば足りる。分析は都度のクエリで行う |
| 閾値・重みの自動チューニング | 要求定義 §5 Out of Scope。本機能はその判断材料を供給するに留まる |
| 重複排除の観点 | [F-001](F-001_triage_and_ingest.md) が担う。本機能は同じ記録に対し「検証に耐える網羅性」の制約のみを規定する |
| 記録の性能特性（蓄積量の増加に伴う突合の劣化） | 重複排除の突合方式の問題であり [F-001](F-001_triage_and_ingest.md) / SPEC 層が担う。本機能のゴール（網羅性）とは別軸 |
| 記録の定期的な削除・アーカイブ | 保持期間は無期限（要件定義 §6）。年間 5,000 件規模で容量上の問題が生じない |
| 投入済み記事の Raindrop 側での評価（`#digest-candidate` 昇格）の取り込み | 要求定義 §5 Out of Scope（双方向同期を行わない）。昇格率の測定は運用者が手動で突合する |
