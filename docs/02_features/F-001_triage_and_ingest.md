## 1. ユーザーストーリー

```
As a   運用者,
I want 定義した情報源の新着記事が、学習価値の基準で選別された上で
       収集レイヤーへ投入されること,
So that 13 件の情報源を個別に巡回して告知記事と設計解説記事を
        読み分ける作業がなくなり、週次レビューでは選別済みの候補だけを
        見れば済む状態になる.
```

---

## 2. 背景・動機

公式ベンダーブログは告知系記事と設計解説系記事を同一フィードで配信しており、
フィードを購読するだけでは選別できない（要求定義 §1）。選別を人間の読解に委ねる限り、
購読する情報源を増やすほど選別コストが線形に増え、「情報源を増やす」という改善策
そのものが取れなくなる（R-003）。

この機能がないと、運用者は毎週 13 件の情報源を個別に開き、各記事のタイトルと要約を
読んで投入可否を判断し続けることになる。これは現状の運用そのものであり、
§3.4 の根本原因（収集が人間の能動的な巡回を前提にした設計になっている）が
解消されない。

あわせて、同じ記事を繰り返し投入しないこと（R-002）もこの機能が担う。定期実行を
前提とする以上、実行のたびに重複が増えるようでは収集レイヤーが汚染され、
レビューの対象として使い物にならなくなる。

**対応する要求:** R-001（供給の継続）、R-002（重複排除）、R-003（低価値記事の除外）、
R-004（高価値記事の識別）、R-005（情報源ごとの傾向反映）

## 3. 受け入れ基準 (Acceptance Criteria)

> エラーメッセージの具体的な文言、リトライ回数・待機時間の具体値、
> タグの命名規則の詳細は SPEC 層に委ねる（Rule B-3 / B-4）。

### 正常系

- [ ] AC-001 `[正常系]` 情報源が定義済みで未処理の新着記事があるとき、実行すると、補正後スコアが閾値以上の記事だけが収集レイヤーの指定コレクションに投入されること
- [ ] AC-002 `[正常系]` 記事が投入されるとき、自動投入を示すタグとスコア帯を示すタグが付与されていること
- [ ] AC-002b `[正常系]` 記事が投入されるとき、その情報源に定義されたタグが付与されていること
- [ ] AC-002c `[正常系]` 記事が投入されるとき、評価時に得られた提案タグが付与されていること
- [ ] AC-003 `[正常系]` 補正後スコアが高評価帯にある記事が投入されるとき、レビュー時に識別できるタグが追加で付与されていること
- [ ] AC-004 `[正常系]` 一度処理した記事があるとき、同一のフィード定義で再実行すると、その記事は再度投入されないこと（投入数が 0 件になること）
- [ ] AC-005 `[正常系]` 情報源に重みが定義されているとき、投入可否の判定には評価スコアに重みを加算した値が用いられること
- [ ] AC-006 `[正常系]` 実行が完了したとき、当該実行で評価を試みた記事について、投入したものと投入しなかったものの両方が処理済みとして記録されていること（上限超過により評価しなかった記事は対象外 → AC-025。記録の内容と検証可能性は → [F-003](F-003_verify_triage_criteria.md)）
- [ ] AC-007 `[正常系]` 情報源からエントリを取得したとき、各エントリの URL・タイトル・要約・公開日時・情報源名が後続処理で利用できる形で得られていること

### エラー系

- [ ] AC-010 `[エラー系]` 1件の記事の評価に失敗したとき、規定回数の再試行の後にその記事がスキップされ、残りの記事の処理が継続し、実行全体が異常終了しないこと
- [ ] AC-011 `[エラー系]` 1つの情報源の取得に失敗したとき、その情報源がスキップされ、他の情報源の処理が継続すること
- [ ] AC-012 `[エラー系]` 1件の記事の投入に失敗したとき、他の記事の投入が継続すること
- [ ] AC-013 `[エラー系]` 情報源が応答しないとき、規定時間で打ち切られ、当該情報源が取得失敗として扱われて（→ AC-011）実行全体が停止しないこと
- [ ] AC-014 `[エラー系]` 投入対象が1件以上あったにもかかわらず収集レイヤーへの投入が全件失敗したとき、実行が失敗として終了し、実行履歴上で異常と判別できること（投入対象が 0 件の場合は正常終了すること）
- [ ] AC-015 `[エラー系]` 評価に失敗してスキップされた記事について、失敗した事実と失敗回数が記録されること（スコアは記録されない）。**失敗回数は当該実行内で試行した回数分だけ増加すること**（＝「上限」は週数ではなく総試行回数を意味する）
- [ ] AC-015a `[エラー系]` API 呼び出し自体の失敗（ネットワーク障害・サーバーエラー・レート制限・タイムアウト）により評価できなかった記事について、失敗回数が増加せず、次回の実行で再評価の対象に含まれること（外部の一時的な障害で記事を恒久的に失わないこと）
- [ ] AC-018 `[エラー系]` 前回の実行で評価に失敗し、失敗回数が上限に達していない記事があるとき、次回の実行で再評価の対象に含まれること
- [ ] AC-018a `[エラー系]` 過去に評価に失敗した記事が再評価で成功したとき、その記事が以降の実行で再評価の対象に含まれなくなり、スコアと評価理由が記録に反映されること
- [ ] AC-019 `[エラー系]` 評価の失敗回数が上限に達した記事は、以降の実行で再評価されないこと
- [ ] AC-016 `[エラー系]` 評価または投入の外部通信が応答しないとき、規定時間で打ち切られ、当該記事がスキップされて残りの処理が継続すること
- [ ] AC-017 `[エラー系]` 収集レイヤーがレート制限を理由に投入を拒否したとき、その理由が他の投入失敗と区別できる形で示されること
- [ ] AC-017a `[エラー系]` 定義された情報源が1件以上あり、その**全件**の取得に失敗したとき、実行が失敗として終了すること（供給が完全に途切れた事実を、運用者がサマリを見る前に検知できること → [F-004](F-004_execution_summary.md) AC-014）

### 境界値

- [ ] AC-020 `[境界値]` 補正後スコアが閾値ちょうどのとき、その記事は投入されること
- [ ] AC-021 `[境界値]` 補正後スコアが閾値の1つ下のとき、その記事は投入されないこと
- [ ] AC-022 `[境界値]` 新着記事が 0 件のとき、投入を行わずに正常終了すること
- [ ] AC-023 `[境界値]` 記事の要約が空または欠落しているとき、タイトルのみで評価が行われ、処理が停止しないこと
- [ ] AC-023a `[境界値]` 記事のタイトルと要約の**両方**が空または欠落しているとき、当該記事は評価されずスキップされ、**評価失敗として記録されないこと**（評価する材料がないため。失敗として記録すると、材料がないだけの記事が再評価の対象になり続ける → [SPEC-003](../03_specs/SPEC-003_entry_evaluation.md) §5.2）
- [ ] AC-024 `[境界値]` 情報源の定義が 0 件のとき、その旨が示されて正常終了すること（異常終了しないこと）
- [ ] AC-025 `[境界値]` 1回の実行で評価する記事が上限件数に達したとき、超過分は処理済みとして記録されず、次回の実行に持ち越されること
- [ ] AC-025a `[境界値]` 再評価対象の記事と新規記事の合計が上限件数を超えるとき、**新規記事が優先して評価され**、再評価対象の超過分が次回に持ち越されること（恒久的に失敗する記事が上限枠を占有して新規の供給を止めないこと → R-001）
- [ ] AC-026 `[境界値]` エントリに公開日時が欠落しているとき、処理が停止せず、当該エントリが評価対象に含まれること
- [ ] AC-027 `[境界値]` 評価が提案タグを返さなかった（空だった）とき、他のタグのみが付与されて投入が成功すること
- [ ] AC-027a `[境界値]` 評価が返した提案タグの**一部だけ**が不正なとき（配列でない要素・文字列でない要素が混じるとき）、不正な要素のみが除外され、**残りのタグは採用されて投入が成功すること**（1要素の不正で提案タグ全体を捨てない）
- [ ] AC-028 `[境界値]` 情報源にタグが定義されていないとき、他のタグのみが付与されて投入が成功すること
- [ ] AC-029 `[境界値]` 評価が想定範囲外のスコアを返したとき、そのスコアが投入判定にそのまま用いられず、当該記事が評価失敗として扱われること

### 権限

- [ ] AC-030 `[権限]` 通常実行において必須の秘匿情報（収集レイヤーの認証情報・LLM API キー）が未設定のとき、フィード取得や評価を開始する前に実行が中止され、部分的な処理が行われないこと（dry-run 時の扱いは [F-005](F-005_dry_run.md) AC-030 による）
- [ ] AC-030a `[権限]` フィード定義（`feeds.yaml`）またはトリアージ基準（`profile.md`）が**存在しない・読み込めない・構造が不正**なとき、フィード取得や評価を開始する前に失敗し、部分的な処理が行われないこと。**空の情報源リストや基準なしで続行してはならない**（基準なしで評価すると全件のスコアが無意味になる）
- [ ] AC-031 `[権限]` 収集レイヤーの認証情報が無効なとき、投入が失敗したことが判別できる形で示され、認証情報そのものはログに出力されないこと
- [ ] AC-032 `[権限]` 通常実行において投入先コレクションの ID が未設定のとき、実行開始時に検知され、既定のコレクションへ投入されないこと（dry-run 時の扱いは [F-005](F-005_dry_run.md) による）
- [ ] AC-033 `[権限]` LLM API キーが無効なとき、評価が失敗したことが判別できる形で示され、API キーそのものはログ・サマリ・エラーメッセージに出力されないこと

## 4. UXフロー概要

```
[情報源が定義済み・認証情報が設定済み]
  ↓
運用者または定期実行ジョブが実行を開始する
  ↓
[秘匿情報・投入先の検証（収集レイヤーの認証情報・LLM API キー・コレクション ID）]
  ├─ 未設定・不正 → 実行を中止（何も投入しない）→ 運用者が設定を修正して再実行
  └─ OK ↓
[全情報源からフィードを取得]
  ├─ 一部の情報源が失敗 → 警告として記録し、他の情報源を継続
  ├─ 応答なし → 規定時間で打ち切り、当該情報源をスキップ
  └─ ↓
[処理済み記録と突合して新規記事のみ抽出]
  ├─ 新規 0 件 → 投入せず正常終了（結果は F-004 のサマリで可視化）
  └─ ↓
[評価件数の上限と突合]
  ├─ 上限超過 → 超過分は評価せず、記録もせず次回に持ち越す（→ AC-025）
  └─ ↓
[各記事を評価してスコア・理由・提案タグを得る]
  ├─ 評価失敗（API 障害・応答の意味的不正・範囲外スコア）
  │    → 再試行 → 再失敗なら当該記事をスキップして記録、次の記事へ
  └─ ↓
[スコアに情報源の重みを加算し、閾値と比較]
  ├─ 閾値未満 → 投入しない（評価結果は記録する → F-003）
  └─ 閾値以上 ↓
[収集レイヤーへ投入し、タグを付与]
  ├─ 投入失敗 → 記録して次の記事へ（実行は継続）
  └─ 成功 ↓
[投入の有無にかかわらず全件を処理済みとして記録]
  ↓
[完了。結果はサマリとして出力される → F-004]
```

## 5. スコープ

### In Scope

- 定義された全情報源からのフィード取得と、エントリのメタデータ（URL・タイトル・要約・公開日時・情報源名）の抽出
- 処理済み記録との突合による新規エントリの抽出と、投入の有無によらない全件の記録
- トリアージ基準に照らした各エントリの評価（スコア・理由・提案タグ）
- 情報源の重みによるスコア補正と、閾値に基づく投入可否の判定
- 収集レイヤーの指定コレクションへの投入とタグ付与
- 個別の失敗（情報源・評価・投入）を分離して処理を継続すること

### Out of Scope

| 対象外の内容 | 理由・代替 |
|---|---|
| 定期実行のスケジューリング・手動起動 | [F-002](F-002_scheduled_execution.md) で対応する |
| 閾値未満エントリの評価結果を用いた事後検証 | 記録自体は本機能が行うが、検証の観点は [F-003](F-003_verify_triage_criteria.md) で扱う |
| 実行結果のサマリ出力 | [F-004](F-004_execution_summary.md) で対応する |
| 投入を行わない確認実行（dry-run） | [F-005](F-005_dry_run.md) で対応する |
| 記事本文の取得・要約 | 要求定義 §5 Out of Scope。タイトルと要約のみで選別が成立するかを先に検証する |
| 投入済みエントリの更新・削除・再スコアリング | 要求定義 §5 Out of Scope。誤投入は収集レイヤー上で手動削除する |
| 重み・閾値の自動チューニング | 要求定義 §5 Out of Scope。判断根拠となる実測データの蓄積が先 |
| 複数情報源から取得した同一記事の名寄せ | URL が異なれば別エントリとして扱う（REQ-F-002 除外条件）。要否は TASK-009 で判断する |
