## 1. 概要

フィード定義ファイル（`feeds.yaml`）を読み込み、定義された全情報源から HTTP で
フィードを取得し、RSS/Atom をパースして各エントリの URL・タイトル・要約・公開日時・
情報源名を抽出する。抽出結果は **決定的な順序**（§4 出力）で後続処理へ渡す。

取得は `httpx`、パースは `feedparser`（**バイト列を渡す**）で行う。
`feedparser.parse(url)` の URL モードは使わない（→ [ADR-004](../04_decisions/ADR-004_implementation_stack.md) 補遺B）。

重複排除・評価・投入は本仕様の対象外（それぞれ SPEC-002 / SPEC-003 / SPEC-004）。
本仕様は **状態を参照しない** — 取得したエントリを無条件に全件返し、既知/新規の判定は
SPEC-002 の `select_evaluation_targets` が行う。

> **粒度についての注記（Rule S-1 / S-3）:** フロー定義表は 20 行あり Rule S-1 の
> 目安（15行）を超える。**それでも分割しない。** 分割候補は「① `feeds.yaml` の
> ロード」と「② 1情報源の取得・パース」だが、Rule S-2 の分割トリガー（独立した
> 状態機械）に該当しない — 本仕様は §6 のとおり状態を一切持たず、①②とも同一の
> `Source` / `Entry` を扱う純粋な変換である。加えて ① を切り出すと 4 行（#1・#2・
> #12・#13）となり Rule S-3（3行以下は統合）に近い。**行数が多いのは例外系が 12 行
> あるためであり、独立した振る舞いが混在しているためではない。**

## 2. 前提条件 (Preconditions)

| 前提条件 | 満たされない場合の挙動 |
|---|---|
| フィード定義ファイル（`feeds.yaml`）が既定のパスに存在すること | 実行を中止し、終了コード `CONFIG_ERROR`（2）で終了する（→ フロー #12） |
| フィード定義ファイルが YAML として解釈可能であること | 同上（→ フロー #13） |
| 起動時の秘匿情報の検証が完了していること（F-001 AC-030 / AC-032） | 本仕様の処理は開始されない。検証は SPEC-005（CLI）が本仕様より前に行う |
| 各情報源への HTTPS 到達性があること | 当該情報源のみ取得失敗として扱い、他の情報源の処理を継続する（→ フロー #14〜18 / F-001 AC-011） |

> **注記:** 「情報源が 1 件以上定義されていること」は前提条件に**しない**。
> 0 件は正常系として扱い、その旨を示して正常終了する（→ フロー #3 / F-001 AC-024）。

## 3. フロー定義

> 本仕様は無人 CLI のバッチ処理であり、対話的な画面を持たない。
> 「ユーザーへの表示 / レスポンス」列は **標準エラー出力への出力内容**、および
> 呼び出し元（`pipeline`）への戻り値を指す。サマリ（標準出力）の書式は SPEC-006 が定める。
>
> **終了コードは新設しない。** 参照する値は `src/feed_triage/contract/exit_codes.py` の
> 既存定義であり、正典は SPEC-005（CLI）が持つ。

| # | フロー種別 | 条件 / トリガー | アクター | 操作・イベント | システムの処理 | ユーザーへの表示 / レスポンス |
|---|---|---|---|---|---|---|
| 1 | 主系 | 実行開始時 | システム | フィード定義の読み込み | `feeds.yaml` をパースし `Source` の列を構築する。**YAML 上の記載順を保持する**（→ §4 出力の順序規定） | （標準エラー）`情報源を読み込みました: {n}件` |
| 2 | 主系 | フィード定義の読み込み完了後 | システム | 情報源ごとの取得 | 各 `Source` の URL へ `httpx` で GET する。**情報源の定義順に、1件ずつ逐次実行する**（REQ-NF-002「単一プロセス・逐次処理」） | （標準エラー）`取得中: {source_name}` |
| 3 | 代替系 | IF 情報源の定義が 0 件 | システム | フィード定義の読み込み | 取得も抽出も行わず、0 件のサマリを出力して**正常終了する**（終了コード `OK`）。`SourceOutcome` は**空リスト**を返す（全件失敗との区別 → §4 出力） | （標準エラー）`情報源が定義されていません`（サマリ本体は SPEC-006 → F-004 AC-023） |
| 4 | 主系 | HTTP 200 を受信 | システム | フィードのパース | レスポンスの**バイト列**を `feedparser.parse()` に渡す。URL モードは使わない（→ [ADR-004](../04_decisions/ADR-004_implementation_stack.md) 補遺B） | - |
| 5 | 主系 | パース完了 | システム | エントリの抽出 | 各エントリから URL・タイトル・要約・公開日時を取り出し、`source_name` を付与して `Entry` を構築する。**フィード内の掲載順を保持する**（→ §4） | - |
| 6 | 主系 | 全情報源の処理完了 | システム | 結果の返却 | 全 `Entry` を情報源の定義順に連結して返す。あわせて情報源ごとの取得件数・失敗理由（`SourceOutcome`）を返す | （標準エラー）`取得完了: {合計件数}件 / {成功情報源数}情報源` |
| 7 | 代替系 | IF エントリが 0 件のフィードを取得した | システム | エントリの抽出 | 当該情報源を**成功・0件**として記録する（失敗と区別する → F-004 AC-022） | （標準エラー）`{source_name}: 0件` |
| 8 | 代替系 | IF エントリの要約が空または欠落 | システム | エントリの抽出 | 要約を空文字として `Entry` を構築し、**評価対象から除外しない**（→ F-001 AC-023。タイトルのみでの評価は SPEC-003 が担う） | （標準エラー・詳細ログ時のみ）`{url}: 要約がありません` |
| 9 | 代替系 | IF エントリの公開日時が欠落または解釈不能 | システム | エントリの抽出 | `published_at` を `None` として `Entry` を構築し、**評価対象から除外しない**（→ F-001 AC-026） | （標準エラー・詳細ログ時のみ）`{url}: 公開日時を解釈できません` |
| 10 | 代替系 | IF エントリのタイトルが空または欠落 | システム | エントリの抽出 | タイトルを空文字として `Entry` を構築し、除外しない（→ §5） | （標準エラー・詳細ログ時のみ）`{url}: タイトルがありません` |
| 11 | 代替系 | WHERE dry-run が指定されている | 運用者 | 実行 | **通常実行と完全に同一の取得・抽出を行う**（dry-run による分岐を持たない → F-005 AC-010） | 通常実行と同じ |
| 12 | 例外系 | IF フィード定義ファイルが存在しない | システム | フィード定義の読み込み | 実行を中止する（終了コード `CONFIG_ERROR`）。空の情報源リストにフォールバックしない（全情報源の静かな消失を「0件」と誤って正常終了させないため）。**この振る舞いに対応する AC が F にない → OQ-008** | （標準エラー）`フィード定義が見つかりません: {path}` |
| 13 | 例外系 | IF フィード定義が YAML として解釈できない、または `sources` キーを欠く | システム | フィード定義の読み込み | 同上（終了コード `CONFIG_ERROR`）。**同じく OQ-008** | （標準エラー）`フィード定義を解釈できません: {path} ({理由})` |
| 14 | 例外系 | WHEN HTTP が 4xx / 5xx を返す | システム | 情報源ごとの取得 | 当該情報源を**取得失敗**として記録し、次の情報源へ進む。リトライしない（→ §7「リトライ方針」） | （標準エラー）`{source_name} の取得に失敗しました: HTTP {status}。この情報源をスキップします` |
| 15 | 例外系 | WHILE 情報源が応答しない（タイムアウト 30 秒） | システム | 情報源ごとの取得 | 30 秒で打ち切り、取得失敗として記録して次の情報源へ進む（→ F-001 AC-013 → AC-011）。実行全体は停止しない | （標準エラー）`{source_name} の取得がタイムアウトしました（30秒）。この情報源をスキップします` |
| 16 | 例外系 | WHEN 接続・TLS・DNS のエラーが発生 | システム | 情報源ごとの取得 | 取得失敗として記録し、次の情報源へ進む。**証明書検証を無効化しない**（REQ-NF-006） | （標準エラー）`{source_name} に接続できません: {理由}。この情報源をスキップします` |
| 17 | 例外系 | IF レスポンスサイズが上限を超過 | システム | 情報源ごとの取得 | 受信を打ち切り、当該情報源を取得失敗として記録して次へ進む。**部分的に受信したバイト列をパースしない**（途中で切れた XML から不完全なエントリを作らないため） | （標準エラー）`{source_name} の応答が上限（{上限}）を超えました。この情報源をスキップします` ※上限値は OQ-001 |
| 18 | 例外系 | IF 取得したバイト列が RSS/Atom としてパースできない | システム | フィードのパース | 当該情報源を取得失敗として記録し、次の情報源へ進む。`feedparser` の `bozo` フラグが立ってもエントリが 1 件以上得られる場合は**成功として扱う**（→ §5） | （標準エラー）`{source_name} のフィードを解釈できません: {理由}。この情報源をスキップします` |
| 19 | 例外系 | IF エントリの URL が空・欠落・`http(s)` 以外のスキーム | システム | エントリの抽出 | **当該エントリのみ**を除外し、同一フィードの他のエントリの処理を継続する。URL は一意性のキーであり（REQ-F-002）、欠くと重複排除が成立しないため | （標準エラー）`{source_name}: URL のないエントリを {n}件 無視しました` |
| 20 | 例外系 | WHEN すべての情報源の取得に失敗 | システム | 全情報源の処理完了 | エントリ 0 件として後続処理へ進む（**中断しない**）。全件失敗の事実はサマリで識別できる（→ F-004 AC-014）。終了コードは本仕様では決めない（→ SPEC-005 / OQ-004） | （標準エラー）`すべての情報源（{n}件）の取得に失敗しました` |

> - [x] **権限違反アクセス** — フロー #14 と同じ。本システムは認証機構を持たず（REQ-NF-005）、取得元の HTTP ステータスに委ねる
> - [x] **必須項目未入力** — フロー #19（エントリの `url`）／フロー #13（`feeds.yaml` の `sources` キー）。情報源側の必須項目欠落は §5 の既定値で補完する
> - [x] **最大値・最小値超過** — フロー #17（レスポンスサイズ上限 → OQ-001）。要約長の切り詰めは本仕様の対象外（→ OQ-002 / TASK-029）
> - [x] **空文字・NULL入力** — フロー #8 / #9 / #10（要約・公開日時・タイトル）とフロー #19（URL）。前3者は補完して継続し、URL のみ除外する
> - [x] **外部システムの障害** — フロー #14 / #16 / #18（HTTP エラー・接続失敗・パース不能）
> - [x] **タイムアウト** — フロー #15（1情報源あたり 30 秒 → REQ-NF-001）
> - [x] **同時操作・競合** — **対象なし。** 本仕様は状態を読み書きせず（§6）、取得は読み取り専用の GET のみであるため、競合しうる共有リソースが存在しない。実行の競合は状態の永続化で生じ、SPEC-002 フロー #17 / #18 が扱う
> - [x] **対象リソースが存在しない** — フロー #12（`feeds.yaml`）／フロー #14 の 404（`blef-fr` で実際に発生した経路 → TASK-027）
> - [x] **対象リソースが削除済み** — フロー #14 の 404 / 410 と同じ扱い。情報源側でフィードの提供が終了した場合、取得失敗が継続する。**継続的な 0 件の検知は本仕様では行わない**（→ F-004 AC-003a / TASK-048）

## 4. 入出力定義

### 入力

#### (a) フィード定義ファイル（`feeds.yaml`）の `sources[]` の1要素

| 項目名 | 型 | 必須 | 制約 | NULL・空文字の扱い | 備考 |
|---|---|---|---|---|---|
| `name` | string | Yes | 情報源の識別子。**定義内で一意であること** | **実行を中止する**（`CONFIG_ERROR` → OQ-008）。エントリの `source_name` になり、重みとタグの引き当てキーでもあるため補完できない | `Entry.source_name` に転記する（F-003 AC-004 / F-004 AC-003） |
| `url` | string | Yes | `https://` で始まること | **実行を中止する**（`CONFIG_ERROR` → OQ-008）。取得先がないため | `http://` の可否は OQ-003 |
| `weight` | integer | No | `-1` / `0` / `+1` を想定。値域は制約しない | 欠落・NULL は `0` として扱う（補正なし） | 本仕様は値を保持するのみ。加算は SPEC-003 / SPEC-004 が行う |
| `tags` | array\<string\> | No | - | 欠落・NULL・空配列はいずれも「タグ定義なし」として空タプルにする（→ F-001 AC-028） | 本仕様は保持のみ。付与は SPEC-004 |
| `verified` | boolean | No | - | 欠落・NULL は `false` として扱う | **本仕様の振る舞いに影響しない**。運用者が疎通確認の済否を記録するための注記であり、`false` でも取得する（→ OQ-005） |

#### (b) 各情報源の HTTP レスポンス

| 項目名 | 型 | 必須 | 制約 | NULL・空文字の扱い | 備考 |
|---|---|---|---|---|---|
| ステータスコード | integer | Yes | 200 のみを成功とする | - | 3xx は `httpx` のリダイレクト追従で解決する（→ OQ-003） |
| ボディ | bytes | Yes | 上限値は OQ-001 | 空（0 バイト）はパース不能としてフロー #18 で扱う | **`str` にデコードせずバイト列のまま** `feedparser` へ渡す（宣言された文字コードの解決を feedparser に委ねる） |

#### (c) パース済みフィードの1エントリ

| 項目名 | 型 | 必須 | 制約 | NULL・空文字の扱い | 備考 |
|---|---|---|---|---|---|
| `link` | string | Yes | `http` / `https` スキームであること | **当該エントリを除外**（フロー #19）。一意性のキーであるため | `Entry.url` になる。**正規化しない**（REQ-F-002 除外条件） |
| `title` | string | No | - | 空文字として扱い、エントリは残す（フロー #10） | 評価の主入力（SPEC-003）。空でもエントリを落とさないのは、要約のみで評価しうるため |
| `summary` / `description` / `content` | string | No | - | 空文字として扱い、エントリは残す（→ F-001 AC-023） | 取得元による名称の差は `feedparser` が吸収する。優先順位は §5 |
| `published` / `updated` | string | No | 解釈可能な日時形式 | `None` として扱い、エントリは残す（→ F-001 AC-026） | 多様な形式の吸収は `feedparser` に委ねる（→ [ADR-004](../04_decisions/ADR-004_implementation_stack.md)） |

### 出力

| 項目名 | 型 | 内容 | 条件 |
|---|---|---|---|
| 取得エントリ | list\<Entry\> | 抽出した全エントリ。**下記の順序規定に従う** | 常時（0件でも空リストを返す） |
| 情報源別の結果 | list\<SourceOutcome\> | 情報源ごとの取得件数と失敗理由。**定義された全情報源が、成功・失敗・0件のいずれでも 1 要素として現れる**（F-004 AC-022 / AC-010） | 常時。**定義0件のときは空リスト、全件失敗のときは全要素が `error` 非 null**。この差により下流が両者を区別する（F-004 AC-014 / AC-023） |

#### 出力順序の規定（**SPEC-002 が依存する**）

**取得エントリは次の二段の順序で返す。この順序は決定的でなければならない。**

1. **第一キー: 情報源の定義順** — `feeds.yaml` の `sources[]` の**記載順**。取得の
   完了順ではない（逐次取得のため両者は一致するが、規定するのは記載順の側である）
2. **第二キー: フィード内の掲載順** — フィードが返した**エントリの出現順をそのまま保持する**。
   公開日時で並べ替えない

**SPEC-002 が本仕様に要求するのは「決定性」のみである。** `select_evaluation_targets`
（`domain/state.py`）は入力順をそのまま保つだけで、**順序の意味を一切解釈しない**。
したがって「掲載順であること」自体が要求されているわけではない。

**その上で掲載順を採る理由:**

1. **追加の規定なしに決定的である。** 公開日時でソートする場合、`published_at` は
   欠落しうる（フロー #9 / F-001 AC-026）ため、**欠落分をどこに置くかを別途規定しないと
   決定的にならない**（`None` を最古に固定すれば全順序自体は定義できるが、その規定が要る）
2. **情報源をまたいで日時で混ぜると、`feeds.yaml` の定義順という運用者が制御できる
   唯一の優先順位が失われる。** 多くのフィードは新しい順に並ぶが、これは規約ではなく
   取得元の慣習であり、依存すると情報源ごとに順序の意味が変わる

**取得に失敗した情報源はエントリを寄与しないため、列から欠落する。** これにより後続の
情報源の相対位置が繰り上がるため、**同一のフィード内容でも、取得の成否が変われば
持ち越される記事の集合が変わる**（→ OQ-006）。

**この順序が持つ意味:** SPEC-002 の `select_evaluation_targets` は「新規どうしは
フィードからの取得順」を保って評価対象を選び、上限超過分を次回へ持ち越す
（F-001 AC-025 / AC-025a）。したがって**本仕様の出力順序が、上限に達したときにどの
記事が持ち越されるかを決める**。順序が非決定的だと、同じ入力でも持ち越される記事が
実行ごとに変わり、テストで固定できない。

> **既知の非対称性（OQ-006）:** 上記より、`feeds.yaml` の末尾に定義された情報源ほど
> 上限超過時に持ち越されやすい。SPEC-002 §6 は再評価対象について
> 「`evaluated_at` が古い順」で飢餓を構造的に防いだが、**新規エントリ側には同種の
> 保証がない**。持ち越された記事は次回も新規のまま同じ位置に現れるため、上限に
> 繰り返し達する状況では末尾の情報源が継続的に漏れうる。上限値（暫定200件 → TASK-028）が
> 実測の週31〜49件より十分大きいため当面は顕在化しないが、規定として残す。

## 5. バリデーション仕様

> フロー定義表（§3）に条件を書いた項目は、ここに重複して書かない。
> 本節は **§3 に現れない導出規則と補完規則**のみを定める。

| 項目 | ルール | タイミング | エラーメッセージ |
|---|---|---|---|
| `sources[].name` の一意性 | 定義内で重複しないこと | フィード定義の読み込み時 | `フィード定義に重複した情報源名があります: {name}` → 実行を中止（`CONFIG_ERROR` → OQ-008）。重複すると情報源別の集計（F-004 AC-003）と重みの引き当てが破綻するため |
| 要約の選択 | `summary` → `content[0].value` → `description` の順で最初に非空の値を採る | エントリ抽出時 | すべて空なら空文字（フロー #8）。エラーとしない |
| 要約の HTML | フィードの要約は HTML を含みうる。**本仕様ではタグを除去せずそのまま保持する** | エントリ抽出時 | エラーとしない。除去・切り詰めの要否は OQ-002 |
| 公開日時の基準 | `published` を優先し、無ければ `updated` を用いる。タイムゾーンを持たない値は UTC とみなす | エントリ抽出時 | いずれも解釈できなければ `None`（フロー #9） |
| フィード内の URL 重複 | **同一フィード内に同じ URL のエントリが複数ある場合、最初に現れたものを残し以降を無視する** | エントリ抽出時 | `{source_name}: 重複した URL のエントリを {n}件 無視しました`。同一実行内で同じ URL を二重に評価・投入しないため |
| 情報源間の URL 重複 | **名寄せしない。** 異なる情報源が同じ URL を返した場合も別エントリとして残す | エントリ抽出時 | エラーとしない。REQ-F-002 の除外条件（要否は TASK-009） |
| `bozo` フラグ | `feedparser` が `bozo=1`（整形式でない XML 等）を返しても、エントリが 1 件以上得られていれば成功として扱う | パース時 | 詳細ログ時のみ `{source_name}: フィードに不整合があります（{理由}）が、{n}件を取得しました`。**多くの実フィードが軽微な不整合で `bozo` を立てるため、これを失敗とすると取得可能な情報源を失う** |

## 6. 状態遷移

**対象なし** — 本仕様は状態を持たない。

`feeds.yaml` の読み込みも HTTP GET もパースも副作用のない読み取りであり、
`Entry` は不変（frozen dataclass）で、遷移する属性を持たない。処理済みか否かという
状態は `StateRecord` が担い、その状態機械は SPEC-002 §6 が定義する。

**本仕様は状態を参照しない。** 取得したエントリを既知/新規で選別せず全件返す。
これは責務の分離であると同時に、F-002 AC-018（状態の読み込みに失敗したら 1 件も
投入せず失敗終了する）を成立させる条件でもある — 取得が状態に依存しなければ、
状態の読み込み失敗を検知する時点が取得の前でも後でも振る舞いが変わらない。
