## 1. 概要

フィード定義ファイル（`feeds.yaml`）を読み込み、定義された全情報源から HTTP で
フィードを取得し、RSS/Atom をパースして各エントリの URL・タイトル・要約・公開日時・
情報源名を抽出する。抽出結果は **決定的な順序**（§4 出力）で後続処理へ渡す。

取得は `httpx`、パースは `feedparser`（**バイト列を渡す**）で行う。
`feedparser.parse(url)` の URL モードは使わない（→ [ADR-004](../04_decisions/ADR-004_implementation_stack.md) 補遺B）。

重複排除・評価・投入は本仕様の対象外（それぞれ SPEC-002 / SPEC-003 / SPEC-004）。
本仕様は **状態を参照しない** — 取得したエントリを無条件に全件返し、既知/新規の判定は
SPEC-002 の `select_evaluation_targets` が行う。

> **粒度についての注記（Rule S-1 / S-3）:** フロー定義表は 20 行あり Rule S-1 の
> 目安（15行）を超える。**それでも分割しない。** 分割候補は「① `feeds.yaml` の
> ロード」と「② 1情報源の取得・パース」だが、Rule S-2 の分割トリガー（独立した
> 状態機械）に該当しない — 本仕様は §6 のとおり状態を一切持たず、①②とも同一の
> `Source` / `Entry` を扱う純粋な変換である。加えて ① を切り出すと 4 行（#1・#2・
> #12・#13）となり Rule S-3（3行以下は統合）に近い。**行数が多いのは例外系が 12 行
> あるためであり、独立した振る舞いが混在しているためではない。**

## 2. 前提条件 (Preconditions)

| 前提条件 | 満たされない場合の挙動 |
|---|---|

| 各情報源が `name`（一意）と `url` を持つこと | 同上。本仕様は**検証済みの `Source` 列を受け取る** |
| 起動時の秘匿情報の検証が完了していること（F-001 AC-030 / AC-032） | 本仕様の処理は開始されない。検証は SPEC-005（CLI）が本仕様より前に行う |
| 各情報源への HTTPS 到達性があること | 当該情報源のみ取得失敗として扱い、他の情報源の処理を継続する（→ フロー #12〜16 / F-001 AC-011） |

> **注記:** 「情報源が 1 件以上定義されていること」は前提条件に**しない**。
> 0 件は正常系として扱い、その旨を示して正常終了する（→ フロー #3 / F-001 AC-024）。

## 3. フロー定義

> 「ユーザーへの表示 / レスポンス」列は **標準エラー出力への出力内容**、および
> 呼び出し元（`pipeline`）への戻り値を指す。サマリ（標準出力）の書式は SPEC-006 が定める。
>
> **終了コードは新設しない。** 参照する値は `src/feed_triage/contract/exit_codes.py` の
> 既存定義であり、正典は SPEC-005（CLI）が持つ。

|---|---|---|---|---|---|---|
| 1 | 主系 | 実行開始時 | システム | フィード定義の読み込み | `feeds.yaml` をパースし `Source` の列を構築する。**YAML 上の記載順を保持する**（→ §4 出力の順序規定） | （標準エラー）`情報源を読み込みました: {n}件` |
| 2 | 主系 | フィード定義の読み込み完了後 | システム | 情報源ごとの取得 | 各 `Source` の URL へ `httpx` で GET する。**情報源の定義順に、1件ずつ逐次実行する**（REQ-NF-002「単一プロセス・逐次処理」） | （標準エラー）`取得中: {source_name}` |
| 3 | 代替系 | IF 情報源の定義が 0 件 | システム | フィード定義の読み込み | 取得も抽出も行わず、0 件のサマリを出力して**正常終了する**（終了コード `OK`）。`SourceOutcome` は**空リスト**を返す（全件失敗との区別 → §4 出力） | （標準エラー）`情報源が定義されていません`（サマリ本体は SPEC-006 → F-004 AC-023） |
| 4 | 主系 | HTTP 200 を受信 | システム | フィードのパース | レスポンスの**バイト列**を `feedparser.parse()` に渡す。URL モードは使わない（→ [ADR-004](../04_decisions/ADR-004_implementation_stack.md) 補遺B） | - |

| 7 | 代替系 | IF エントリが 0 件のフィードを取得した | システム | エントリの抽出 | 当該情報源を**成功・0件**として記録する（失敗と区別する → F-004 AC-022） | （標準エラー）`{source_name}: 0件` |
| 8 | 代替系 | IF エントリの要約が空または欠落 | システム | エントリの抽出 | 要約を空文字として `Entry` を構築し、**評価対象から除外しない**（→ F-001 AC-023。タイトルのみでの評価は SPEC-003 が担う） | （標準エラー・詳細ログ時のみ）`{url}: 要約がありません` |
| 9 | 代替系 | IF エントリの公開日時が欠落または解釈不能 | システム | エントリの抽出 | `published_at` を `None` として `Entry` を構築し、**評価対象から除外しない**（→ F-001 AC-026） | （標準エラー・詳細ログ時のみ）`{url}: 公開日時を解釈できません` |
| 10 | 代替系 | IF エントリのタイトルが空または欠落 | システム | エントリの抽出 | タイトルを空文字として `Entry` を構築し、除外しない（→ §5） | （標準エラー・詳細ログ時のみ）`{url}: タイトルがありません` |
| 11 | 代替系 | WHERE dry-run が指定されている | 運用者 | 実行 | **通常実行と完全に同一の取得・抽出を行う**（dry-run による分岐を持たない → F-005 AC-010） | 通常実行と同じ |
| 12 | 例外系 | WHEN HTTP が 4xx / 5xx を返す | システム | 情報源ごとの取得 | 当該情報源を**取得失敗**として記録し、次の情報源へ進む。リトライしない（→ §7「リトライ方針」） | （標準エラー）`{source_name} の取得に失敗しました: HTTP {status}。この情報源をスキップします` |
| 13 | 例外系 | WHILE 情報源が応答しない（タイムアウト 30 秒） | システム | 情報源ごとの取得 | 30 秒で打ち切り、取得失敗として記録して次の情報源へ進む（→ F-001 AC-013 → AC-011）。実行全体は停止しない | （標準エラー）`{source_name} の取得がタイムアウトしました（30秒）。この情報源をスキップします` |
| 14 | 例外系 | WHEN 接続・TLS・DNS のエラーが発生 | システム | 情報源ごとの取得 | 取得失敗として記録し、次の情報源へ進む。**証明書検証を無効化しない**（REQ-NF-006） | （標準エラー）`{source_name} に接続できません: {理由}。この情報源をスキップします` |
| 15 | 例外系 | IF レスポンスサイズが上限を超過 | システム | 情報源ごとの取得 | 受信を打ち切り、当該情報源を取得失敗として記録して次へ進む。**部分的に受信したバイト列をパースしない**（途中で切れた XML から不完全なエントリを作らないため） | （標準エラー）`{source_name} の応答が上限（10 MB）を超えました。この情報源をスキップします` |

> - [x] **権限違反アクセス** — フロー #14 と同じ。本システムは認証機構を持たず（REQ-NF-005）、取得元の HTTP ステータスに委ねる
> - [x] **必須項目未入力** — フロー #17（エントリの `url`）。`feeds.yaml` の構造検証は SPEC-005 が担う（→ §2）。情報源側の必須項目欠落は §5 の既定値で補完する
> - [x] **最大値・最小値超過** — フロー #15（レスポンスサイズ上限 10 MB → §7）。要約長の切り詰めは本仕様の対象外（→ OQ-002 / TASK-029）
> - [x] **空文字・NULL入力** — フロー #8 / #9 / #10（要約・公開日時・タイトル）とフロー #17（URL）。前3者は補完して継続し、URL のみ除外する
> - [x] **外部システムの障害** — フロー #12 / #14 / #16（HTTP エラー・接続失敗・パース不能）
> - [x] **タイムアウト** — フロー #13（1情報源あたり 30 秒 → REQ-NF-001）
> - [x] **同時操作・競合** — **対象なし。** 本仕様は状態を読み書きせず（§6）、取得は読み取り専用の GET のみであるため、競合しうる共有リソースが存在しない。実行の競合は状態の永続化で生じ、SPEC-002 フロー #17 / #18 が扱う
> - [x] **対象リソースが存在しない** — `feeds.yaml` の不在は SPEC-005 が起動時に検知（→ §2）／フロー #12 の 404（`blef-fr` で実際に発生した経路 → TASK-027）
> - [x] **対象リソースが削除済み** — フロー #12 の 404 / 410 と同じ扱い。情報源側でフィードの提供が終了した場合、取得失敗が継続する。**継続的な 0 件の検知は本仕様では行わない**（→ F-004 AC-003a / TASK-048）

## 4. 入出力定義

### 入力

#### (a) フィード定義ファイル（`feeds.yaml`）の `sources[]` の1要素

### 出力

| 項目名 | 型 | 内容 | 条件 |
|---|---|---|---|
| 取得エントリ | list\<Entry\> | 抽出した全エントリ。**下記の順序規定に従う** | 常時（0件でも空リストを返す） |
| 情報源別の結果 | list\<SourceOutcome\> | 情報源ごとの取得件数と失敗理由。**定義された全情報源が、成功・失敗・0件のいずれでも 1 要素として現れる**（F-004 AC-022 / AC-010） | 常時。**定義0件のときは空リスト、全件失敗のときは全要素が `error` 非 null**。この差により下流が両者を区別する（F-004 AC-014 / AC-023） |

#### 出力順序の規定（**SPEC-002 が依存する**）

**取得エントリは次の二段の順序で返す。この順序は決定的でなければならない。**

1. **第一キー: 情報源の定義順** — `feeds.yaml` の `sources[]` の**記載順**。取得の
   完了順ではない（逐次取得のため両者は一致するが、規定するのは記載順の側である）
2. **第二キー: フィード内の掲載順** — フィードが返した**エントリの出現順をそのまま保持する**。
   公開日時で並べ替えない

**SPEC-002 が本仕様に要求するのは「決定性」のみである。** `select_evaluation_targets`
（`domain/state.py`）は入力順をそのまま保つだけで、**順序の意味を一切解釈しない**。
したがって「掲載順であること」自体が要求されているわけではない。

**その上で掲載順を採る理由:**

1. **追加の規定なしに決定的である。** 公開日時でソートする場合、`published_at` は
   欠落しうる（フロー #9 / F-001 AC-026）ため、**欠落分をどこに置くかを別途規定しないと
   決定的にならない**（`None` を最古に固定すれば全順序自体は定義できるが、その規定が要る）
2. **情報源をまたいで日時で混ぜると、`feeds.yaml` の定義順という運用者が制御できる
   唯一の優先順位が失われる。** 多くのフィードは新しい順に並ぶが、これは規約ではなく
   取得元の慣習であり、依存すると情報源ごとに順序の意味が変わる

**取得に失敗した情報源はエントリを寄与しないため、列から欠落する。** これにより後続の
情報源の相対位置が繰り上がるため、**同一のフィード内容でも、取得の成否が変われば
持ち越される記事の集合が変わる**（→ OQ-006）。

**この順序が持つ意味:** SPEC-002 の `select_evaluation_targets` は「新規どうしは
フィードからの取得順」を保って評価対象を選び、上限超過分を次回へ持ち越す
（F-001 AC-025 / AC-025a）。したがって**本仕様の出力順序が、上限に達したときにどの
記事が持ち越されるかを決める**。順序が非決定的だと、同じ入力でも持ち越される記事が
実行ごとに変わり、テストで固定できない。

> **既知の非対称性（OQ-006）:** 上記より、`feeds.yaml` の末尾に定義された情報源ほど
> 上限超過時に持ち越されやすい。SPEC-002 §6 は再評価対象について
> 「`evaluated_at` が古い順」で飢餓を構造的に防いだが、**新規エントリ側には同種の
> 保証がない**。持ち越された記事は次回も新規のまま同じ位置に現れるため、上限に
> 繰り返し達する状況では末尾の情報源が継続的に漏れうる。上限値（暫定200件 → TASK-028）が
> 実測の週31〜49件より十分大きいため当面は顕在化しないが、規定として残す。

## 6. 状態遷移

**対象なし** — 本仕様は状態を持たない。

`feeds.yaml` の読み込みも HTTP GET もパースも副作用のない読み取りであり、
`Entry` は不変（frozen dataclass）で、遷移する属性を持たない。処理済みか否かという
状態は `StateRecord` が担い、その状態機械は SPEC-002 §6 が定義する。

**本仕様は状態を参照しない。** 取得したエントリを既知/新規で選別せず全件返す。
これは責務の分離であると同時に、F-002 AC-018（状態の読み込みに失敗したら 1 件も
投入せず失敗終了する）を成立させる条件でもある — 取得が状態に依存しなければ、
状態の読み込み失敗を検知する時点が取得の前でも後でも振る舞いが変わらない。

## 7. 非機能仕様（この仕様固有）

| 観点 | 仕様 | 対応要件 |
|---|---|---|
| タイムアウト | 1情報源あたり **30秒**。接続・読み込みを含む1情報源の取得全体に適用する（個々のソケット操作ごとではない）。13情報源が全てタイムアウトしても 6.5 分で、実行時間目標 30 分に収まる | REQ-NF-001, [F-001](../02_features/F-001_triage_and_ingest.md) AC-013 |
| タイムアウト（全体上限） | `httpx` のフェーズ別タイムアウト（connect / read / write / pool）とは別に、**1情報源の取得開始からの経過時間で 30 秒の全体上限を設ける**。低速に送信し続けるサーバではフェーズ別タイムアウトが発火せず、REQ-NF-001 の「13情報源すべてで6.5分」が成立しない経路があるため。**30秒の独立した根拠は未確立**（→ TASK-064。SPEC-004 OQ-005 と同種の問題） | REQ-NF-001, REQ-NF-004 |
| リトライ方針 | **取得失敗時にリトライしない。** 週次実行であり、次回実行で自動的に再取得される（要件定義 §5「次回実行時に再取得を試みる」）。実行内リトライは 13情報源 × 待機時間の分だけ実行時間を伸ばす一方、恒久的な失効（404）には無効である | REQ-NF-001, REQ-NF-004 |
| 逐次処理 | 情報源を並列取得せず、定義順に 1 件ずつ処理する | REQ-NF-002「単一プロセス・逐次処理」 |
| 部分障害の分離 | 1情報源の失敗が他の情報源の処理を止めない。1エントリの不正が同一フィードの他エントリを落とさない（フロー #17） | REQ-NF-004, [F-001](../02_features/F-001_triage_and_ingest.md) AC-011 |
| メモリ | **`httpx` の `stream()` でチャンクを逐次読み込み、累積バイト数が上限を超えた時点で接続を切る。** `Content-Length` があれば事前判定も行うが、それのみに依拠しない（チャンク転送エンコーディングでは存在しないため）。**上限値は 10 MB。** | REQ-NF-004, ADR-004 補遺B |
| **リダイレクト** | **追従する。上限3回**（`follow_redirects=True` / `max_redirects=3`）。**`https` → `http` へのダウングレードは拒否**し、当該情報源を取得失敗として扱う | REQ-NF-006, ADR-004 補遺B |
| セキュリティ（外部入力） | 取得したバイト列は**信頼できない入力**として扱う。XXE 対策は `feedparser` の自前実装（`feature_external_ges=0`）に依拠し、`defusedxml` を追加しない | [ADR-004](../04_decisions/ADR-004_implementation_stack.md) 補遺B, REQ-NF-006 |
| 依存バージョン | `feedparser >= 6.0.12`（ReDoS 修正版。6.0.11 以下は `mixin.py` の email 正規表現に ReDoS がある → ADR-004 補遺B B-2 / B-3）。バージョンの固定は `pyproject.toml`（ADR-004 OQ-003） | ADR-004 補遺B |
| セキュリティ（通信） | 全通信を HTTPS で行い、証明書検証を無効化しない | REQ-NF-006 |
| セキュリティ（副作用） | フィード由来の文字列をサブプロセス・シェルへ渡さない。本仕様はサブプロセスを起動しない | REQ-NF-006, `application_checklist` C-S01 / C-S02 |
| アクセス頻度 | 週1回の取得であり、取得元の利用規約に反する頻度でのアクセスを行わない | 要件定義 §4.5 |
| 冪等性 | 同一の入力（同じ `feeds.yaml` と同じフィード内容）に対し、同じエントリ列を**同じ順序で**返す（→ §4 出力順序） | R-002, [F-001](../02_features/F-001_triage_and_ingest.md) AC-004 |
| 取得件数の制約 | 多くのフィードは直近 N 件のみを配信する（実測で複数フィードが 20 件で頭打ち）。**本仕様は取得できた範囲のみを返し、欠落を検知しない** | [F-002](../02_features/F-002_scheduled_execution.md) AC-011 / OQ-004（TASK-047） |

> **レスポンスサイズ上限を 10 MB とする根拠（TASK-062）:** 実測の最大フィードは
> 全文配信の 9,238 字（数十 KB 相当）であり、**その3桁上に置く**。誤って正常な
> フィードを落とす確率を実質ゼロにしつつ、メモリ枯渇の緩和として機能する値である。
> 13情報源すべてが上限いっぱいでも 130 MB で、GitHub Actions の標準ランナー（7 GB）に
> 対して十分小さい。**逐次処理（並列取得しない）のため、実際に同時に載るのは1情報源分のみ。**
>
> **リダイレクトを追従する根拠（TASK-071）:** ブログのフィード URL は移転（301）が
> 実運用で起こり、追従しないと該当情報源が静かに取得失敗し続ける。一方
> **`https` → `http` のダウングレードを許すと、通信の平文化に加え、ADR-004 補遺B が
> 「`feeds.yaml` の固定値だから該当しない」として退けた SSRF の前提が崩れる**
> （追従先は取得元が指定する値であり固定値ではない）。上限3回は、正当な移転
> （旧ドメイン → 新ドメイン → 正規化 URL）を追従でき、かつ無限ループを塞ぐ値。
