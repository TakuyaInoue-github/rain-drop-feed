## 1. 概要

コマンドライン引数を解析し、**実行に必要な設定・秘匿情報を起動時に検証**した上で、
処理本体（SPEC-001 → SPEC-002 → SPEC-003 → SPEC-004）を起動する。処理の完了後、
結果に応じた**終了コードを決定して返す**。

**本仕様は終了コードの正典である。** 他の SPEC は本仕様が定めた値を参照するのみで、
新たな値を定義しない。

> **なぜ起動時にまとめて検証するか:** 設定不備を処理の途中で発見すると、
> それまでのフィード取得・LLM 評価のコストが無駄になり、かつ**一部だけ投入された
> 中途半端な状態**が残りうる（F-001 AC-030 の「部分的な処理が行われないこと」）。
> ADR-002 が「実行の最後に push」を選んだ結果、権限不備は評価コストを全て払った後に
> 発覚するため、事前に検証できるものは事前に検証する（→ OQ-003）。

**本仕様の範囲外:**

| 範囲外の内容 | 置き場 |
|---|---|
| フィード取得・評価・投入・状態管理の処理内容 | SPEC-001 / 002 / 003 / 004 |
| サマリの出力項目・書式 | SPEC-006 |
| 定期実行のスケジューリング（cron 定義） | ワークフロー定義（F-002。SPEC 化しない） |

> **粒度についての注記（Rule S-1 / S-2 / S-3）:** フロー定義表は13行で目安内。
> 本仕様は状態を持たない（§6）ため Rule S-2 の分割トリガーに該当しない。
> 「引数解析」と「起動時検証」を分けないのは、両者が**同一の失敗（`CONFIG_ERROR`）へ
> 収束し、分割すると 4〜5 行ずつで Rule S-3 に近づく**ため。終了コードの決定を
> 分けないのは、それが引数（dry-run か否か）と処理結果の**両方**に依存し、
> どちらの SPEC に置いても片方をまたぐため。

## 2. 前提条件 (Preconditions)

| 前提条件 | 満たされない場合の挙動 |
|---|---|
| Python 3.10 以上で実行されること | 起動しない。パッケージのメタデータが弾く（ADR-004） |
| （通常実行）`RAINDROP_TOKEN` が設定されていること | フロー #8。処理を開始せず `CONFIG_ERROR` で終了する |
| （通常実行）`RAINDROP_COLLECTION_ID` が設定され整数として解釈できること | フロー #9。同上 |
| `ANTHROPIC_API_KEY` が設定されていること | フロー #10。**dry-run でも必須**（評価は実行するため → F-005 AC-030 の除外対象外） |
| `feeds.yaml` が存在し、YAML として解釈でき、**`sources[]` の各要素が `name` / `url` を持ち `name` が一意であること** | フロー #11。同上。**構造の検証も本仕様が担う**（→ 下記の注記） |
| `profile.md` が存在し読み込めること | フロー #12。同上（→ SPEC-003 §2 / TASK-087） |

> **`feeds.yaml` の構造検証を本仕様が担う理由:** SPEC-001 のロード時ではなく起動時に行う。
> (1) 同じ `CONFIG_ERROR` のエラーメッセージが2つの SPEC に分散するのを避ける（Rule B-3）。
> (2) 情報源の定義不備は**評価コストを払う前に**弾ける。SPEC-001 は検証済みの `Source` 列を
> 受け取る前提とし、フロー表から構造検証を持たない。
>
> **dry-run で検証を緩める対象:** `RAINDROP_TOKEN` と `RAINDROP_COLLECTION_ID` の2つのみ
> （F-005 AC-030）。評価は dry-run でも実際に行うため `ANTHROPIC_API_KEY` は必須であり、
> 設定ファイル2種も同様に必須とする（→ **OQ-001。F に AC がないため暫定**）。

## 3. フロー定義

> 本仕様は無人 CLI のバッチ処理であり、対話的な画面を持たない。
> 「ユーザーへの表示 / レスポンス」列は **標準エラー出力への出力内容**と**終了コード**を指す。
> サマリ（標準出力）の書式は SPEC-006 が定める。

| # | フロー種別 | 条件 / トリガー | アクター | 操作・イベント | システムの処理 | ユーザーへの表示 / レスポンス |
|---|---|---|---|---|---|---|
| 1 | 主系 | 実行開始時 | 運用者 / 定期実行ジョブ | コマンドの起動 | 引数を解析し `RunOptions`（`dry_run` / `verbose`）を構築する（→ §4） | - |
| 2 | 主系 | 引数の解析完了後 | システム | 起動時検証 | §2 の項目を**すべて**検証する。**1つでも欠ければ処理を開始しない**（F-001 AC-030 / F-002 AC-012） | （標準エラー・詳細ログ時のみ）`設定の検証が完了しました` |
| 3 | 主系 | 検証をすべて通過 | システム | 処理本体の起動 | SPEC-001 → SPEC-002 → SPEC-003 → SPEC-004 の順に実行し、`RunSummary` を得る | （標準出力）サマリ（→ SPEC-006） |
| 4 | 主系 | 処理の完了 | システム | 終了コードの決定 | §5 の規則に従い終了コードを決定して返す | 終了コード |
| 5 | 代替系 | WHERE `--dry-run` が指定されている | 運用者 | コマンドの起動 | `RAINDROP_TOKEN` / `RAINDROP_COLLECTION_ID` の検証を**省略**する（F-005 AC-030）。他の検証は行う | （標準出力）dry-run であることを示す（→ SPEC-006 / F-005 AC-005） |
| 6 | 代替系 | WHERE `--dry-run` かつ収集レイヤーの秘匿情報が未設定 | 運用者 | 起動時検証 | 処理を継続する。ただし**通常実行では起動時に失敗する状態であること**を出力に含める（F-005 AC-030a） | （標準エラー）`dry-run のため続行しますが、通常実行に必要な設定が不足しています: {項目名}` |
| 7 | 代替系 | WHERE `--verbose` が指定されている | 運用者 | コマンドの起動 | 標準エラーへの出力を詳細化する。**サマリ（標準出力）の内容は変化しない**（F-004 AC-007） | 詳細な処理経過 |
| 8 | 例外系 | IF `RAINDROP_TOKEN` が未設定・空文字（通常実行） | 運用者 | 起動時検証 | 処理を開始せず終了する（`CONFIG_ERROR`）。**値そのものは出力しない**（F-001 AC-031） | （標準エラー）`環境変数 RAINDROP_TOKEN が設定されていません` |
| 9 | 例外系 | IF `RAINDROP_COLLECTION_ID` が未設定・空文字・整数として解釈できない（通常実行） | 運用者 | 起動時検証 | 同上。**既定のコレクションへフォールバックしない**（F-001 AC-032） | （標準エラー）`環境変数 RAINDROP_COLLECTION_ID が設定されていないか、整数ではありません` |
| 10 | 例外系 | IF `ANTHROPIC_API_KEY` が未設定・空文字 | 運用者 | 起動時検証 | 同上。**dry-run でも中止する**（評価を実行するため） | （標準エラー）`環境変数 ANTHROPIC_API_KEY が設定されていません` |
| 11 | 例外系 | IF `feeds.yaml` が存在しない・YAML として解釈できない・`sources` キーを欠く・**`sources[]` の要素が `name` / `url` を欠く**・**`name` が定義内で重複する** | 運用者 | 起動時検証 | 処理を開始せず終了する（`CONFIG_ERROR`）。空の情報源リストにフォールバックしない | （標準エラー）`フィード定義が見つかりません: {path}` / `フィード定義を解釈できません: {path} ({理由})` / `フィード定義の情報源に必須項目がありません: sources[{i}]` / `フィード定義に重複した情報源名があります: {name}` |
| 12 | 例外系 | IF `profile.md` が存在しない・読み込めない | 運用者 | 起動時検証 | 同上。基準なしで評価すると全件のスコアが無意味になるため（→ SPEC-003 §2） | （標準エラー）`トリアージ基準が見つかりません: {path}` |
| 13 | 例外系 | IF 未知のコマンドライン引数が与えられた | 運用者 | 引数の解析 | 使用方法を表示して終了する（`CONFIG_ERROR`。`argparse` の既定挙動） | （標準エラー）`usage: feed-triage [-h] [--version] [--dry-run] [--verbose]` |

> **確認チェック:** 例外系9項目の検討結果
> - [x] **未認証アクセス** — フロー #8 / #10（秘匿情報の未設定）。本システム自体は認証機構を持たない（REQ-NF-005）
> - [x] **権限違反アクセス** — **本仕様では検証しない。** トークンが有効かどうか（401/403）は実際に呼ぶまで分からず、起動時には未設定の検知しかできない。状態ブランチへの書き込み権限も同様（→ OQ-003 / TASK-070・TASK-077）
> - [x] **必須項目未入力** — フロー #8〜12（秘匿情報3種・設定ファイル2種）
> - [x] **最大値・最小値超過** — **対象なし。** 本仕様が受け取る引数は真偽値2つのみで、値域を持つ入力がない。評価件数・レスポンスサイズ等の上限は各 SPEC が扱う
> - [x] **空文字・NULL入力** — フロー #8〜10（環境変数が空文字の場合を未設定と同じ扱いにする → §4）
> - [x] **外部システムの障害** — **本仕様では扱わない。** 起動時検証は環境変数とローカルファイルのみを見る。外部への疎通確認は行わない（→ OQ-003 でその是非を扱う）
> - [x] **タイムアウト** — 同上。本仕様に外部通信がない
> - [x] **同時操作・競合** — **本仕様では発生しない。** 引数解析と検証は読み取りのみ。実行の同時起動による競合は状態の永続化で生じ、SPEC-002 フロー #17 / #18 が扱う
> - [x] **対象リソースが存在しない** — フロー #11 / #12（設定ファイルの不在）
> - [x] **対象リソースが削除済み** — フロー #11 / #12 と同じ扱い

## 4. 入出力定義

### 入力 (a) コマンドライン引数

| 項目名 | 型 | 必須 | 制約 | NULL・空文字の扱い | 備考 |
|---|---|---|---|---|---|
| `--dry-run` | boolean | No | フラグ（値を取らない） | 未指定は `false`（通常実行） | 投入を行わない（→ F-005） |
| `--verbose` | boolean | No | フラグ | 未指定は `false` | 標準エラーの詳細化。**サマリは変化しない**（F-004 AC-007） |
| `--version` | boolean | No | フラグ | - | バージョンを表示して `OK` で終了する（`application_checklist` C-U02） |
| `-h` / `--help` | boolean | No | フラグ | - | 使用方法を表示して `OK` で終了する（`application_checklist` C-U01）。**起動時検証より前に処理する**（設定不備でもヘルプは読めなければならない） |

> **オプションを増やさない方針:** 閾値・件数上限・タイムアウト等は引数で上書きできる
> ようにしない。これらは要件層・SPEC 層が値を持ち（REQ-F-005 / REQ-NF-002a）、
> **実行のたびに変えられると R-006 の事後検証で「どの設定で得た結果か」が
> 追跡できなくなる**ため。設定の変更はファイルの編集とコミットで行う（REQ-NF-008）。

### 入力 (b) 環境変数

| 項目名 | 型 | 必須 | 制約 | NULL・空文字の扱い | 備考 |
|---|---|---|---|---|---|
| `RAINDROP_TOKEN` | string | Yes（通常実行のみ） | 空でないこと | 未設定・空文字を**同じ扱い**とし `CONFIG_ERROR` で終了する（フロー #8） | 値をログ・サマリ・エラーメッセージに出力しない（F-001 AC-031 / REQ-NF-006） |
| `RAINDROP_COLLECTION_ID` | string → integer | Yes（通常実行のみ） | 整数として解釈できること | 同上（フロー #9） | 値をサマリに出力しない（F-004 AC-030） |
| `ANTHROPIC_API_KEY` | string | **Yes（dry-run を含む）** | 空でないこと | 同上（フロー #10） | 値を出力しない（F-001 AC-033） |

> **未設定と空文字を区別しない理由:** 空文字のトークンで API を呼べば必ず 401 になり、
> 未設定と同じ結果に至る。区別してもエラーメッセージが変わるだけで、運用者の対処
> （値を設定する）は同一であるため、同じ扱いにして分岐を減らす。

### 出力

| 項目名 | 型 | 内容 | 条件 |
|---|---|---|---|
| 終了コード | integer | §5 の規則で決定した値 | 常時 |
| `RunOptions` | dataclass | `dry_run` / `verbose` | 検証を通過した場合のみ。処理本体へ渡す |
| 検証済みの設定 | dataclass | 秘匿情報3種・`feeds.yaml` の内容・`profile.md` の内容 | 同上。**秘匿情報は `__repr__` に含めない**（誤ってログへ出力されるのを型で防ぐ） |

## 5. 終了コードの規則（**本仕様が正典**）

`src/feed_triage/contract/exit_codes.py` の定義が実装上の正典であり、
本節はその意味論を定める。**他の SPEC は本節の値を参照するのみで新設しない。**

| 値 | 定数 | 意味 | 決定する条件 | 発生源 |
|---|---|---|---|---|
| 0 | `OK` | 正常終了 | 下記のいずれにも該当しない。**投入対象が0件の実行を含む**。また**情報源の定義が0件の実行**も含む（→ F-001 AC-024）。全情報源の取得に失敗した実行は `FETCH_ALL_FAILED` | - |
| 1 | `INGEST_ALL_FAILED` | 投入対象があったが全件失敗した | POST を試行した件数が1件以上あり、その全件が失敗した。**401/403 の打ち切りで未試行となった分は分母に含めない** | SPEC-004 フロー #15 |
| 2 | `CONFIG_ERROR` | **運用者が是正すべき**設定・秘匿情報の不備、または引数の誤り | フロー #8〜13 のいずれか。**処理本体を開始する前に決定する** | 本仕様のみ |
| 3 | `STATE_PERSIST_FAILED` | 処理済み記録の読み込み・書き込み・永続化に失敗した | ローカル追記の失敗、push の再試行が規定回数すべて失敗、状態ブランチへの書き込み権限なし、読み込み失敗 | SPEC-002 フロー #16 / #19 / #20 / #21 |
| 4 | `SPEC_ERROR` | **実装が是正すべき**要求の不正 | LLM API が HTTP 400 を返した（プロンプト構成・スキーマ定義の誤り）。**処理本体の途中で決定する** | SPEC-003 フロー #15 |
| 5 | `FETCH_ALL_FAILED` | 定義された情報源の**全件**の取得に失敗した | 情報源の定義が1件以上あり、その全件が取得に失敗した。**定義0件の実行は含まない**（`OK`） | SPEC-001 フロー #18 |

> **`SPEC_ERROR` を `CONFIG_ERROR` と分ける理由:** 無人実行では終了コードが原因究明の
> 一次情報である（F-002 AC-010）。両者を同じ値に畳むと、運用者は実装バグを
> **「自分の設定ミス」と誤読し、設定を見直す方向へ調査を誤らせる**。是正の主体が
> 異なる（運用者 vs 実装）ため、値を分ける。

> **非0にしないもの（`application_checklist` C-I01 / REQ-F-010）:** 次はいずれも
> **実行全体の終了コードに影響しない**。
>
> - 個別情報源の取得失敗（SPEC-001 フロー #12〜#17）。**#18（全情報源の失敗）は含まない** — こちらは `FETCH_ALL_FAILED` として非0にする
> - 個別エントリの評価失敗（SPEC-003 フロー #9〜14）
> - 個別エントリの投入失敗（SPEC-004 フロー #10 / #12〜14）
>
> 個別の失敗が実行全体の失敗になるのは、**その段階の全件が失敗した場合のみ**である（SPEC-001 フロー #18 / SPEC-004 フロー #15）。
> これは「個別の失敗によって実行全体が異常終了してはならない」（REQ-F-010）の帰結であり、
> 週次バッチが1件の障害で止まらないことを保証する。

### 複数の条件が同時に成立した場合の優先順位

**次回の実行へ伝播する障害を、当該実行内で閉じる障害より優先して報せる。**

| 順位 | 値 | 伝播範囲 |
|---|---|---|
| 1 | `CONFIG_ERROR` | 処理本体を開始する前に確定するため、**他と競合しない** |
| 2 | `STATE_PERSIST_FAILED` | **次回実行の入力を壊す** |
| 3 | `SPEC_ERROR` | 当該実行内で閉じる（次回は正常な入力から始まる） |
| 4 | `FETCH_ALL_FAILED` | 当該実行内で閉じる。ただし**供給が完全に途切れている** |
| 5 | `INGEST_ALL_FAILED` | 同上 |
| 6 | `OK` | - |

> **`STATE_PERSIST_FAILED` を最優先する理由:** 記録に失敗すると、記録できなかった分は
> 次回実行で**すべて新規として扱われる**。投入済みなら重複投入（R-002 違反）、
> 評価済みなら再評価によりコストが二重にかかる（REQ-NF-002a）。
> **障害が次回実行へ伝播する唯一の経路**である。
>
> 一方 `SPEC_ERROR` と `INGEST_ALL_FAILED` は当該実行内で閉じる。記録さえ残れば、
> 投入されなかったことは `ingested: false` として保存され、次回の入力は正常である。
>
> なお `SPEC_ERROR` と `STATE_PERSIST_FAILED` は**同時に成立しうる**。HTTP 400 で
> 実行を中止しても、それまでに評価済みのエントリの記録を永続化する段階で
> push に失敗する経路があるため（SPEC-003 フロー #15 → SPEC-002 フロー #19）。
> この場合は上表に従い `STATE_PERSIST_FAILED` を返す。

### dry-run 時の終了コード

dry-run では投入も記録も行わないため、`INGEST_ALL_FAILED` と `STATE_PERSIST_FAILED` は
発生しない。返りうるのは `CONFIG_ERROR`（フロー #10〜13）・**`SPEC_ERROR`**・**`FETCH_ALL_FAILED`**・`OK` の4つ。

**`SPEC_ERROR` と `FETCH_ALL_FAILED` が dry-run でも発生する**のは、評価と取得を実際に行うためである（SPEC-003 フロー #8 / SPEC-001 フロー #11）。
プロンプト構成の誤りは dry-run でも同じく HTTP 400 を返す。

## 6. 状態遷移

**対象なし** — 本仕様は状態を持たない。引数解析・検証・終了コードの決定はいずれも
その場で完結する変換であり、実行をまたいで保持する状態がない。
