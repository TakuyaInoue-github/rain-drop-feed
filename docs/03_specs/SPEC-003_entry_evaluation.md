## 1. 概要

1件のエントリ（タイトル・要約・情報源名）を Anthropic Messages API へ渡し、
トリアージ基準に照らした **スコア・評価理由・提案タグ** を得る。
呼び出しは SDK 経由の同期呼び出しとし（[ADR-001](../04_decisions/ADR-001_llm_invocation_method.md)）、
モデルは Claude Haiku 4.5（[ADR-003](../04_decisions/ADR-003_triage_model_selection.md)、暫定）、
出力は構造化出力（`output_config.format`）で受ける。

本仕様は **1件の評価が「成功」か「どの種別の失敗」かを判定して返すところまで**を担う。
失敗回数の加算・状態への追記は行わない（→ §1.1）。投入可否の判定・重み補正も行わない
（→ SPEC-004（未作成）／`domain/scoring.py`）。

### 1.1 責務境界（SPEC-002 との分担）

`failure_count` を**加算するのは SPEC-002 側**であり、本仕様は加算しない。
本仕様は各エントリについて **「失敗の種別」と「当該実行内での試行回数」** を含む
評価結果（§4 出力の `EvaluationOutcome`）を返し、SPEC-002 がそれを受けて
`failure_count` の加算要否と加算量を決める。

**この分担を選んだ根拠:**

1. **単一の書き手を保つ。** `failure_count` は状態ファイルの列であり、その読み書きは
   SPEC-002 に集約されている（SPEC-002 §4 / §6）。評価側からも書けるようにすると
   同じ列に2つの書き手が生まれ、SPEC-002 §6 の状態遷移表が唯一の正典でなくなる。
2. **dry-run で分岐させない。** dry-run では評価は行うが失敗回数を記録しない
   （F-005 AC-011）。加算を状態層に寄せておけば、本仕様は dry-run と通常実行で
   完全に同一の振る舞いになり（→ フロー #8）、分岐は SPEC-002 側の1箇所で済む。
3. **判別基準は評価側にしか置けない。** 「API 呼び出し自体の失敗」と「応答の意味的不正」の
   区別（F-001 AC-015 / AC-015a）は API 応答そのものを見なければ判定できない。
   したがって**判別は本仕様が行い、加算は SPEC-002 が行う**。SPEC-002 §6 の
   「評価に失敗（意味的不正）」「評価に失敗（API 呼び出し自体）」の2イベントは、
   本仕様 §5 の分類表を参照する形で読む。
4. **層構造と整合する。** 確率的な外部呼び出しは `adapters`、その出力の決定論的な検証は
   `domain` に置く（[ADR-004](../04_decisions/ADR-004_implementation_stack.md) 設計原則(3)）。
   スコアの値域検証は既に `domain/scoring.py` の `is_valid_score()` にあり、
   本仕様の §5 はその関数の仕様である。

> **粒度についての注記（Rule S-1 / S-2 / S-4）:** フロー定義表は14行で15行の目安内。
> 本仕様は状態を持たない（§6）ため Rule S-2 の分割トリガーに該当しない。
> F-001 と F-005 の双方から参照される（Rule S-4 の「複数の F が 1 SPEC を共有」）。
> 評価と投入判定を1つの SPEC にまとめない理由は、投入判定が決定論的な純関数であり
> 外部呼び出し・リトライ・失敗分類を一切持たないため、フロー定義表を共有する必要が
> ないこと（Rule S-3 の「統合する」側にも当たらない。投入は Raindrop API 連携という
> 独立した外部システム連携を持つ）。

## 2. 前提条件 (Preconditions)

| 前提条件 | 満たされない場合の挙動 |
|---|---|
| `ANTHROPIC_API_KEY` が設定されていること | 起動時の検証で実行を中止する（終了コード 2 / F-001 AC-030）。本仕様のフローには到達しない。dry-run でも同じ（F-005 AC-030 が API キーを除外対象としないため） |
| トリアージ基準（`profile.md`）が読み込めること | 評価の判断基準が欠けるため実行を中止する（→ フロー #14） |
| 評価対象エントリが選定済みであること | 選定は SPEC-002 が行う。0件なら本仕様は一度も呼ばれない（F-001 AC-022） |
| エントリが `url` / `title` を持つこと | `title` が空の場合の扱いは §5。`url` の欠落は本仕様に到達する前に排除される（SPEC-001（未作成）の取得段階） |
| モデル ID が明示的に指定されていること | SDK の必須パラメータであり省略できない（ADR-001。既定モデルへの暗黙のフォールバックが構造的に起こらない） |

## 3. フロー定義

> 本仕様は無人 CLI のバッチ処理であり、対話的な画面を持たない。
> 「ユーザーへの表示 / レスポンス」列は **標準エラー出力への出力内容**、
> および呼び出し元（`pipeline`）への戻り値を指す。スコア・判定そのものの出力は
> サマリ側の責務である（→ SPEC-006（未作成）／F-004）。

| # | フロー種別 | 条件 / トリガー | アクター | 操作・イベント | システムの処理 | ユーザーへの表示 / レスポンス |
|---|---|---|---|---|---|---|
| 1 | 主系 | 評価対象エントリが1件与えられた | システム | 評価の実行 | トリアージ基準・タイトル・要約・情報源名からプロンプトを構成する（→ §4 入力） | （標準エラー・詳細ログ時のみ）`評価中: {url}` |
| 2 | 主系 | プロンプト構成後 | システム | API 呼び出し | Messages API を同期呼び出しする。モデル ID・`max_tokens`・構造化出力スキーマ・タイムアウトを明示指定する（→ §7） | - |
| 3 | 主系 | `stop_reason` が `end_turn` かつ応答が得られた | システム | 応答の検証 | スコアの値域（0〜10 の整数）を検証する（`is_valid_score()`）。通れば `EvaluationOutcome(ok)` を返す | （標準エラー・詳細ログ時のみ）`評価完了: {url} score={score}` |
| 4 | 代替系 | IF 要約が空または欠落している | システム | プロンプト構成 | タイトルのみでプロンプトを構成し、評価を継続する（F-001 AC-023） | （標準エラー）`{url} の要約が空です。タイトルのみで評価します` |
| 5 | 代替系 | IF 要約が切り詰め上限を超過している | システム | プロンプト構成 | 上限まで切り詰めてプロンプトへ渡す。**上限値は未決**（→ OQ-001） | （標準エラー）`{url} の要約を {n}文字に切り詰めました` |
| 6 | 代替系 | IF 応答の提案タグが空配列 | システム | 応答の検証 | 空のまま `EvaluationOutcome(ok)` を返す。失敗として扱わない（F-001 AC-027） | - |
| 7 | 代替系 | WHEN 意味的不正（→ フロー #10〜12）が1回目に発生 | システム | 実行内リトライ | 同一エントリを1回だけ再試行する（**暫定1回** → OQ-002）。試行回数を `attempts` として数える | （標準エラー）`{url} の評価に失敗しました（{理由}）。再試行します（{n}/{上限}）` |
| 8 | 代替系 | WHERE dry-run が指定されている | 運用者 | 評価の実行 | **通常実行と完全に同一の処理を行う**（F-005 AC-011。API を実際に呼び、コストも発生する）。返す `EvaluationOutcome` も同一。記録しないのは SPEC-002 側の分岐 | 通常実行と同じ |
| 9 | 例外系 | IF スコアが 0〜10 の範囲外・非整数 | システム | 応答の検証 | **意味的不正**として分類する。フロー #7 のリトライ後も再発したら `EvaluationOutcome(invalid_value, attempts)` を返し、当該エントリをスキップして次のエントリへ進む。範囲外のスコアを投入判定へ渡さない（F-001 AC-029） | （標準エラー）`{url} の評価スコアが範囲外です（{score}）。この記事をスキップします` |
| 10 | 例外系 | IF `stop_reason` が `max_tokens`（出力の途中切断） | システム | 応答の検証 | **意味的不正**として分類する。以降フロー #9 と同じ | （標準エラー）`{url} の評価応答が途中で切れました。この記事をスキップします` |
| 11 | 例外系 | IF `stop_reason` が `refusal` | システム | 応答の検証 | **意味的不正**として分類する。以降フロー #9 と同じ。構造化出力でもスキーマに従わない可能性があるため、フィールド参照の前に判定する（ADR-001 影響節） | （標準エラー）`{url} の評価が拒否されました。この記事をスキップします` |
| 12 | 例外系 | IF スコアは値域内だが理由が空文字 | システム | 応答の検証 | **成功として扱う**（意味的不正としない）。理由は投入判定に用いず、事後検証の可読性のみに影響するため（F-003 AC-002 の品質低下に留まる） | （標準エラー）`{url} の評価理由が空です` |
| 13 | 例外系 | WHEN API 呼び出しがネットワーク障害・5xx・429 で失敗 | システム | API 呼び出し | **API 呼び出し自体の失敗**として分類する。SDK の既定リトライ（指数バックオフ）に委ね、それでも失敗したら `EvaluationOutcome(api_error, attempts=0)` を返す。当該エントリをスキップし、残りのエントリの処理を継続する（F-001 AC-010） | （標準エラー）`{url} の評価に失敗しました: {種別}。次回実行で再評価します` |
| 14 | 例外系 | WHEN API 呼び出しがタイムアウトする | システム | API 呼び出し | フロー #13 と同じ分類・同じ戻り値。打ち切り時間は §7（F-001 AC-016） | （標準エラー）`{url} の評価がタイムアウトしました（{n}秒）。次回実行で再評価します` |

> **確認チェック:** 例外系9項目の検討結果
> - [x] **未認証アクセス** — API キー未設定は §2 の前提条件で扱い、起動時に中止する（F-001 AC-030）。フローには到達しない。**キーが無効（401）**な場合はフロー #13 に含まれる（API 呼び出し自体の失敗）
> - [x] **権限違反アクセス** — 本システムは認証・認可の機構を持たない（REQ-NF-005）。API キーのスコープ違反（403）はフロー #13 に含まれる
> - [x] **必須項目未入力** — フロー #4（要約の欠落）。`title` が空の場合は §5 のバリデーション表を参照
> - [x] **最大値・最小値超過** — フロー #9（スコアの値域）、フロー #5（要約長）、フロー #10（`max_tokens`）
> - [x] **空文字・NULL入力** — フロー #4（要約）、フロー #6（提案タグ）、フロー #12（理由）
> - [x] **外部システムの障害** — フロー #13（ネットワーク・5xx・429）
> - [x] **タイムアウト** — フロー #14
> - [x] **同時操作・競合** — **本仕様では発生しない。** 評価は単一プロセスの逐次処理であり（REQ-NF-002「スケールしない」）、同一エントリを同時に評価する経路がない。API 側のレート制限による拒否（429）は競合ではなく外部障害として フロー #13 で扱う
> - [x] **対象リソースが存在しない** — 評価対象エントリの不在（0件）は本仕様に到達しない（§2）。トリアージ基準ファイルの不在は §2 の前提条件（実行を中止する）
> - [x] **対象リソースが削除済み** — 記事が削除済みでも評価はタイトルと要約のみで行うため影響しない（本文を取得しない → F-001 Out of Scope）

## 4. 入出力定義

### 入力

プロンプトへ渡す項目。**エントリの取得は SPEC-001（未作成）、選定は SPEC-002 が行う。**
本仕様は選定済みの `Entry`（`contract/model.py`）1件を受け取る。

| 項目名 | 型 | 必須 | 制約 | NULL・空文字の扱い | 備考 |
|---|---|---|---|---|---|
| トリアージ基準 | string | Yes | `profile.md` の全文 | 空・読み込み不能なら実行を中止する（§2 前提条件）。基準なしで評価すると全件のスコアが無意味になるため | 変更には運用者の合意を要する（`.ref/spec.md` 要合意項目）。**内容は本仕様の対象外** |
| `title` | string | Yes | - | 空文字でも評価を実行する。要約が併せて空の場合は §5 のとおり評価に進まない | エントリの主要な判断材料 |
| `summary` | string | No | 切り詰め上限は未決（→ OQ-001） | 空・NULL のときはタイトルのみで評価する（フロー #4 / F-001 AC-023） | 実測で全文配信が2件（8,800字・9,238字） |
| `source_name` | string | No | `feeds.yaml` の `name` | 空文字として扱い、プロンプトから当該行を省く | 情報源の文脈を与える。**重みの加算はここで行わない**（→ SPEC-004） |
| モデル ID | string | Yes | ADR-003 が定める値 | 省略不可（SDK の必須パラメータ） | 設定として外出しする（ADR-001 トレードオフ表） |
| `max_tokens` | integer | Yes | §7 の値 | 省略不可 | 到達時はフロー #10 |

> **プロンプトに含めないもの:** API キー、Raindrop トークン、コレクション ID、`state.jsonl` の内容。
> 秘匿情報を評価の入力に混入させない（REQ-NF-006 / F-001 AC-033 → T-014）。

### 出力

呼び出し元（`pipeline`）へ返す `EvaluationOutcome`。**この型が SPEC-002 との受け渡し境界である**（§1.1）。

| 項目名 | 型 | 内容 | 条件 |
|---|---|---|---|
| `kind` | enum | `ok` / `invalid_value` / `truncated` / `refused` / `api_error` | 常時。`api_error` 以外の失敗は「意味的不正」に属する（→ §5 分類表） |
| `verdict` | `Verdict` \| null | スコア・理由・提案タグ（`contract/model.py`） | `kind == ok` のときのみ非 null。失敗時は必ず null（範囲外スコアを後段へ渡さないため） |
| `attempts` | integer | **当該実行内で意味的不正により消費した試行回数。** SPEC-002 が `failure_count` に加算する量そのもの | 意味的不正の失敗時は 1 以上。`ok` および `api_error` のときは 0 |
| `error_detail` | string | 失敗の内容（範囲外スコアの実値・`stop_reason`・例外の種別）。**API キーを含めない** | 失敗時のみ。サマリ・ログへ出力する |
| `usage` | (入力トークン数, 出力トークン数) \| null | API 応答の `usage`。コスト算出の一次データ（F-004 AC-004） | 応答が得られたときのみ。**算出方法は未決** → OQ-003 |

> **`attempts` が `api_error` のとき 0 である理由:** F-001 AC-015a により API 呼び出し自体の
> 失敗は失敗回数に計上しない。SPEC-002 側で「種別を見て加算しない」分岐を持たせるより、
> **加算量そのものを 0 にして渡す**ほうが、加算側に判別ロジックを二重に持たせずに済む。
> ただし SPEC-002 §6 の状態遷移表は種別を明示的に区別しているため、`kind` も併せて返す。

## 5. バリデーション仕様

> フロー定義表（§3）が「いつ・どう振る舞うか」を定めるのに対し、本節は
> **どの条件をどちらの失敗種別に分類するか**の対応表である。SPEC-002 §6 の
> 「意味的不正 / API 呼び出し自体」の2イベントはこの表を参照する。

### 5.1 失敗の分類基準

**判別の原則: 「Anthropic API から応答本体を受け取れたか」を境界とする。**
受け取れていないなら外部の一時的な障害であり（`api_error`）、受け取った上で内容が
使えないなら本システムが引き受ける失敗である（意味的不正）。

| 観測された事象 | 分類 | `failure_count` への計上 | 根拠 |
|---|---|---|---|
| `stop_reason == end_turn` かつスコアが 0〜10 の整数 | 成功 | しない | F-001 AC-001 |
| スコアが 0〜10 の範囲外、または非整数（`bool` を含む） | 意味的不正 | **する**（`attempts` 分） | F-001 AC-029 / AC-015 |
| `stop_reason == max_tokens`（切断） | 意味的不正 | **する** | ADR-001 影響節 |
| `stop_reason == refusal` | 意味的不正 | **する** | ADR-001 影響節 |
| 接続不能・DNS 失敗・TLS 失敗 | API 呼び出し自体 | しない | F-001 AC-015a |
| HTTP 5xx | API 呼び出し自体 | しない | F-001 AC-015a |
| HTTP 429（レート制限） | API 呼び出し自体 | しない | F-001 AC-015a |
| HTTP 401 / 403（キーが無効・権限不足） | API 呼び出し自体 | しない | F-001 AC-033。**ただし全件が同一理由で失敗する → OQ-004** |
| タイムアウト | API 呼び出し自体 | しない | F-001 AC-016 / AC-015a |

> **境界事例の扱い:** HTTP 400（リクエスト不正）は応答本体を受け取っているが、
> 原因は本システムのプロンプト構成・スキーマ定義にあり**再試行で解決しない**。
> 意味的不正として計上すると、こちらのバグでエントリの失敗回数を消費してしまう。
> したがって `api_error` に分類する（計上しない）。

### 5.2 入力・応答の検証

| 項目 | ルール | タイミング | エラーメッセージ |
|---|---|---|---|
| `title` と `summary` | 少なくとも一方が非空であること | プロンプト構成時 | 両方とも空なら API を呼ばず、意味的不正として扱わずスキップする: `{url} はタイトルも要約も空のため評価できません`（**上位に AC がない** → OQ-005） |
| `score` | 0〜10 の整数であること（`is_valid_score()`。`bool` は不正） | 応答受領時 | `{url} の評価スコアが範囲外です（{score}）。この記事をスキップします` |
| `reason` | 文字列であること。空文字を許容する | 応答受領時 | `{url} の評価理由が空です`（警告のみ。スキップしない） |
| `suggested_tags` | 文字列の配列であること。空配列を許容する | 応答受領時 | 非配列・非文字列要素は除去し警告する: `{url} の提案タグの一部を解釈できません。除外します` |
| `stop_reason` | `end_turn` であること | 応答受領時 | §3 フロー #10 / #11 のメッセージ |
| プロンプト全体 | 秘匿情報を含まないこと | プロンプト構成時 | 秘匿値の混入は実装上の欠陥であり実行時メッセージを持たない。T-014 で検出する |

## 6. 状態遷移

**対象外** — 本仕様が扱うのは1件のエントリに対する1回の評価であり、永続的な状態を持たない
（実行内リトライの試行回数はフロー #7 の局所的なカウンタであり、エンティティの状態ではない）。

処理済みエントリの状態機械（未知 / 評価失敗（継続中）/ 評価失敗（打ち切り）/ 評価済み）は
[SPEC-002 §6](SPEC-002_state_management.md#6-状態遷移) に一元化されている。
本仕様が返す `EvaluationOutcome` はその遷移のイベントに対応するが、遷移の定義は持たない（→ §1.1）。

## 7. 非機能仕様（この仕様固有）

| 観点 | 仕様 | 対応要件 |
|---|---|---|
| パフォーマンス | 1件あたり 2.7〜5.3秒（`claude -p` での実測を安全側に流用 → TASK-038）。逐次処理で 100件・5〜8分。上限200件（暫定）でも 30分以内に収まること | REQ-NF-001, ADR-001 |
| タイムアウト | 評価1件あたりの API 呼び出しに明示的なタイムアウトを設定する。**具体値は未決**（→ OQ-006）。上限件数200件（暫定）× タイムアウト値が REQ-NF-001 の30分を超えてはならない | REQ-NF-004「タイムアウト」, F-001 AC-016 |
| リトライ（実行内） | 意味的不正に限り暫定1回再試行する（→ OQ-002）。API 呼び出し自体の失敗は SDK の既定リトライに委ね、実行内の追加リトライを行わない（二重リトライで所要時間が積算しないため） | REQ-NF-004「リトライ（実行内）」 |
| コスト | 1件あたり入力約550トークン・出力約150トークン想定。Haiku 4.5 で年 $2.70。`max_tokens` を明示指定して出力側の上振れを構造的に抑える | REQ-NF-002a, ADR-003 |
| **秘匿情報の非出力** | API キーを **プロンプト・ログ・`error_detail`・サマリ・例外メッセージのいずれにも出力しない**。SDK 例外の文字列化がヘッダを含む可能性があるため、例外はそのまま流さず種別と HTTP ステータスのみを取り出して `error_detail` に詰める | REQ-NF-006, F-001 AC-033 |
| 決定論性の分離 | API 呼び出し（確率的）は `adapters` に隔離し、応答の検証（決定論的）は `domain/scoring.py` の `is_valid_score()` で行う。範囲外スコアが投入判定へ到達する経路を層の契約で塞ぐ | ADR-004 設計原則(3) |
| 部分障害の分離 | 1件の評価失敗が他のエントリの処理を停止させない。本仕様は例外を呼び出し元へ伝播させず、必ず `EvaluationOutcome` を返す | REQ-NF-004, REQ-F-010, F-001 AC-010 |
| 終了コード | **本仕様は終了コードを決定しない。** 個別エントリの評価失敗は非0終了の理由にならない（`contract/exit_codes.py`。正典は SPEC-005（未作成）） | F-001 AC-010 |

---

> **実装参考: API 呼び出しの形（ADR-001 / ADR-003 の帰結）**
>
> ```
> client.messages.create(
>     model="<ADR-003 が定めるモデル ID>",   # 必須パラメータ。既定へのフォールバックなし
>     max_tokens=<§7 の値>,
>     timeout=<OQ-006 で確定>,
>     system=<profile.md の全文>,
>     messages=[{"role": "user", "content": <title + summary + source_name>}],
>     output_config={"format": {...}},        # 構造化出力。スキーマ違反は発生しない
> )
> ```
>
> 応答から取り出す順序は **`stop_reason` の判定 → フィールド参照** とする。
> `refusal` 時はスキーマに従わない可能性があるため（ADR-001 影響節）、
> 先にフィールドへ触れると例外の種別が失敗分類を誤らせる。

## 10. テスト観点

| # | テスト観点 | 種別 | 対応AC | 反証可能性（どう壊せばレッドになるか） |
|---|---|---|---|---|
| T-001 | 正常系: 有効な応答からスコア・理由・提案タグを持つ `Verdict` が得られること | 機能テスト | F-001 AC-001 | 応答の `reason` / `suggested_tags` を捨てて `score` のみ返す実装にすればレッド（F-003 AC-002 / AC-002a の供給元が消える） |
| T-002 | 正常系: dry-run でも通常実行と同一の `EvaluationOutcome` が返ること | 機能テスト | F-005 AC-011 | dry-run 時に API 呼び出しを短絡してダミーのスコアを返せばレッド |
